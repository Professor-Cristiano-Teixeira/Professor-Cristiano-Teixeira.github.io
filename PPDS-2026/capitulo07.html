2º Bimestre • Capítulo 07 (100 min/semana)

Classes Abstratas e Interfaces (C#)

Agora que temos Produto, Lanche e Bebida, vamos dar um passo a mais no design: usar classe abstrata para impedir que existam “produtos genéricos” e usar interfaces para garantir capacidades (ex.: calcular total e gerar etiqueta) sem depender apenas de herança.

Roteiro Passo a passo Atividades

Objetivos de aprendizagem

  • Explicar o que é classe abstrata e por que ela não pode ser instanciada.
  • Criar membros abstratos (obrigatórios) e membros concretos (reaproveitáveis) na mesma classe.
  • Explicar o que é interface e quando usar em vez de herança.
  • Aplicar interfaces no projeto: IEtiquetavel e IPrecificavel.
  • Refatorar o cadastro para criar o tipo correto (Lanche/Bebida) — já preparando MVC do Cap. 08.

Pré-requisitos

  • Capítulo 06 concluído (venda simples + CalcularTotalVenda)
  • Projeto organizado por pastas/namespaces (Cap. 04)
  • Herança e override funcionando (Cap. 05)
Observação
Como vamos tornar Produto abstrato, o cadastro precisa escolher o tipo (Lanche/Bebida) para criar objetos.

1) Parte teórica (conceitos essenciais)

1.1 Classe abstrata (abstract)

Uma classe abstrata é uma classe que não pode ser instanciada. Ela existe para servir como “modelo base” e para concentrar código comum. Você usa classe abstrata quando faz sentido dizer: “nunca deve existir um objeto desse tipo genérico”.

No nosso caso: faz sentido existir um Lanche e uma Bebida, mas não faz muito sentido existir um “Produto” genérico sem tipo. Então vamos tornar Produto abstrato.

1.2 Membros abstratos x membros virtuais

Um membro abstrato (propriedade/método) não tem implementação na classe base e obriga as classes filhas a implementarem. Já um membro virtual tem implementação padrão e permite que a filha sobrescreva se quiser.

Exemplo: queremos Tipo e Detalhes obrigatórios (cada produto deve dizer o seu). Então vamos torná-los abstratos. Já Etiqueta() pode ter implementação padrão e permitir customização (pode ser virtual).

1.3 Interface (contrato de capacidades)

Uma interface define um contrato: um conjunto de membros que uma classe promete ter. Ela não diz como fazer, só define o que deve existir. Interfaces são úteis quando diferentes classes (nem sempre relacionadas) precisam oferecer a mesma capacidade.

No projeto, vamos criar duas interfaces simples: IEtiquetavel (gera etiqueta) e IPrecificavel (calcula total). Assim, um método pode aceitar “qualquer coisa que gere etiqueta”, sem se importar se é Lanche, Bebida, Combo etc.

Regra prática
Herança resolve reutilização e relação “é um”. Interface resolve “tem a capacidade de”. Classe abstrata resolve “tipo genérico não deve existir como objeto”.

2) Passo a passo (abstratas + interfaces no projeto)

Vamos criar as interfaces, tornar Produto abstrato e adaptar o cadastro para criar Lanche/Bebida. Depois vamos reaproveitar interfaces para gerar etiqueta e calcular total.

Antes de começar

  1. Abra a solução LanchoneteApp.
  2. Garanta que o Cap. 06 está funcionando (Venda simples abre e calcula).
  3. Faça um commit (se usar Git) ou crie uma cópia da pasta do projeto (backup).

Passo 1 — Criar interfaces em Models

  1. Crie Models/IEtiquetavel.cs
  2. Crie Models/IPrecificavel.cs
Arquivo: Models/IEtiquetavel.cs
namespace LanchoneteApp.Models
{
    public interface IEtiquetavel
    {
        string Etiqueta();
    }
}
Arquivo: Models/IPrecificavel.cs
namespace LanchoneteApp.Models
{
    public interface IPrecificavel
    {
        decimal CalcularTotalVenda(int quantidade, decimal descontoPercentual = 0);
    }
}
Interfaces são “contratos”: qualquer classe que implementar deve ter esses métodos.

Passo 2 — Tornar Produto uma classe abstrata e implementar as interfaces

Agora vamos: (1) declarar abstract class Produto, (2) implementar IEtiquetavel e IPrecificavel, (3) tornar Tipo e Detalhes abstratos (obrigatórios).

  1. Abra Models/Produto.cs.
  2. Altere o cabeçalho da classe e as propriedades conforme o trecho abaixo.
Arquivo: Models/Produto.cs (trechos principais para ajustar)
namespace LanchoneteApp.Models
{
    // Produto agora é abstrato e implementa interfaces
    public abstract class Produto : IEtiquetavel, IPrecificavel
    {
        // ... (mantenha seus campos/propriedades/constructores existentes)

        // Agora são obrigatórios nas classes filhas
        public abstract string Tipo { get; }
        public abstract string Detalhes { get; }

        // Etiqueta pode continuar com implementação padrão (virtual)
        public virtual string Etiqueta()
        {
            return $"[{Tipo}] {Nome} • Preço: {Preco:C} • Estoque: {Estoque} • {Detalhes}";
        }

        // CalcularTotalVenda já existe do Cap. 06. Mantenha virtual.
        public virtual decimal CalcularTotalVenda(int quantidade, decimal descontoPercentual = 0)
        {
            // (mantenha sua implementação)
        }
    }
}
Atenção
Depois dessa mudança, não será possível fazer new Produto(...). Por isso, no próximo passo vamos adaptar o Service/Form para criar Lanche ou Bebida.

Passo 3 — Ajustar Lanche e Bebida para cumprir os membros abstratos

Como Tipo e Detalhes ficaram abstratos, as classes filhas precisam implementar. Elas já tinham override, então normalmente basta garantir que está usando override corretamente.

Arquivo: Models/Lanche.cs (garanta override das propriedades)
public override string Tipo => "Lanche";
public override string Detalhes => $"Tamanho: {Tamanho}";
Arquivo: Models/Bebida.cs (garanta override das propriedades)
public override string Tipo => "Bebida";
public override string Detalhes => $"{VolumeMl}ml • {(Alcoolica ? "Alcoólica" : "Não alcoólica")}";
Ok!
Agora Lanche e Bebida cumprem o contrato da classe abstrata.

Passo 4 — Refatorar o Service: criar produto por tipo (factory simples)

Antes, o Service criava new Produto(...) quando o ID estava vazio. Agora isso não existe. Vamos criar um método de cadastro que recebe o tipo e campos específicos.

  1. Abra Services/ProdutoService.cs.
  2. Adicione o método abaixo (ou substitua o método antigo de criação, se preferir):
Arquivo: Services/ProdutoService.cs (novo método CriarProdutoPorTipo)
public Produto CriarProdutoPorTipo(
    string tipo,
    string? idTexto,
    string nome,
    string precoTexto,
    string estoqueTexto,
    string? tamanhoTexto,
    string? volumeTexto,
    bool alcoolica)
{
    // validações comuns (aproveite sua lógica existente)
    nome = (nome ?? "").Trim();
    if (string.IsNullOrWhiteSpace(nome))
        throw new ArgumentException("Informe o nome.");

    var cultura = new CultureInfo("pt-BR");
    if (!decimal.TryParse(precoTexto, NumberStyles.Any, cultura, out decimal preco))
        throw new ArgumentException("Preço inválido.");

    int estoque = 0;
    if (!string.IsNullOrWhiteSpace(estoqueTexto))
    {
        if (!int.TryParse(estoqueTexto, out estoque))
            throw new ArgumentException("Estoque inválido.");
    }

    // id opcional
    int? id = null;
    if (!string.IsNullOrWhiteSpace(idTexto))
    {
        if (!int.TryParse(idTexto, out int tmp))
            throw new ArgumentException("ID inválido.");
        if (_repo.FindById(tmp) != null)
            throw new InvalidOperationException("Já existe um produto com esse ID.");
        id = tmp;
    }

    Produto novo;
    tipo = (tipo ?? "").Trim().ToLower();

    if (tipo == "lanche")
    {
        string tamanho = (tamanhoTexto ?? "").Trim();
        if (string.IsNullOrWhiteSpace(tamanho))
            throw new ArgumentException("Informe o tamanho do lanche.");

        novo = id.HasValue
            ? new Lanche(id.Value, nome, preco, estoque, tamanho)
            : new Lanche(nome, preco, estoque, tamanho);
    }
    else if (tipo == "bebida")
    {
        if (!int.TryParse(volumeTexto, out int volume) || volume <= 0)
            throw new ArgumentException("Informe o volume (ml) da bebida.");

        novo = id.HasValue
            ? new Bebida(id.Value, nome, preco, estoque, volume, alcoolica)
            : new Bebida(nome, preco, estoque, volume, alcoolica);
    }
    else
    {
        throw new ArgumentException("Tipo inválido. Use Lanche ou Bebida.");
    }

    _repo.Add(novo);
    return novo;
}
Conceito importante
Isso é uma “factory simples”: um método que decide qual classe instanciar. Você está preparando o terreno para padrões (Cap. 08 MVC e, mais tarde, DAO).

Passo 5 — Atualizar o FrmProdutos para escolher o tipo

Agora a tela deve permitir escolher Lanche ou Bebida e exibir campos específicos. Faça assim (simples):

  1. No Designer do FrmProdutos, adicione um ComboBox cboTipo com itens: Lanche e Bebida.
  2. Adicione campos específicos:
  • Para lanche: TextBox txtTamanho (Label: Tamanho)
  • Para bebida: TextBox txtVolume (Label: Volume (ml)) + CheckBox chkAlcoolica (Text: Alcoólica)

Dica visual: deixe os campos em um GroupBox “Dados do tipo”.

Agora, no código do form, carregue o combo e altere o botão Adicionar para usar o novo método do service:

Arquivo: Views/FrmProdutos.cs (inicializar o combo)
// no construtor do FrmProdutos, após InitializeComponent():
cboTipo.Items.Clear();
cboTipo.Items.AddRange(new object[] { "Lanche", "Bebida" });
cboTipo.SelectedIndex = 0;
Arquivo: Views/FrmProdutos.cs (btnAdicionar_Click atualizado)
private void btnAdicionar_Click(object sender, EventArgs e)
{
    try
    {
        string tipo = cboTipo.SelectedItem?.ToString() ?? "";

        _service.CriarProdutoPorTipo(
            tipo,
            txtId.Text,
            txtNome.Text,
            txtPreco.Text,
            txtEstoque.Text,
            txtTamanho.Text,
            txtVolume.Text,
            chkAlcoolica.Checked
        );

        AtualizarGrid();

        // limpar
        txtId.Clear(); txtNome.Clear(); txtPreco.Clear(); txtEstoque.Clear();
        txtTamanho.Clear(); txtVolume.Clear(); chkAlcoolica.Checked = false;
        txtNome.Focus();
    }
    catch (Exception ex)
    {
        MessageBox.Show(ex.Message, "Atenção", MessageBoxButtons.OK, MessageBoxIcon.Warning);
    }
}
Resultado
Agora o sistema não cria “Produto genérico”. Ele cria um Lanche ou Bebida, respeitando a classe abstrata.

Passo 6 — Usar interfaces no código (sem depender da classe concreta)

Vamos criar métodos utilitários (pode ser no Service ou Utils) que aceitam interfaces. Isso mostra o poder das interfaces: o método não precisa saber se é Bebida/Lanche.

  1. Crie uma classe Utils/Operacoes.cs (ou coloque no Service) com os métodos abaixo.
Arquivo: Utils/Operacoes.cs
using LanchoneteApp.Models;

namespace LanchoneteApp.Utils
{
    public static class Operacoes
    {
        public static string GerarEtiqueta(IEtiquetavel item)
        {
            return item.Etiqueta();
        }

        public static decimal CalcularTotal(IPrecificavel item, int qtd, decimal desconto = 0)
        {
            return item.CalcularTotalVenda(qtd, desconto);
        }
    }
}

Agora, em qualquer lugar (ex.: botão Etiqueta no FrmProdutos), você pode usar:

Exemplo: Views/FrmProdutos.cs (usar interface)
using LanchoneteApp.Utils;

// ...
if (dgvProdutos.CurrentRow?.DataBoundItem is Produto p)
{
    MessageBox.Show(Operacoes.GerarEtiqueta(p), "Etiqueta", MessageBoxButtons.OK, MessageBoxIcon.Information);
}
O que você ganhou com isso?
Agora o código pode trabalhar com IEtiquetavel e IPrecificavel. Se amanhã surgir Combo, basta implementar as interfaces — sem mudar o resto.

3) Atividades práticas (para fixar)

Faça 2 atividades (ou todas para bônus). Elas reforçam abstract + interface.

Atividade A — Criar Combo como novo tipo
  • Crie Combo : Produto com Itens e DescontoPercentual.
  • Implemente Tipo e Detalhes (obrigatórios).
  • Override de CalcularTotalVenda aplicando desconto extra do combo.
Atividade B — Interface extra: IExportavel
  • Crie IExportavel com método string ToCsv().
  • Implemente em Lanche e Bebida (CSV com campos principais).
  • Crie um botão no form para exportar o item selecionado (MessageBox com CSV).
Atividade C — Melhorar UI: mostrar campos por tipo
  • No evento cboTipo_SelectedIndexChanged, oculte/mostre campos (tamanho vs volume/alcoolica).
  • Garanta que a validação acompanha (não exigir volume quando for lanche, etc.).
  • Mostre mensagens amigáveis quando faltar dado do tipo.

Critérios rápidos

  • Produto abstrato e sem instância direta.
  • Classes filhas implementam Tipo e Detalhes (obrigatório).
  • Uso correto de interfaces em pelo menos 1 ponto do código.
  • Projeto compila e funciona.
