Uma **SPA (Single Page Application)** é um modelo no qual o navegador carrega um HTML “base” apenas uma vez e, a partir daí, a navegação e as atualizações de tela acontecem com JavaScript, trocando componentes e dados sem recarregar a página inteira. Isso deixa a experiência mais fluida (menos “pisca”), permite manter estados (como filtros e carrinho) enquanto o usuário navega e reduz a quantidade de requisições de páginas completas. O **React** é uma biblioteca para criar interfaces compondo pequenas partes (componentes). Já o **Next.js** é um framework que “organiza a casa”: ele define uma estrutura de pastas, oferece roteamento pronto, otimiza build e entrega, e possibilita uma **renderização híbrida**. Híbrida significa que, dependendo do que você escrever, a página pode ser: - **CSR (Client-Side Rendering)**: a tela é montada no navegador; ótimo para interações e estado local. - **SSG (Static Site Generation)**: gera HTML no build; ideal para conteúdo estável e rápido. - **SSR (Server-Side Rendering)**: gera HTML em cada requisição; ideal para dados “ao vivo”. No **App Router** (pasta `/app`), o Next.js transforma pastas em rotas. Isso diminui o “trabalho manual” de configurar rotas e ajuda a manter o projeto consistente. Dois arquivos são fundamentais: - `app/layout.jsx`: define o **layout compartilhado** (estrutura comum em todas as páginas). - `app/page.jsx`: define o conteúdo da rota raiz `/` (a Home). > Exemplo aplicado no Passo a Passo > > No passo a passo, quando você cria `app/layout.jsx` e coloca **Header** e **Footer** ali, você está aplicando a ideia de “layout compartilhado”. Em seguida, ao criar `app/page.jsx`, você define o conteúdo específico da Home. Isso já te dá uma navegação de SPA com estrutura organizada. ### 2) Framework CSS: por que Bootstrap 5 Em projetos reais, a maior parte do tempo não está em “inventar” um layout do zero, e sim em **entregar uma interface** que funcione bem em telas diferentes, seja consistente e seja fácil de manter. Um **framework CSS** como o Bootstrap acelera isso porque ele já traz um conjunto de padrões prontos. O Bootstrap 5 entrega três pilares importantes: - **Grid responsivo**: você monta layouts com `container`, `row` e `col-*`, e o conteúdo se adapta automaticamente entre celular, tablet e desktop. - **Utilitários**: classes rápidas para espaçamento, alinhamento e display (por exemplo, `p-3` para padding, `m-2` para margin, `d-flex`, `gap-2` etc.). Isso reduz CSS “manual” e aumenta produtividade. - **Componentes**: Navbar, Cards, Buttons, Alerts, Modals, Offcanvas… todos com estilos consistentes. Em muitos casos você só monta a estrutura HTML/JSX e aplica as classes. Além disso, os **Bootstrap Icons** fornecem ícones vetoriais fáceis de usar com classes `bi bi-*`. Em um projeto educacional, isso ajuda a reforçar semântica visual (um ícone de carrinho, de lista, de contato) sem depender de imagens externas. > Exemplo aplicado no Passo a Passo > > No passo a passo, quando você instala `bootstrap` e `bootstrap-icons` e depois cria uma Home com `container`, `row`, `col-md-4` e `card`, você aplica diretamente o grid e os componentes. A Navbar responsiva com `navbar-expand-lg` e `collapse` também é um exemplo clássico de componente Bootstrap. ### 3) Git (início) Git é uma ferramenta de **controle de versão**. Pense nele como uma “linha do tempo” do seu projeto. Em vez de salvar arquivos com nomes como *projeto-final-versao3*, você registra mudanças em etapas chamadas **commits**. Cada commit guarda o estado do código naquele momento e uma mensagem descrevendo o que foi feito. Isso traz benefícios práticos para estudar e trabalhar: - **Segurança**: se algo quebrar, você consegue voltar para um ponto que estava funcionando. - **Organização**: dá para ver o histórico do que foi feito e por quê. - **Trabalho em etapas**: você implementa pequenas partes, testa e “salva” com commit. Uma **branch** é uma “linha paralela” de desenvolvimento. Em projetos maiores, você pode criar uma branch para uma funcionalidade (ex.: `cap1` ou `final/cap16`), trabalhar sem afetar a principal, e depois juntar. Aqui, já no começo, a disciplina de commits pequenos ajuda a evitar retrabalho. > Exemplo aplicado no Passo a Passo > > No passo a passo, quando você executa `git init`, faz `git add .` e registra um commit como *“chore: bootstrap projeto Next.js + Bootstrap para Lanchonete”*, você cria o primeiro marco do projeto. Depois, ao criar Header/Footer e fazer novos commits, você pratica a ideia de “pequenas entregas versionadas”. ### 4) ESLint & Prettier (padrões de código) Quando muitas pessoas (ou você mesmo ao longo do tempo) mexem no mesmo projeto, o código pode ficar inconsistente: aspas diferentes, tamanhos de linha, indentação irregular, nomes confusos. Isso dificulta ler e revisar. Para resolver, usamos duas ferramentas complementares: - **ESLint**: procura problemas de qualidade e possíveis bugs (por exemplo, variáveis não usadas, padrões perigosos, regras recomendadas do React/Next). - **Prettier**: padroniza a formatação automaticamente (espaços, quebras de linha, aspas, ponto e vírgula). Ele reduz discussões sobre “estilo” e deixa o foco na lógica. O ganho real é que você passa a **estudar o código com menos distrações**. Quando o arquivo está bem formatado e sem avisos críticos, fica mais fácil identificar conceitos como componentes, props, estado e rotas nos capítulos seguintes. > Exemplo aplicado no Passo a Passo > > No passo a passo, ao criar o arquivo `.prettierrc` e rodar `npm run lint`, você valida que o projeto está seguindo padrões mínimos. Isso evita que pequenos erros (como imports errados ou variáveis não usadas) virem problemas maiores quando você começar a criar páginas e componentes mais complexos. ## Questionário (com gabarito) Responda cada questão e confira a alternativa correta indicada ao final. ### 1. O `map` percorre cada item do array e devolve um novo array com JSX. É por isso que você vê o padrão: *lista.map(item => ``)*. Porém, quando renderizamos listas, o React precisa de um jeito de **identificar cada item** entre renderizações. Imagine que você aplicou um filtro e a lista mudou de ordem, ou que um item foi ocultado por estar esgotado. Se o React não souber qual “card” corresponde a qual item, ele pode reaproveitar o DOM errado e causar efeitos estranhos (por exemplo, um badge ou foco “pular” para outro item). É exatamente para isso que existe a **key**. A key deve ser: - **Única** dentro daquela lista (nenhum item pode repetir a mesma key). - **Estável** (não deve mudar quando você filtra, ordena ou altera a lista). - **Semântica** (idealmente, um `id` do produto, e não o índice do array). Por que evitar o índice do array? Porque o índice muda quando a lista muda. Isso reduz configurações manuais e deixa o projeto mais fácil de entender, porque você “enxerga” as rotas olhando para as pastas. A regra principal é: dentro de `app/`, uma pasta representa um segmento da rota, e o arquivo `page.jsx` define o conteúdo daquela rota. Por exemplo, `app/cardapio/page.jsx` vira `/cardapio`. Esse padrão é importante porque, conforme o sistema cresce, você adiciona páginas apenas criando arquivos no lugar certo. Além do `page.jsx`, o App Router introduz arquivos especiais que ajudam a organizar comportamento por rota: - `layout.jsx`: estrutura compartilhada por um conjunto de páginas (ex.: sidebar do admin). - `loading.jsx`: fallback enquanto uma rota carrega (melhora UX). - `not-found.jsx`: página 404 contextual (por escopo). - `error.jsx`: error boundary da rota (captura erros naquele segmento). Outro recurso do App Router é a possibilidade de definir **metadados** (título/descrição) no layout ou na página com `export const metadata`. Isso melhora organização e SEO, além de deixar cada área (como /admin) com identidade própria. > Exemplo aplicado no Passo a Passo > > No passo a passo, você cria `app/favoritos/page.jsx` para ter a rota `/favoritos` (Etapa 2) e cria `app/admin/layout.jsx` para que todas as páginas dentro de `/admin` herdem a sidebar (Etapa 5). Isso é file-based routing + layout aninhado funcionando na prática. ### 2) Navegação SPA com Link e usePathname Em aplicações modernas, queremos navegação rápida e sem recarregar a página inteira. Ele faz navegação no estilo SPA: quando você clica, o Next troca a rota e carrega somente o necessário, preservando parte do estado e evitando o “reload completo” que acontece com um `` tradicional. Para menus, um detalhe de UX importante é mostrar qual página está ativa. No App Router, você consegue ler a rota atual com `usePathname()` (hook do Next). Como hooks rodam no cliente, isso exige que o componente seja um **Client Component**. Depois, você compara o `pathname` com o `href` do link e aplica uma classe como `active`. O aluno aprende aqui um padrão muito usado em sistemas: **estado visual baseado na rota atual**. Um cuidado comum em menus: quando você tem rotas “filhas” (ex.: `/cardapio` e `/cardapio/[id]`), faz sentido marcar o menu como ativo também nas páginas internas. Assim, `app/cardapio/[id]/page.jsx` vira qualquer URL do tipo `/cardapio/`. O valor do parâmetro chega no componente da página via `params`. Como o arquivo de detalhe, por padrão, é um Server Component, você pode buscar dados ali de forma direta (neste capítulo, no dataset). A lógica típica é: 1. Ler `params.id`. 2. Você pode ter um `not-found.jsx` global (em `app/`) ou específico (por exemplo, dentro de `app/cardapio`). O Next escolhe o mais específico disponível para aquele “escopo” de rota. Agora vamos consolidar o Grid como uma “linguagem de layout” completa. O objetivo do Grid não é apenas colocar colunas na tela, mas permitir que a interface se adapte a diferentes tamanhos de tela com o mínimo de CSS manual. Os **breakpoints** são pontos de mudança de layout (xs, sm, md, lg, xl). Quando você usa classes como `col-sm-6` ou `col-lg-4`, está dizendo: “a partir desta largura, o elemento ocupa este tanto de colunas”. O Bootstrap segue a lógica *mobile-first*: você define o comportamento para telas pequenas primeiro e vai melhorando para telas maiores. Os **gutters** (classes `g-1` até `g-5`, ou separadas em `gx-*` e `gy-*`) controlam o espaçamento entre colunas e linhas. Isso é importante para legibilidade: cards muito juntos parecem “amontoados”. Em layouts mais complexos, aparecem dois recursos valiosos: - **Order** (`order-*`): muda a ordem de blocos sem alterar o HTML (ex.: imagem primeiro no mobile, texto primeiro no desktop). - **Offset** (`offset-*`): cria “margem” em colunas, útil para centralizar ou criar respiros em telas grandes. > Exemplo aplicado no Passo a Passo > > No passo a passo (Etapa 2), você revisa a Home com um banner e botões usando utilitários, e na prática do Cap. 3/4 você já usa `col-12 col-sm-6 col-lg-4` para o catálogo. Aqui, você aplica o “Grid avançado” ao ajustar espaçamento com `g-4` e, se quiser refinar o layout do banner, pode usar `order-md-*` para reorganizar elementos em telas maiores. ### 2) Utilitários essenciais Os utilitários do Bootstrap são classes pequenas que resolvem problemas comuns de layout sem você escrever CSS. Eles são especialmente úteis em projetos didáticos porque ajudam a manter consistência e acelerar entrega. A ideia é: **usar utilitários para 80% dos ajustes** e recorrer a CSS customizado apenas quando fizer sentido. Os grupos de utilitários mais usados neste capítulo são: - **Espaçamento**: `p-*`, `px-*`, `py-*`, `m-*`, `my-*` e `gap-*` (este é excelente em flex/grid). - **Display/visibilidade**: `d-none`, `d-md-block`, `d-flex`, `d-grid` para adaptar UI por tamanho. - **Alinhamento com flex**: `justify-content-between`, `align-items-center` para distribuir e alinhar itens. - **Cores**: `bg-*`, `text-*`, `text-bg-*` para planos, textos e badges consistentes. Um “atalho mental”: se você quer alinhar elementos em uma linha com espaçamento entre eles, use `d-flex` com `justify-content-between` (extremos) ou `gap-2` (distância constante). Se quer botões ocupando toda a largura, use `d-grid` (ou `w-100` em casos simples). > Exemplo aplicado no Passo a Passo > > Na Etapa 2, ao refatorar o hero da Home, você aplica utilitários como `py-5`, `text-center`, `d-flex`, `justify-content-center` e `gap-2` para alinhar os botões. Isso demonstra como montar uma UI agradável sem escrever CSS extra. ### 3) Customização por CSS Variables e `data-bs-theme` A partir do Bootstrap 5, boa parte do tema é controlada por **variáveis CSS** (os “tokens” do design). Isso significa que você consegue alterar cores, bordas e outros detalhes **sem precisar usar SASS**. Em vez de recompilar o framework, você sobrescreve variáveis como `--bs-primary` e `--bs-border-radius` no seu CSS. O benefício educacional é enorme: os alunos enxergam que a identidade visual pode ser centralizada em poucos pontos e aplicada em toda a UI. Ao mudar `--bs-primary`, por exemplo, botões, links, badges e componentes que usam “primary” herdam a nova cor. Já o atributo `data-bs-theme` é um mecanismo simples para alternar entre modo claro e escuro. Quando você define `data-bs-theme="dark"` no `` (ou em um container), o Bootstrap ativa tokens de cor compatíveis com dark mode. Você pode complementar isso sobrescrevendo variáveis específicas em `:root[data-bs-theme='dark']`. Um ponto importante: tema não é só “ficar bonito”. Ele também pode melhorar legibilidade (contraste), reduzir cansaço visual e criar consistência de marca. > Exemplo aplicado no Passo a Passo > > Na Etapa 1, você sobrescreve variáveis como `--bs-primary` e `--bs-border-radius` em `app/globals.css`, e cria um botão `ThemeToggle` que alterna `data-bs-theme` no elemento `document.documentElement`. O resultado é que toda a aplicação muda para o tema escuro/claro sem trocar arquivos CSS. ### 4) Componentes com JS API (Modal e Toast) Alguns componentes do Bootstrap são apenas CSS (ex.: badges, cards), mas outros precisam de JavaScript porque têm comportamento: abrir/fechar, animar, controlar foco. É o caso de **Modal** e **Toast**. Como o projeto já carrega o `bootstrap.bundle.min.js` no cliente (via `BootstrapClient`), a **API JavaScript** do Bootstrap fica disponível. Quando usamos React, o padrão mais seguro é: o React controla **quando** o componente deve abrir/fechar (por estado), e o Bootstrap executa a UI/animação (por instância). Por isso, usamos `ref` para acessar o elemento DOM e chamamos `Modal.getOrCreateInstance(...)` ou `Toast.getOrCreateInstance(...)`. Esse padrão evita bugs de “duas fontes de verdade”: React controla intenção; Bootstrap controla o comportamento visual. Também é uma boa prática usar **import dinâmico** do bundle do Bootstrap dentro do effect, garantindo que esse código rode só no cliente. > Exemplo aplicado no Passo a Passo > > Na Etapa 3, você cria `ToastContainer` que, ao receber `show=true`, chama a API do Bootstrap para exibir o toast automaticamente. Um modal, por definição, deve **prender o foco** enquanto estiver aberto, para que o usuário de teclado não navegue “por trás” sem perceber. O Bootstrap já ajuda nisso, mas você precisa garantir atributos corretos e botões com rótulos. Para o **Modal**, boas práticas incluem: - `aria-labelledby` apontando para o título do modal. - Botão de fechar com `aria-label`. - Evitar conteúdos que não possam ser alcançados pelo teclado. Para o **Toast**, o objetivo é informar sem interromper. Por isso, usamos uma região com `aria-live="polite"` e `role="status"`. Assim, leitores de tela anunciam a mensagem de forma apropriada. E como o toast some sozinho, ele reduz “poluição visual” em relação ao Alert. Por fim, para botões de alternância (como o tema), o atributo `aria-pressed` comunica “ligado/desligado” para tecnologias assistivas. > Exemplo aplicado no Passo a Passo > > Na Etapa 1, o `ThemeToggle` usa `aria-pressed` para indicar quando o modo escuro está ativo. Neste curso, vamos priorizar inputs controlados porque eles deixam o comportamento mais previsível e facilitam validação, formatação e feedback. Um **input controlado** é aquele em que o atributo `value` vem do estado, e o evento `onChange` atualiza esse estado a cada digitação. Assim, o estado vira a **fonte de verdade** do formulário: o que está na tela reflete o que está no estado, e vice-versa. Isso parece “mais trabalho” no começo, mas dá vantagens importantes: - **Validação em tempo real**: você consegue detectar erros enquanto o usuário digita. - **Normalização e formato**: dá para ajustar espaços, capitalização, casas decimais etc. - **Envio confiável**: no submit, você usa o estado (não depende de ler o DOM). - **Reuso**: fica fácil reaproveitar o mesmo formulário para “editar” futuramente. Abaixo está o padrão essencial (estado + value + onChange). Observe que o campo sempre mostra exatamente o valor armazenado no estado. JSX **Código (jsx)** ```jsx const [nome, setNome] = useState(''); setNome(e.target.value)} /> ``` > Exemplo aplicado no Passo a Passo > > No passo a passo (Etapa 2), a página `/admin/itens/novo` mantém estados como `nome`, `preco`, `categoria` e `disponivel`. Cada campo usa `value` e `onChange`, formando um formulário totalmente controlado. Isso é o que permite validar e, ao final, montar o objeto `item` com segurança. ### 2) Validação nativa HTML5 + feedback visual do Bootstrap Formulários precisam impedir dados inválidos (ex.: preço negativo, nome vazio) e orientar o usuário com mensagens claras. Antes de usar bibliotecas externas, dá para ir muito longe combinando: - **Validação nativa do HTML5** (regras no próprio input), e - **Feedback visual do Bootstrap** (classes e mensagens). A validação nativa do HTML5 funciona com atributos como: `required`, `min`, `max`, `step`, `minLength`, `pattern` e tipos como `type="number"`. Esses atributos descrevem regras básicas e o navegador consegue detectar violações (campo vazio, número fora do mínimo, padrão inválido, etc.). O Bootstrap entra para transformar essas falhas em uma experiência melhor. O padrão é: - Aplicar `is-invalid` (ou `is-valid`) no input para mudar o estilo. - Exibir uma mensagem próxima usando `.invalid-feedback` (ou `.valid-feedback`). - Quando for validar “no envio”, marcar o formulário com `was-validated` para ativar os estilos. Além do visual, o importante é separar dois tipos de validação: - **Validação de UI**: mostra ao usuário o que falta e onde. - **Regra de negócio**: decide se pode salvar/enviar (por exemplo, descrição mínima por categoria). Nesta apostila, a regra final para salvar é calculada por um objeto `erros` e um booleano `invalido`. Assim, mesmo que o HTML5 ajude, o React ainda garante consistência. > Exemplo aplicado no Passo a Passo > > Na Etapa 2, o campo **Preço** usa `type="number"`, `min="0"` e `step="0.01"`. No seu sistema, **bebidas** têm `volume`, enquanto **lanches e sobremesas** têm `descricao`. Se você mostrar todos os campos sempre, o usuário fica confuso e aumenta a chance de erro (por exemplo, preencher volume em um lanche). Isso é uma regra de negócio aplicada à UX: **a categoria define quais dados são obrigatórios**. Em React, isso se resolve com renderização condicional: - Se `categoria === 'bebida'` → mostrar e validar `volume`. - Se não for bebida → mostrar e validar `descricao`.
