Capítulo 16 — Projeto Final Integrador + Apresentação
Catálogo Híbrido + CRUD + Carrinho + Testes + Build + Docker

Carga prevista: 2 aulas × 140 min (kickoff, orientação, ensaios) + 1–2 aulas de laboratório (conclusão e ensaio final).

Projeto-base: Sistema da Lanchonete (Admin) consolidando Cap. 1–15.

Stack fixa: Next.js (App Router) + React, Bootstrap 5 + Bootstrap Icons, Jest + RTL, Docker.

Papel único: Administrador.

🎯 Objetivos de Aprendizagem

  • Integrar os pilares do curso (SPA/SSR/SSG/Hidratação, Bootstrap, formulários/validação, APIs, testes, build, release, Docker).
  • Planejar e executar um mini-projeto completo com Git, documentação e apresentação técnica.
  • Medir e justificar escolhas arquiteturais (SSG vs SSR vs CSR).
  • Publicar localmente via Docker (multi-stage), com README e scripts executáveis.

Requisitos do Projeto Voltar: Cap. 15

🧠 Parte Teórica (síntese para fechamento)

1) Arquitetura híbrida em Next.js (decisão por página)

O projeto final existe para provar que você consegue tomar decisões técnicas — não apenas “seguir receita”. A ideia de arquitetura híbrida é escolher a melhor estratégia de renderização para cada página com base em três perguntas: (1) o dado muda com que frequência? (2) é público ou depende do usuário? (3) a página precisa de interatividade intensa?

No escopo da Lanchonete, isso normalmente se traduz assim:

  • SSG + ISR: páginas de vitrine que mudam pouco, mas podem atualizar periodicamente. São excelentes para Home, categorias e detalhes (quando o catálogo é previsível).
  • SSR: páginas administrativas com dados “do agora” (pedidos do dia, estoque do dia). Aqui, a prioridade é refletir o estado atual, mesmo com custo maior de TTFB.
  • CSR/Hidratação: partes interativas no navegador (carrinho, filtros, favoritos, modais/offcanvas). A página pode até ser SSG/SSR, mas a interação acontece em “ilhas” client.

O pulo do gato é que essas estratégias não competem: elas se complementam. Em um app moderno, é comum ter Home SSG, páginas de catálogo SSG/ISR, áreas administrativas SSR e, por cima disso, componentes client para a experiência do usuário.

Além de renderização, a arquitetura também envolve rotas dinâmicas e SEO: generateStaticParams para dizer quais páginas estáticas gerar e generateMetadata para produzir títulos/descrições por item/categoria.

Exemplo aplicado no Passo a Passo

No próprio Cap. 16, você organiza o projeto em milestones: a vitrine (SSG/ISR) e o admin (SSR) aparecem como requisitos mínimos no entregável, enquanto o carrinho é explicitamente client/hidratado. Isso amarra diretamente as decisões de renderização aprendidas nos Caps. 9–12 com as rotas dinâmicas do Cap. 10.

2) Qualidade e confiabilidade (testes como parte da entrega)

Um projeto “funcionando” não é o mesmo que um projeto “confiável”. Qualidade aqui significa: (1) você consegue alterar sem medo e (2) você consegue provar o comportamento esperado. Por isso, os testes entram como requisito mínimo (e não como extra).

Para este curso, pense em testes como camadas:

  • Unitários (componentes): confirmam comportamentos isolados e rápidos (ex.: ProductCard desabilita “Adicionar” quando indisponível).
  • Interface/fluxo (integração leve): validam experiência do usuário cruzando componentes (ex.: adicionar no card → contador do carrinho → abrir offcanvas → alterar quantidade).
  • Mocs: tornam testes determinísticos (fetch 200/400/500, mock de router.refresh, timers de toast).

A regra da RTL continua valendo: teste o que o usuário vê e prefira queries semânticas (getByRole, getByLabelText, findBy*). Isso melhora tanto a robustez do teste quanto a acessibilidade.

Cobertura (ex.: ≥70%) é uma meta pedagógica: ela ajuda a identificar áreas sem testes, mas você deve priorizar fluxos críticos antes de perseguir porcentagem.

Exemplo aplicado no Passo a Passo

No entregável do Cap. 16, a exigência de “mínimo 5 testes” é detalhada: 2 de componentes, 2 de fluxos/páginas e 1 extra. Isso espelha exatamente os Caps. 8 e 13 (Jest/RTL e fluxos), incluindo mocks de fetch e timers.

3) Entrega e operação (build, env e Docker como checklist de “mundo real”)

O último passo de um projeto profissional é conseguir rodar o sistema de forma repetível. Em sala, isso aparece como: build de produção, variáveis de ambiente corretas e execução via Docker. A lógica é simples: se você consegue rodar em produção local, você está muito próximo de publicar de verdade.

O ciclo de entrega recomendado para o projeto final é:

  1. Build: npm run build para gerar artefatos de produção.
  2. Execução: npm start para validar comportamento em modo produção.
  3. Medição: DevTools (TTFB/Response) e Lighthouse (2–3 ações corretivas justificadas).
  4. Container: Docker multi-stage e execução por docker run ou docker compose --profile prod.
  5. Documentação: README com instruções, decisões e evidências (prints).

O ponto central é entender o que vai para o cliente e o que fica no servidor. Variáveis NEXT_PUBLIC_* são públicas; segredos ficam apenas no servidor. No Docker, isso se traduz em passar variáveis no runtime, nunca embutir segredos na imagem.

Exemplo aplicado no Passo a Passo

Na Milestone E do Cap. 16, você fecha o ciclo: roda testes, faz build/start, mede (Home SSG vs Admin SSR) e depois comprova a execução em contêiner. O checklist de entrega exige prints e README, alinhando diretamente com os Caps. 14 e 15.

Regra de ouro (reforço)

Documente o porquê de cada escolha (2–3 frases por decisão importante). Isso vale ouro na apresentação: você mostra consciência técnica e consegue defender a arquitetura com evidências.

🗂️ Entregável — Definição do Projeto Final

Nome sugerido: Lanchonete Admin — SPA+Híbrida

Foco: Operações essenciais do Administrador (papel único), com vitrine híbrida para o público.

Requisitos Funcionais (mínimos)

1) Vitrine (público)

  • Home (SSG + ISR) com destaques.
  • Categorias (SSG + ISR) e Detalhe do item (SSG dinâmico).
  • Cardápio (CSR) com filtros, mostrar/ocultar esgotados, ordenação por destaque/nome.
  • Carrinho (cliente) com Offcanvas + localStorage + total + quantidades.

2) Administração

  • Dashboard (SSR) com pedidos do dia (simulado) + KPIs.
  • CRUD mínimo de Itens via API Routes: listar/criar (já) e editar/excluir (agora).
  • Formulários com validação + feedback Bootstrap.

3) APIs

  • /api/itens (GET/POST) com validação.
  • /api/itens/[id] (PUT/DELETE) para editar/excluir itens extras (mock in-memory).
  • /api/pedidos-dia (GET) para SSR do Admin.

4) Qualidade

  • Mínimo 5 testes:
  • 2 componentes (ex.: ProductCard, CategoryFilters)
  • 2 fluxos/páginas (ex.: /admin/itens com fetch; form novo item)
  • 1 extra (toast/timers, refresh, a11y modal…)
  • Cobertura sugerida: ≥ 70% linhas (ajuste conforme a turma).

5) Entrega

  • Build produção local (next start).
  • Docker multi-stage + execução (docker run / compose --profile prod).
  • README com instruções, decisões (SSG/SSR/CSR), e evidências (prints DevTools/Lighthouse/Postman).

🛠️ Passo a Passo (guia de execução)

Milestone A — Kickoff e planejamento (Aula 1)

  1. Repositório e branches
    • Crie branch: final/cap16.
    • Padrão de commits: feat:, fix:, chore:, test:, docs:, refactor:.
  2. Quadro de tarefas (Kanban simples)
    • To Do → Doing → Review → Done (pode ser GitHub Projects).
    • Quebre tarefas em partes pequenas (≤ 1 aula cada).
  3. Escopo e prioridades
    • Priorize: CRUD + vitrine + carrinho + SSR admin. Extras ficam como opcionais.

Milestone B — CRUD completo de Itens

Complete editar e excluir (base: Cap. 6–7).

1) API: /api/itens/[id]

  • PUT: validar o body (mesma lógica do POST).
  • DELETE: remover do array extras (itens base não podem ser removidos).
PUT /api/itens/{id}
Content-Type: application/json

{
  "nome": "X-Burger Duplo",
  "preco": 24.90,
  "categoria": "lanche",
  "descricao": "Hambúrguer duplo, queijo, molho",
  "disponivel": true,
  "destaque": false
}

→ 200 { "item": { ...atualizado } } | 400 { "erros": {...} } | 404

2) Admin UI

  • /admin/itens: botões Editar e Excluir em cada card.
  • /admin/itens/editar/[id]: formulário pré-preenchido + validações + salvar (PUT).
  • Excluir: confirmar, chamar DELETE e exibir Toast sucesso/erro.

3) Teste

  • Mock de fetch para PUT/DELETE + verificação de mensagens de sucesso/erro.

Milestone C — Vitrine & Carrinho (integração final)

  1. Cardápio
    • Filtros/ordenação/estado vazio (Cap. 3).
    • Ao Adicionar: Toast + atualiza contador global no Header.
  2. Offcanvas do Carrinho
    • UX: “Finalizar (demo)”, limpar carrinho ao confirmar + Toast “Pedido realizado!”.
    • Bônus: cupom (UI) e desconto.
  3. Links
    • Home → categorias SSG; categorias → detalhes SSG; cardápio (CSR) integra carrinho.

Milestone D — SSR do Admin (refino)

  1. /admin (SSR)
    • Confirmar dynamic='force-dynamic' ou fetch(..., { cache: 'no-store' }).
    • RefreshButton funcionando (Cap. 11).
  2. Teste (opcional)
    • Mock de useRouter().refresh() e assert ao clicar.

Milestone E — Qualidade, Build e Docker

  1. Testes
    • Garanta ≥ 5 testes passando (npm test).
    • Se usar cobertura, registre no README.
  2. Build Prod
    • npm run build / npm start.
    • DevTools → Network: compare TTFB Home (SSG) × Admin (SSR).
    • Lighthouse: registrar 2–3 ações corretivas.
  3. Docker
    • docker build -t lanchonete-web:prod .
    • docker run -p 3000:3000 lanchonete-web:prod ou docker compose --profile prod up
    • Print do serviço rodando e endpoint acessível.

🧪 Atividades Práticas (extras / diferenciais)

  1. Busca e paginação no Admin
    • GET /api/itens?q=...&limit=...&offset=... + UI Próxima/Anterior.
  2. Favoritos persistentes
    • Favoritar nos cards + página /favoritos.
    • “Adicionar todos os favoritos ao carrinho”.
  3. Promoções SSG
    • /promocoes (SSG + ISR diário), preço riscado e badge.
  4. Relatórios SSR
    • /admin/relatorios/ultimas-vendas com filtros.
  5. Análise de bundles
    • npm run analyze e justificar 2 melhorias com dynamic()/remover dependências.

📦 Checklist de Entrega

  • Código versionado com histórico de commits legíveis.
  • Mínimos funcionais completos (requisitos acima).
  • Testes executando + print do terminal.
  • Build prod + prints (DevTools: Response/TTFB, Lighthouse).
  • Docker (Dockerfile + comando de execução comprovado).
  • README contendo: Setup, Execução prod, Docker, Decisões (SSG/SSR/CSR), Evidências (prints), Testes/cobertura.

🎤 Roteiro de Apresentação (5–8 min)

  1. Problema e objetivos (30–40s)
  2. Arquitetura (1 min) — mapa das páginas: SSG/SSR/CSR.
  3. Demo (3–4 min) — vitrine, cardápio (filtros + carrinho), admin (CRUD + SSR/refresh).
  4. Qualidade e Release (1–2 min) — testes, build prod, Docker, Lighthouse.
  5. Lições aprendidas e próximos passos (30–40s).
Dica

Tenha um script de demo curto, com dados previsíveis, e deixe as páginas certas já abertas em abas antes de iniciar.

📚 Materiais e Dicas Finais

  • Postman: exporte uma collection com GET/POST/PUT/DELETE de /api/itens e GET /api/pedidos-dia.
  • Acessibilidade: aria-label em botões icônicos, aria-live="polite" em toasts/alerts e foco visível.
  • Erros comuns: hidratação (ler localStorage fora do useEffect), segredos em NEXT_PUBLIC_*, payload sem validação.
