Capítulo 13 — Testes de Interface e Fluxos (RTL avançado)
Fluxo de compra (carrinho), painel SSR (refresh), timers e acessibilidade básica

Carga: 2 aulas × 140 min

Projeto-base: Lanchonete (Cap. 1–12)

Stack fixa: Next.js (App Router) + React, Bootstrap 5, Jest + React Testing Library (RTL) + user-event

Resultados de aprendizagem deste capítulo:

  • Modelar testes de fluxo de usuário (integração leve) cobrindo componentes conectados.
  • Trabalhar com assíncronos (findBy*, waitFor), timers (auto-hide de Toast) e mocks (fetch, next/navigation).
  • Validar acessibilidade mínima (roles, aria, foco) e UX (toasts, offcanvas).
  • Acompanhar cobertura e estabelecer uma meta (p.ex. 70% linhas no app).

🎯 Competências e Habilidades

  • Competências: (1) Elaborar interfaces web; (2) Aplicar práticas de desenvolvimento de sistemas.
  • Habilidades: 2.1 (testes unitários e de interface — ênfase em fluxos), 4 (qualidade, versionamento, automação).

🧠 Parte Teórica

1) Testes de fluxo de usuário (integração leve)

Testes de fluxo (ou integração leve) ficam entre o unitário e o E2E. Eles não tentam validar o sistema inteiro no navegador real (isso seria E2E), mas também não isolam totalmente um único componente. A ideia é juntar componentes que trabalham em conjunto e reproduzir um caminho real do usuário.

Em um app como a Lanchonete, um fluxo típico envolve:

  • O usuário clica em “Adicionar” em um ProductCard.
  • O contador do carrinho aparece/atualiza no Header.
  • O usuário abre o Offcanvas do carrinho e ajusta quantidades.
  • O total muda, o item pode ser removido e o carrinho pode ser limpo.

Esse fluxo atravessa vários componentes e estados: CartProvider (Context), ProductCard (ação), Header (indicador) e CartOffcanvas (UI de revisão). Um teste unitário isolado não capturaria bugs de integração (por exemplo: o botão chama o contexto certo? o Offcanvas mostra o item correto?).

A filosofia segue a RTL: teste o comportamento observável. Ou seja: valide textos, roles, labels e mudanças visíveis. Evite checar classes CSS, ordem de divs ou detalhes internos. Isso deixa o teste resistente a refactors visuais.

Exemplo aplicado no Passo a Passo

Na Etapa 2, o teste CartFlow.test.jsx renderiza CartProvider + CartOffcanvas + ProductCard e simula o fluxo completo: adicionar 2x, abrir carrinho via evento open-cart, conferir “qtd: 2”, ajustar e remover até ficar “Carrinho vazio”.

2) Assíncronos na RTL (findBy, waitFor) e fake timers

Interface real é cheia de comportamento assíncrono: dados chegam depois (fetch), componentes abrem depois (bootstrap JS), toasts desaparecem depois (delay), e assim por diante. A RTL fornece ferramentas específicas para lidar com isso sem tornar os testes instáveis.

Três recursos formam o “kit de sobrevivência” para testes assíncronos:

  • findBy*: retorna uma Promise e espera o elemento aparecer. Use quando o elemento surge depois de alguma ação ou atraso.
  • waitFor: espera uma condição ficar verdadeira. Use para esperar o desaparecimento de um spinner, ou uma mudança que não tem um “elemento novo” fácil de encontrar.
  • Fake timers: com jest.useFakeTimers() você controla o tempo e consegue testar auto-hide e delays. Isso é essencial para toasts que somem sozinhos.

Um erro comum é misturar await e timers sem cuidado. Quando usar fake timers, você precisa avançar o tempo explicitamente (jest.advanceTimersByTime(...)) e, em alguns casos, combinar com act/waitFor se houver re-renderizações após o timer.

Exemplo aplicado no Passo a Passo

Na Etapa 3, ToastAndTimers.test.jsx liga jest.useFakeTimers(), renderiza o toast com show=true e avança o tempo em 2000ms para verificar que onHide foi chamado. Esse é o padrão para validar auto-hide de componentes temporizados sem depender do “tempo real”.

3) Mocks úteis (fetch e next/navigation)

Testes bons são determinísticos: eles devem passar ou falhar sempre pelo mesmo motivo. Dependências externas (rede, data/hora, rotas) são fontes comuns de flakiness. Por isso, mocks são parte do “bom teste”, não um atalho.

Dois mocks aparecem com frequência no Next.js App Router:

  • Mock de fetch: permite simular respostas 200/400/500 sem depender de rede. Você controla ok, status e json() para testar loading/erro/sucesso.
  • Mock de next/navigation: permite simular useRouter() (com refresh, push) e usePathname() para testar menus ativos e botões de refresh.

Regras práticas:

  • Limpe mocks entre testes (jest.clearAllMocks ou jest.resetAllMocks).
  • Mocke apenas o necessário; o objetivo é controlar entradas e observar saídas.
  • Se um teste depende de uma sequência (primeira chamada falha, segunda sucesso), use mockResolvedValueOnce.
Exemplo aplicado no Passo a Passo

Na Etapa 4, o teste do RefreshButton usa jest.mock('next/navigation') para expor um refreshMock e verifica que ele é chamado após o clique. Na Etapa 5, o mock de usePathname força a rota /cardapio e o teste verifica que o link “Cardápio” recebe a classe active.

4) Acessibilidade (a11y) mínima em testes

Testar acessibilidade não precisa ser “tudo ou nada”. Mesmo sem ferramentas avançadas, você consegue aumentar muito a qualidade garantindo que os componentes tenham nomes acessíveis e atributos básicos. A RTL incentiva isso ao usar queries semânticas.

Checkpoints mínimos que valem ouro em projetos educacionais:

  • Botões com nome acessível: getByRole('button', { name: /adicionar/i }) só funciona se o botão tiver texto ou aria-label.
  • Toasts/Alerts com anúncio: verificar role e aria-live (por exemplo, role="status" e aria-live="polite").
  • Modais/Offcanvas: botão de fechar com aria-label, título com aria-labelledby.

Sobre foco: componentes do Bootstrap podem depender de JS para trap de foco. Em Jest/RTL, muitas vezes é mais realista validar atributos e ações (abre/fecha) do que tentar simular toda a gestão de foco. Mesmo assim, você pode usar document.activeElement quando fizer sentido.

Exemplo aplicado no Passo a Passo

Na Etapa 6, o teste ItemModalA11y.test.jsx valida que o modal exibe um heading com o nome do item, mostra o preço e possui botões acessíveis ("Fechar" e "Adicionar") encontráveis por getByRole. Isso garante o mínimo de a11y sem depender de detalhes internos do Bootstrap.

5) Cobertura e critérios (como usar cobertura sem “virar refém”)

Cobertura mede “quantas linhas foram executadas” durante os testes. Ela é útil para encontrar áreas sem testes, mas não garante qualidade sozinha. Um teste ruim pode aumentar cobertura sem validar comportamento importante.

Por isso, a abordagem recomendada neste capítulo é: defina uma meta realista e priorize fluxo. Em projetos educacionais, uma faixa como 60–80% costuma ser saudável. O importante é cobrir:

  • Fluxos críticos (carrinho, formulário, listas com fetch).
  • Cenários de erro/sucesso (fetch 200 vs 400/500, validações).
  • Componentes que concentram regras (Provider, funções de cálculo, etc.).

Outra prática que ajuda muito: excluir arquivos que não fazem sentido na cobertura (ex.: loading.jsx, not-found.jsx), como o capítulo sugere no collectCoverageFrom.

Exemplo aplicado no Passo a Passo

Na Etapa 1, o capítulo mostra como habilitar collectCoverage e definir coverageThreshold (por exemplo, 70%). Na Etapa 7, você roda npm test e verifica se a cobertura atingiu a meta. Se estiver abaixo, você cria mais um teste focado em um fluxo relevante para subir a cobertura com qualidade.

2) Fluxo do Carrinho (adicionar → abrir offcanvas → alterar → total)

__tests__/flow/CartFlow.test.jsx

import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

import CartProvider from '@/components/cart/CartProvider';
import CartOffcanvas from '@/components/cart/CartOffcanvas';
import ProductCard from '@/components/ProductCard';

function Wrapper({ children }) {
  return (
    <CartProvider>
      {children}
      <CartOffcanvas />
    </CartProvider>
  );
}

const coca = {
  id: 'refri-cola-350',
  nome: 'Refrigerante Cola',
  preco: 7,
  volume: '350 ml',
  disponivel: true,
  destaque: true,
  icone: 'bi-cup-straw',
  categoria: 'bebida',
};

test('fluxo: adicionar item, abrir carrinho, ajustar quantidades, remover e limpar', async () => {
  const user = userEvent.setup();

  render(
    <Wrapper>
      <ProductCard item={coca} /> {/* usa contexto (onAdd não passado) */}
    </Wrapper>
  );

  // Adiciona 2x
  const addBtn = screen.getByRole('button', { name: /adicionar/i });
  await user.click(addBtn);
  await user.click(addBtn);

  // Abre o carrinho disparando o evento custom que CartOffcanvas escuta
  window.dispatchEvent(new Event('open-cart'));

  // Verifica item e quantidade
  const itemNome = await screen.findByText(/Refrigerante Cola/i);
  expect(itemNome).toBeInTheDocument();
  expect(screen.getByText(/qtd: 2/i)).toBeInTheDocument();

  // Aumenta e diminui
  const plus = screen.getByRole('button', { name: 'Aumentar' });
  const minus = screen.getByRole('button', { name: 'Diminuir' });
  await user.click(plus); // 3
  await user.click(minus); // 2

  // Remove
  const remove = screen.getByRole('button', { name: 'Remover' });
  await user.click(remove);

  // Vazio
  expect(await screen.findByText(/Carrinho vazio/i)).toBeInTheDocument();
});

O que cobrimos?

  • Integração CartProvider + ProductCard + Offcanvas.
  • Ações reais do usuário (user-event).
  • Estados e textos verificados pela UI.

3) Timers — Toast auto-hide (Cap. 5)

__tests__/ui/ToastAndTimers.test.jsx

import { render, screen } from '@testing-library/react';
import ToastContainer from '@/components/ToastContainer';

beforeEach(() => {
  jest.useFakeTimers();
});

afterEach(() => {
  jest.useRealTimers();
});

test('toast some após ~1800ms', async () => {
  const onHide = jest.fn();

  render(
    <ToastContainer
      show={true}
      message="Adicionado!"
      onHide={onHide}
    />
  );

  // aparece imediatamente
  expect(screen.getByText(/Adicionado!/i)).toBeInTheDocument();

  // avança tempo para o auto-hide
  jest.advanceTimersByTime(2000);

  // onHide chamado
  expect(onHide).toHaveBeenCalled();
});

4) Admin Refresh — mock de router.refresh()

__tests__/admin/RefreshButton.test.jsx

import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

// Mock do next/navigation para expor refresh
const refreshMock = jest.fn();
jest.mock('next/navigation', () => ({
  useRouter: () => ({ refresh: refreshMock }),
}));

import RefreshButton from '@/app/admin/refresh-button';

test('clicar chama router.refresh()', async () => {
  const user = userEvent.setup();
  render(<RefreshButton />);
  await user.click(screen.getByRole('button', { name: /Atualizar/i }));
  expect(refreshMock).toHaveBeenCalled();
});

import { render, screen } from '@testing-library/react';
import ItemModal from '@/components/ItemModal';

const item = {
  id: 'xburger',
  nome: 'X-Burger',
  preco: 18,
  descricao: 'Pão, hambúrguer e queijo.',
  disponivel: true,
  icone: 'bi-egg-fried',

test('modal exibe títulos, preço e botões com roles/labels corretos', () => {
  const onClose = jest.fn();
  const onAdd = jest.fn();

  render(<ItemModal item={item} open={true} onClose={onClose} onAdd={onAdd} />);

  expect(screen.getByRole('heading', { name: /x-burger/i })).toBeInTheDocument();
  expect(screen.getByText(/R\$ 18\.00/i)).toBeInTheDocument();

  const fechar = screen.getByRole('button', { name: /fechar/i });
  const adicionar = screen.getByRole('button', { name: /adicionar/i });
  expect(fechar).toBeInTheDocument();
  expect(adicionar).toBeInTheDocument();
});

🧪 Atividades Práticas (para desenvolver por conta própria)

  1. Formulário (Cap. 6) – fluxos de erro e sucesso
    • Preencha incorreto → veja mensagens invalid-feedback.
    • Corrija → POST mockado 201 → Toast de sucesso.
    • Cenário 400: servidor devolve erros por campo → exibí-los (mapear para os inputs).
  2. /admin/itens (Cap. 7) – GET com paginação
    • Mock de duas páginas e spinner; clique “Próxima”/“Anterior” e verifique a lista.
  3. Cart Offcanvas – acessibilidade de teclado
    • Teste que o botão de fechar recebe foco via userEvent.keyboard('{Escape}') (se aplicável) ou valide que clicar fechar remove conteúdo da tela.

  5. Cobertura dirigida
    • Gere cobertura e aumente +5% criando um teste adicional onde estiver mais baixo (ex.: CategoryFilters com filtros e empty state).
