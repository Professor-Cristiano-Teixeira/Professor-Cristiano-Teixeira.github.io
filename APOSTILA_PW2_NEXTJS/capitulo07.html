🧠 Parte Teórica (explicação do conteúdo)

1) API Routes no Next.js (App Router)

Até aqui, o projeto trabalhou apenas com dados locais (datasets em data/ e, no Cap. 6, localStorage). O próximo passo natural é separar responsabilidades: a interface (front) deve pedir dados e enviar dados para um “servidor”. No curso, a forma mais prática de fazer isso sem infraestrutura externa é usar API Routes do Next.js, chamadas de Route Handlers no App Router.

Uma API Route é um endpoint HTTP dentro do próprio projeto. Em vez de criar um servidor separado, você cria arquivos em app/api e exporta funções com o nome do método HTTP (GET, POST, etc.). Por exemplo, app/api/itens/route.js atende /api/itens. Quando o navegador (ou o Postman) faz uma requisição para esse caminho, o Next executa o handler correspondente.

Isso é valioso didaticamente por três motivos:

  • Front e back no mesmo repositório: você aprende o fluxo completo sem configurar servidores extras.
  • Padroniza o “contrato”: a API define o formato dos dados que o front consome.
  • Simula um banco: mesmo com mock in-memory, você pratica CRUD e validação como em produção.
Exemplo aplicado no Passo a Passo

Na Etapa 1, você cria app/api/itens/route.js e implementa export async function GET() e export async function POST(req). Assim, o endpoint /api/itens passa a responder tanto a listagem quanto a criação de itens, permitindo que o Admin e o formulário conversem com a “camada servidor”.

2) Métodos e códigos HTTP importantes

HTTP é a linguagem padrão da web. Quando você consome ou cria uma API, você trabalha com métodos (que indicam intenção) e códigos de status (que indicam resultado). Mesmo num projeto didático, seguir essa semântica melhora o entendimento e prepara para APIs reais.

Neste capítulo focamos nos dois métodos mais usados em cadastros:

  • GET: “quero ler dados”. Em sucesso, a resposta típica é 200 OK com JSON.
  • POST: “quero criar um recurso”. Em sucesso, a resposta típica é 201 Created com o objeto criado.

Para falhas, a API precisa comunicar onde está o problema:

  • 400 Bad Request: erro do cliente (payload inválido, campos faltando, categoria inválida).
  • 500 Internal Server Error: erro do servidor (exceção não tratada, falha inesperada).

Esse padrão é importante para o front: se o servidor devolve 400, o front deve mostrar erros de validação; se devolve 500, o front deve mostrar mensagem genérica e opção de tentar novamente.

Exemplo aplicado no Passo a Passo

Na Etapa 1, o GET retorna 200 com { items: [...] }. No POST, quando a validação passa, a API retorna 201 com { item: novo }. Quando a validação falha, ela retorna 400 com { message, erros }. Depois, na Etapa 3 e 4, o front usa res.ok para decidir se exibe lista, spinner ou alerta de erro.

3) Validação no servidor (por que e como)

Um princípio fundamental de desenvolvimento web é: nunca confie apenas no cliente. O navegador pode ser manipulado: alguém pode alterar o JavaScript, enviar requisições fora do formulário ou usar o Postman para mandar um payload inválido. Se você validar apenas no front, seu sistema pode “aceitar” dados ruins e quebrar mais tarde.

Por isso, o servidor deve ser a última linha de defesa. A validação no servidor deve:

  • Confirmar tipos e regras (ex.: preço é número e ≥ 0).
  • Confirmar coerência de negócio (ex.: bebidas exigem volume; outras categorias exigem descrição).
  • Retornar erros em formato claro (JSON) para o front exibir corretamente.

Um bom padrão é retornar um objeto erros com chaves por campo. Isso permite que, no futuro, o front “mapeie” erros do servidor para cada input. Mesmo que neste capítulo o front use um toast genérico, a API já está preparada.

Exemplo aplicado no Passo a Passo

Na Etapa 1, a função validarPayload verifica nome, preço e categoria. Depois, valida campos condicionais: volume para bebidas e descricao para os demais. Se houver falhas, a API devolve 400 com { message: 'Erro de validação', erros }. Assim, a API garante que nenhum item inválido seja inserido, independentemente do que o front envie.

4) Consumo com fetch e estados assíncronos (loading, erro, dados)

Quando a UI depende de dados vindos de uma API, ela precisa lidar com o tempo. O fetch é assíncrono: ele não retorna imediatamente. Por isso, um bom componente separa claramente três estados:

  • loading: enquanto espera a resposta, mostre spinner/skeleton e evite ações dependentes do dado.
  • erro: se falhar, mostre um Alert com explicação e um botão “Tentar novamente”.
  • dados: quando carregar, renderize a lista normalmente.

No React, o padrão é disparar o fetch dentro de useEffect na montagem do componente. Ao chegar a resposta, você atualiza o estado com os itens e desliga o loading.

Um detalhe avançado (mas importante) é o AbortController. Ele permite cancelar a requisição se o componente desmontar (por exemplo, o usuário saiu da página) ou se você iniciar um novo fetch. Isso evita o erro clássico “state update on unmounted component” e evita gastar recursos com requisições que não serão mais usadas.

Outro ponto essencial: fetch não lança erro automaticamente para HTTP 400/500. Ele só falha “de verdade” em erros de rede. Por isso, o código checa res.ok e, se for falso, lança um erro manual. Essa prática é crucial para tratar corretamente respostas 400/500.

Exemplo aplicado no Passo a Passo

Na Etapa 3, o Admin cria estados lista, loading e erro. O useEffect inicia um AbortController e chama carregar(ctrl.signal). Enquanto loading é true, aparece um spinner. Se der erro, aparece um Alert com botão “Tentar novamente”. Se carregar, renderiza o grid.

5) Postman no fluxo de desenvolvimento

O Postman é uma ferramenta para testar APIs sem depender do front. Ele te ajuda a entender e depurar o “contrato” da API: URL, método, headers, body e resposta. Isso é útil porque, quando algo dá errado, você consegue descobrir se o problema está: (1) na API ou (2) no front.

O fluxo recomendado (e muito usado no mercado) é:

  1. Definir o formato da resposta (JSON esperado, campos, status).
  2. Implementar a API (mock ou real).
  3. Testar no Postman com casos de sucesso e erro (201 e 400, por exemplo).
  4. Integrar no front com fetch e UI de loading/erro.

Uma dica para estudantes: sempre faça pelo menos um teste de “erro intencional” (ex.: preço negativo) para confirmar se a validação está funcionando e se o retorno 400 está correto.

Exemplo aplicado no Passo a Passo

Na Etapa 2, você usa o Postman para enviar um GET em http://localhost:3000/api/itens e verificar o status 200. Depois envia um POST com JSON e verifica o status 201. Por fim, envia um payload inválido (ex.: preco: -1 ou categoria: "pizza") e confirma o status 400 com mensagens de erro. Só depois disso você integra no front.

1) API Route: app/api/itens/route.js

Crie o arquivo:

JSX

// app/api/itens/route.js
import { NextResponse } from 'next/server';
import { itens as base } from '@/data/itens';

// Mock "banco" em memória (zera quando o servidor reinicia)
let extras = [];

// Helpers
const CATEGORIAS = new Set(['bebida', 'lanche', 'sobremesa']);

function slugify(texto = '') {
return texto
.toLowerCase()
.normalize('NFD').replace(/[\u0300-\u036f]/g, '')
.replace(/[^a-z0-9]+/g, '-')
.replace(/(^-|-$)/g, '');
}

function validarPayload(payload) {
const erros = {};
if (!payload?.nome || payload.nome.trim().length < 3) {
erros.nome = 'Informe ao menos 3 caracteres.';
}
const precoNum = Number(payload?.preco);
if (Number.isNaN(precoNum) || precoNum < 0) {
erros.preco = 'Preço inválido (use número ≥ 0).';
}
if (!CATEGORIAS.has(payload?.categoria)) {
erros.categoria = 'Categoria inválida.';
}
if (payload.categoria === 'bebida') {
if (!payload.volume || !payload.volume.trim()) {
erros.volume = 'Volume é obrigatório para bebidas.';
}
} else {
if (!payload.descricao || payload.descricao.trim().length < 5) {
erros.descricao = 'Descrição é obrigatória (mín. 5 caracteres).';
}
}
return erros;
}

export async function GET() {
// Junta base + extras; em produção isso seria do banco
const data = [...base, ...extras];
return NextResponse.json({ items: data }, { status: 200 });
}

export async function POST(req) {
try {
const body = await req.json();
const erros = validarPayload(body);

if (Object.keys(erros).length > 0) {
return NextResponse.json({ message: 'Erro de validação', erros }, { status: 400 });
}

// Evita duplicidade por nome (didático)
const jaExiste = [...base, ...extras].some(
(it) => it.nome.toLowerCase().trim() === body.nome.toLowerCase().trim()
);
if (jaExiste) {
return NextResponse.json(
{ message: 'Já existe item com este nome.' },
{ status: 400 }
);
}

const id = `${slugify(body.nome)}-${Math.random().toString(36).slice(2, 6)}`;
const novo = {
id,
nome: body.nome.trim(),
preco: Number(Number(body.preco).toFixed(2)),
categoria: body.categoria,
volume: body.categoria === 'bebida' ? String(body.volume).trim() : undefined,
descricao: body.categoria !== 'bebida' ? String(body.descricao).trim() : undefined,
disponivel: Boolean(body.disponivel ?? true),
destaque: Boolean(body.destaque ?? false),
icone:
body.icone ||
(body.categoria === 'bebida'
? 'bi-cup-straw'
: body.categoria === 'lanche'
? 'bi-egg-fried'
: 'bi-ice-cream'),
};

extras.push(novo);
return NextResponse.json({ item: novo }, { status: 201 });
} catch (e) {
console.error(e);
return NextResponse.json({ message: 'Erro no servidor' }, { status: 500 });
}
}

3) Refatorar /admin/itens para consumir a API

Edite app/admin/itens/page.jsx:

JSX

// app/admin/itens/page.jsx
'use client';

import { useEffect, useState } from 'react';
import ProductCard from '@/components/ProductCard';

export default function AdminItens() {
const [lista, setLista] = useState([]);
const [loading, setLoading] = useState(true);
const [erro, setErro] = useState(null);

async function carregar(signal) {
try {
setErro(null);
setLoading(true);
const res = await fetch('/api/itens', { signal });
if (!res.ok) throw new Error(`Erro ${res.status}`);
const data = await res.json();
setLista(data.items || []);
} catch (e) {
if (e.name !== 'AbortError') setErro('Falha ao carregar itens.');
} finally {
setLoading(false);
}
}

useEffect(() => {
const ctrl = new AbortController();
carregar(ctrl.signal);
return () => ctrl.abort();
}, []);

return (
<>
<h1 className="h4 mb-3">Admin — Itens do Cardápio</h1>
<p className="text-muted">Itens base + cadastrados via API (mock in-memory).</p>

{loading && (
<div className="d-flex align-items-center gap-3">
<div className="spinner-border text-primary" role="status" aria-label="Carregando"></div>
<span>Carregando itens...</span>
</div>
)}

{erro && (
<div className="alert alert-danger d-flex justify-content-between align-items-center" role="alert">
<span><i className="bi bi-exclamation-triangle me-2"></i>{erro}</span>
<button className="btn btn-outline-danger btn-sm" onClick={() => carregar()}>
Tentar novamente
</button>
</div>
)}

{!loading && !erro && (
<div className="row g-4">
{lista.map((item) => (
<div className="col-12 col-sm-6 col-lg-4" key={item.id}>
<ProductCard item={item} onAdd={() => {}} />
</div>
))}
</div>
)}
</>
);
}

4) Adaptar /admin/itens/novo para enviar POST à API

// ... imports existentes
// remova addExtra e use fetch

async function salvarApi(payload) {
const res = await fetch('/api/itens', {
method: 'POST',
headers: { 'Content-Type': 'application/json' },
body: JSON.stringify(payload),
});
const data = await res.json();
if (!res.ok) {
const msg = data?.message || 'Falha ao salvar.';
// você pode mapear data.erros para mostrar por campo (extra)
throw new Error(msg);
}
return data.item;
}

function handleSubmit(e) {
e.preventDefault();
setTouched({ nome: true, preco: true, volume: true, descricao: true });
if (invalido) return;

const payload = {
nome: nome.trim(),
preco,
categoria,
volume: isBebida ? volume.trim() : undefined,
descricao: !isBebida ? descricao.trim() : undefined,
disponivel,
destaque,
icone,
};

salvarApi(payload)
.then((itemCriado) => {
setToast({ show: true, message: `${itemCriado.nome} cadastrado com sucesso!` });
limparFormulario();
})
.catch((err) => {
setToast({ show: true, message: err.message || 'Erro ao salvar.' });
});
}

    • Na lista admin, adicione um botão “Excluir” (apenas para itens com id que exista em extras).
