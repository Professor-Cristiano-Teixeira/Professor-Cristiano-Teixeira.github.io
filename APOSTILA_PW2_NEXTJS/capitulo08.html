Projeto-base: Sistema da Lanchonete (Admin) (Cap. 1–7)

Resultados de aprendizagem deste capítulo:

  • Instalar e configurar Jest + React Testing Library (RTL) em um projeto Next.js (App Router).
  • Escrever testes unitários de componentes (ex.: ProductCard, CategoryFilters).

🧠 Parte Teórica (explicação do conteúdo)

1) Pirâmide de testes e escopo

Testes automatizados existem para reduzir bugs e aumentar confiança nas mudanças. Mas nem todo teste tem o mesmo custo. Por isso usamos a ideia da pirâmide de testes: quanto mais “embaixo”, mais testes (rápidos e baratos); quanto mais “em cima”, menos testes (caros e lentos).

A pirâmide típica em aplicações web é:

  • Unitários: verificam partes pequenas e isoladas (ex.: um componente). São rápidos e ajudam a cobrir muitos casos. O foco é comportamento observável do componente.
  • Interface / Integração leve: verificam fluxo de usuário envolvendo mais de um componente. Ex.: página que faz fetch, mostra spinner, trata erro e renderiza lista. São mais lentos que unitários, mas capturam problemas reais de UX.
  • E2E (end-to-end): rodam no navegador real e testam o sistema completo. São os mais caros e frágeis (dependem mais do ambiente). Neste curso, ficam fora do capítulo.

O escopo do capítulo é didático e pragmático: testar o que traz maior retorno. Não faz sentido testar “tudo”, mas faz muito sentido testar: (1) componentes críticos (ProductCard, CategoryFilters) e (2) fluxos críticos (Admin itens via GET; formulário via POST).

Exemplo aplicado no Passo a Passo

No passo a passo, você cria testes unitários para ProductCard e CategoryFilters (Etapas 3 e 4) e depois cria testes de interface para /admin/itens e /admin/itens/novo (Etapas 5 e 6). Isso é a pirâmide na prática: mais unitários, menos testes de fluxo — mas cobrindo o essencial.

2) Filosofia da React Testing Library (RTL)

A React Testing Library foi criada com uma ideia simples: testar a aplicação como o usuário a percebe. Isso muda a forma de escrever testes. Em vez de verificar detalhes internos (como estado, métodos privados, estrutura de divs e classes CSS), a RTL incentiva você a verificar o que aparece na tela e como o usuário interage.

Essa filosofia traz benefícios importantes:

  • Testes menos frágeis: se você reorganizar o layout (refactor visual) sem mudar comportamento, os testes continuam passando.
  • Testes mais significativos: você garante que o usuário realmente consegue encontrar e usar os elementos.
  • Acessibilidade como padrão: se o teste encontra um botão por role e name, isso normalmente significa que o botão está bem rotulado para leitores de tela.

Por isso, preferimos queries como: getByRole, getByLabelText, getByPlaceholderText. O getByTestId existe, mas deve ser o último recurso (quando não há alternativa acessível).

Para simular ações reais, usamos @testing-library/user-event. Ele dispara eventos de forma mais próxima do navegador real (digitação tecla a tecla, clique, tab, etc.), diferente do fireEvent, que é mais “baixo nível”.

Exemplo aplicado no Passo a Passo

Na Etapa 3, ao testar o ProductCard, você usa getByRole('button', { name: /adicionar/i }) para achar o botão do jeito que um usuário/assistente encontra. Na Etapa 6, você usa userEvent.type para digitar nos campos do formulário e simular a interação real.

3) Jest em poucas palavras (o que você precisa dominar)

O Jest é o “motor” de testes. Ele executa arquivos .test.js/.test.jsx, organiza suites e mostra relatórios. Para este capítulo, você precisa dominar quatro coisas:

  • Estrutura: describe (agrupa) e test/it (caso de teste).
  • Asserções: expect(...) com matchers (por exemplo, toEqual, toBe). Com @testing-library/jest-dom, você ganha matchers voltados para DOM, como toBeInTheDocument, toHaveTextContent, toBeDisabled.
  • Mocos e spies: jest.fn() cria uma função mock para verificar se foi chamada. Você usa isso para callbacks como onAdd e também para mockar fetch.
  • Assíncrono e timers: testes que dependem de fetch/timers precisam de await. Você usa findBy* (que espera) ou waitFor (para esperar uma condição). Em casos de tempo (toasts), pode usar jest.useFakeTimers().

Um ponto importante de higiene: se você mocka algo (como global.fetch), precisa limpar para não “vazar” para outro teste. Por isso usamos afterEach com jest.clearAllMocks() ou jest.resetAllMocks().

Exemplo aplicado no Passo a Passo

Na Etapa 2, você cria jest.setup.js com afterEach(() => jest.clearAllMocks()). Na Etapa 5, você define global.fetch = jest.fn() e controla diferentes respostas (sucesso/erro) com mockResolvedValueOnce. Isso torna os testes determinísticos e evita dependência de rede.

4) Dicas de acessibilidade nos testes (e por que isso melhora seu código)

Quando você escreve testes usando queries semânticas, você está validando acessibilidade de forma indireta. Se um teste não consegue achar um botão por getByRole com um nome, isso pode indicar que o botão não está bem rotulado (por exemplo, um ícone sem texto e sem aria-label).

As queries mais importantes para este curso são:

  • getByRole: ideal para botões, links, alerts e inputs. Ex.: getByRole('button', { name: /salvar/i }).
  • getByLabelText: ideal para formulários, porque força você a ter label bem associado ao input.
  • findBy*: use quando algo aparece depois de uma ação assíncrona (fetch, timers, render condicional).

Além disso, prefira asserts que refletem comportamento: toBeDisabled() quando indisponível; toHaveTextContent() quando uma mensagem aparece; toHaveValue() quando o formulário limpa.

Exemplo aplicado no Passo a Passo

Na Etapa 3, você verifica que o botão "Adicionar" fica desabilitado com toBeDisabled(). Na Etapa 6, você encontra campos com getByLabelText(/nome \*/i) e confirma que, após o POST, o campo foi limpo com toHaveValue(''). Isso garante UX + acessibilidade e evita testes frágeis.

1) Instalação das dependências de teste

npm i -D jest @testing-library/react @testing-library/jest-dom @testing-library/user-event jest-environment-jsdom identity-obj-proxy

Por quê?

  • jest: runner e assertions.
  • @testing-library/react + user-event: render e interação.
  • @testing-library/jest-dom: matchers extras (ex.: toBeInTheDocument).
  • jest-environment-jsdom: ambiente DOM.
  • identity-obj-proxy: mock simples para imports de CSS.

3) Teste Unitário — ProductCard

Arquivo: __tests__/ProductCard.test.jsx

import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import ProductCard from '@/components/ProductCard';

const baseItem = {
  id: 'refri-cola-350',
  nome: 'Refrigerante Cola',
  preco: 7,
  volume: '350 ml',
  disponivel: true,
  destaque: true,
  icone: 'bi-cup-straw',
  categoria: 'bebida',
};

test('renderiza informações básicas e badges', () => {
  render(<ProductCard item={baseItem} onAdd={() => {}} />);
  expect(screen.getByText('Refrigerante Cola')).toBeInTheDocument();
  expect(screen.getByText('350 ml')).toBeInTheDocument();
  expect(screen.getByText('R$ 7.00')).toBeInTheDocument();
  // badge de destaque e categoria
  expect(screen.getByText(/destaque/i)).toBeInTheDocument();
  expect(screen.getByText(/bebida/i)).toBeInTheDocument();
});

test('desabilita botão "Adicionar" quando indisponível', () => {
  const indisponivel = { ...baseItem, disponivel: false };
  render(<ProductCard item={indisponivel} onAdd={() => {}} />);
  const btn = screen.getByRole('button', { name: /adicionar/i });
  expect(btn).toBeDisabled();
  expect(screen.getByText(/Indisponível/i)).toBeInTheDocument();
});

test('aciona callback onAdd ao clicar em "Adicionar"', async () => {
  const user = userEvent.setup();
  const onAdd = jest.fn();
  render(<ProductCard item={baseItem} onAdd={onAdd} />);
  const btn = screen.getByRole('button', { name: /adicionar/i });
  await user.click(btn);
  expect(onAdd).toHaveBeenCalledTimes(1);
  expect(onAdd).toHaveBeenCalledWith(expect.objectContaining({ id: 'refri-cola-350' }));
});

5) Teste de Interface — /admin/itens (GET com loading/erro/dados)

Arquivo: __tests__/AdminItensPage.test.jsx

import { render, screen, waitFor } from '@testing-library/react';
import AdminItens from '@/app/admin/itens/page';

beforeEach(() => {
  global.fetch = jest.fn();
});

afterEach(() => {
  jest.resetAllMocks();
});

test('mostra spinner de carregamento e renderiza lista após sucesso', async () => {
  fetch.mockResolvedValueOnce({
    ok: true,
    json: async () => ({ items: [
      { id: 'xburger', nome: 'X-Burger', preco: 18, categoria: 'lanche', descricao: '...' , disponivel: true, destaque: true, icone: 'bi-egg-fried' },
    ] }),
  });

  render(<AdminItens />);

  // loading
  expect(screen.getByRole('status', { name: /carregando/i })).toBeInTheDocument();

  // Após carregar
  expect(await screen.findByText(/X-Burger/i)).toBeInTheDocument();
  // spinner some
  await waitFor(() => {
    expect(screen.queryByRole('status', { name: /carregando/i })).not.toBeInTheDocument();
  });
});

test('mostra alerta de erro e permite tentar novamente', async () => {
  // primeira tentativa falha
  fetch.mockResolvedValueOnce({ ok: false, status: 500 });
  render(<AdminItens />);
  expect(await screen.findByRole('alert')).toHaveTextContent(/falha ao carregar/i);

  // segunda tentativa: sucesso
  fetch.mockResolvedValueOnce({
    ok: true,
    json: async () => ({ items: [
      { id: 'agua-500', nome: 'Água Mineral', preco: 4, categoria: 'bebida', volume: '500 ml', disponivel: true, destaque: false, icone: 'bi-droplet' },
    ] }),
  });

  await screen.findByRole('button', { name: /tentar novamente/i }).then(btn => btn.click());
  expect(await screen.findByText(/Água Mineral/i)).toBeInTheDocument();
});

6) Teste de Interface — /admin/itens/novo (formulário e POST)

Arquivo: __tests__/AdminNovoItemPage.test.jsx

import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import NovoItemPage from '@/app/admin/itens/novo/page';

beforeEach(() => {
  global.fetch = jest.fn();
});

afterEach(() => {
  jest.resetAllMocks();
});

async function preencherBebida(user) {
  // Categoria já inicia em "Bebida"
  await user.type(screen.getByLabelText(/nome \*/i), 'Limonada');
  await user.type(screen.getByLabelText(/preço \*/i), '8.5');
  await user.type(screen.getByLabelText(/volume \*/i), '300 ml');
}

test('valida campos obrigatórios antes de enviar', async () => {
  const user = userEvent.setup();
  render(<NovoItemPage />);

  // Enviar vazio
  await user.click(screen.getByRole('button', { name: /salvar/i }));

  expect(await screen.findByText(/Informe ao menos 3 caracteres/i)).toBeInTheDocument();
  expect(screen.getByText(/Informe um preço/i)).toBeInTheDocument();
  expect(screen.getByText(/Informe o volume/i)).toBeInTheDocument();
});

test('envia POST com sucesso e limpa formulário', async () => {
  const user = userEvent.setup();
  fetch.mockResolvedValueOnce({
    ok: true,
    json: async () => ({ item: { id: 'limonada-1234', nome: 'Limonada' } }),
  });

  render(<NovoItemPage />);
  await preencherBebida(user);
  await user.click(screen.getByRole('button', { name: /salvar/i }));

  // Toast de sucesso (texto configurado no componente)
  expect(await screen.findByText(/cadastrado com sucesso/i)).toBeInTheDocument();

  // Nome limpou
  expect(screen.getByLabelText(/nome \*/i)).toHaveValue('');
});

test('exibe erro do servidor (400/500) no toast', async () => {
  const user = userEvent.setup();
  fetch.mockResolvedValueOnce({
    ok: false,
    json: async () => ({ message: 'Já existe item com este nome.' }),
  });

  render(<NovoItemPage />);
  await preencherBebida(user);
  await user.click(screen.getByRole('button', { name: /salvar/i }));

  expect(await screen.findByText(/já existe item/i)).toBeInTheDocument();
});
