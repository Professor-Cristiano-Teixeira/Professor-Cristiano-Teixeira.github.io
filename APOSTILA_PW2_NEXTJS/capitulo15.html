Capítulo 15 — Conteinerização com Docker
Dockerfile multi stage, .dockerignore, docker run, docker compose, perfis dev/prod e boas práticas

Carga: 2 aulas × 140 min

Projeto-base: Lanchonete (Cap. 1–14)

Stack fixa: Next.js (App Router) + React, Bootstrap 5 + Bootstrap Icons, Git, Docker

Resultados de aprendizagem deste capítulo:

  • Entender imagens e contêineres, camadas (layers) e reuso de cache.
  • Produzir um Dockerfile multi stage para build e runtime otimizados.
  • Criar .dockerignore e executar em produção local com docker run.
  • Criar docker-compose.yml com perfis dev (hot reload) e prod (imagem final).
  • Passar variáveis de ambiente, healthcheck e boas práticas (usuário não root, tamanho de imagem, logs).

  • Competências: (2) Aplicar práticas de desenvolvimento de sistemas.
  • Habilidades: 4 (builds, releases, conteinerização e versionamento).

📆 Plano de Aula

Aula 1 (140 min) — Teoria + Dockerfile multi stage + Produção local

Teoria (35–45 min):

  • Conceitos: imagem, contêiner, layer, cache, multi stage, ENTRYPOINT/CMD, EXPOSE, bind mount x cópia, usuário não root.
  • Dev vs Prod: por que separar estágio de build do estágio de runtime.

Prática (85–95 min):

  • Criar .dockerignore e Dockerfile multi stage.
  • Ajustar next.config.mjs para output: 'standalone' (imagem menor).
  • docker build e docker run mapeando a porta 3000.

Aula 2 (140 min) — Compose (dev/prod), variáveis, healthcheck e otimizações

Teoria (20–30 min):

  • docker compose (múltiplos serviços), perfis, volumes, variáveis (.env) e healthcheck.
  • Dicas: imagens slim, não usar root, cache de dependências, logs e limpeza.

Prática (100–110 min):

  • Criar docker-compose.yml com perfis dev (hot reload) e prod (imagem multi stage).
  • Passar variáveis com env_file/environment.
  • Add healthcheck HTTP.

Entrega rápida (10 min): Print do container em execução (prod) e do serviço em dev com auto reload.

🧠 Parte Teórica (explicação do conteúdo)

1) Imagem, contêiner e layers

  • Imagem: “molde” imutável com SO mínimo + dependências + app.
  • Contêiner: instância executando a imagem (isolada).
  • Layers: cada instrução (FROM, RUN, COPY…) cria camadas cacheáveis. Alterar uma camada invalida as seguintes.

2) Multi stage build

  • Um estágio para build (com dependências dev) e outro menor para runtime.
  • Benefícios: imagem final menor, sem ferramentas de desenvolvimento.

3) .dockerignore

  • Evita copiar lixo (.git, node_modules, cache) para o contexto de build → builds mais rápidos e imagens menores.

4) Dev x Prod em containers

  • Dev: bind mount (mapear pasta) + npm run dev + polling em alguns ambientes.
  • Prod: imagem fechada, sem bind mounts, next start (ou standalone com node server.js).

5) Boas práticas de runtime

  • Usuário não root (mais seguro).
  • Variáveis de ambiente (PORT, NODE_ENV, NEXT_PUBLIC_*).
  • Healthcheck (verifica se a app responde).
  • Limitar recursos (CPU/Mem) em produção (conceito).

🛠️ Passo a Passo — Dockerfile, Produção local e Compose

Pré-requisitos: Projeto Next.js funcional (Cap. 14).

Objetivo: Subir a app da lanchonete em contêiner (prod e dev), com imagem otimizada.

0) Ajuste para standalone (imagem menor)

Edite next.config.mjs (se ainda não tiver):

/** @type {import('next').NextConfig} */
const nextConfig = {
  output: 'standalone', // habilita bundle de runtime copiável
  reactStrictMode: true,
  images: { formats: ['image/avif', 'image/webp'] }
};

export default nextConfig;

2) Dockerfile (multi stage, Node 20 bookworm slim)

Usamos node:20-bookworm-slim por compatibilidade com binários e para evitar dores com sharp em alpine.

# -------- Stage 1: Build --------
FROM node:20-bookworm-slim AS builder

WORKDIR /app

# Copie antes para cache
COPY package*.json ./

# Instala dependências
RUN npm ci

# Copia o restante do código
COPY . .

# Build de produção (gera .next/standalone + .next/static)
RUN npm run build

# -------- Stage 2: Runtime --------
FROM node:20-bookworm-slim AS runner

WORKDIR /app
ENV NODE_ENV=production
ENV PORT=3000

# Copia o standalone e estáticos do build
COPY --from=builder /app/.next/standalone ./
COPY --from=builder /app/.next/static ./.next/static
COPY --from=builder /app/public ./public

EXPOSE 3000

# Usuário não-root
USER node

# Start do servidor standalone
CMD ["node", "server.js"]

Comandos:

# construir a imagem
docker build -t lanchonete-web:prod .

# executar (mapeando porta 3000 do host)
docker run --name lanchonete -p 3000:3000 -e PORT=3000 lanchonete-web:prod

# acessar: http://localhost:3000

# parar/remover
docker stop lanchonete && docker rm lanchonete

3) docker-compose.yml (perfis dev e prod)

Crie docker-compose.yml na raiz:

services:
  web:
    # Perfil de PRODUÇÃO
    profiles: ["prod"]
    image: lanchonete-web:prod
    build:
      context: .
      dockerfile: Dockerfile
    ports:
      - "3000:3000"
    environment:
      NODE_ENV: "production"
      PORT: "3000"
      # NEXT_PUBLIC_APP_NAME: "Lanchonete Admin"
    healthcheck:
      test: ["CMD-SHELL", "wget -qO- http://localhost:3000/ || exit 1"]
      interval: 15s
      timeout: 5s
      retries: 5

  web-dev:
    # Perfil de DESENVOLVIMENTO (hot reload)
    profiles: ["dev"]
    image: node:20-bookworm-slim
    working_dir: /app
    command: sh -c "npm install && CHOKIDAR_USEPOLLING=true WATCHPACK_POLLING=true npm run dev"
    ports:
      - "3000:3000"
    volumes:
      - .:/app
      - /app/node_modules
    environment:
      NODE_ENV: "development"
      PORT: "3000"
      NEXT_PUBLIC_APP_NAME: "Lanchonete Admin (Dev)"

Como usar:

# Produção (build + up)
docker compose --profile prod up --build

# Desenvolvimento (hot reload)
docker compose --profile dev up
Notas dev (Windows/macOS)

Os flags *POLLING=true ajudam o Next a detectar alterações de arquivos em bind mounts.

4) Variáveis de ambiente com compose

Crie um .env na raiz (para o compose), por exemplo:

NEXT_PUBLIC_APP_NAME=Lanchonete Admin
PORT=3000

Então, no docker-compose.yml, você pode usar:

environment:
  NODE_ENV: "production"
  PORT: "${PORT}"
  NEXT_PUBLIC_APP_NAME: "${NEXT_PUBLIC_APP_NAME}"

Cuidado: nunca coloque segredos em NEXT_PUBLIC_* (vai para o cliente). Segredos reais → use variáveis só no servidor ou secrets.

5) Healthcheck e logs

  • Healthcheck (já adicionado) tenta acessar /.
  • Logs: docker logs -f lanchonete (ou docker compose logs -f).
  • Limpeza: docker image prune -f e docker builder prune (com cautela).

6) Dicas de otimização

  • Cache de dependências: mantenha COPY package*.json antes de COPY . ..
  • Imagem base: bookworm slim (equilíbrio de compatibilidade e tamanho).
  • Remover devDeps: npm ci --omit=dev no runner só se não usar standalone (standalone já leva o mínimo).
  • Reduzir contexto: use .dockerignore para evitar arquivos grandes no root.

🧪 Atividades Práticas (para desenvolver por conta própria)

  1. Multi stage “completo” (devDeps omitidas no runner)
    • No runner, rode npm ci --omit=dev apenas se não usar standalone.
    • Compare o tamanho da imagem com docker image ls.
  2. Porta alternativa + reverse proxy
    • Rode com PORT=8080 e mapeie -p 8080:8080.
    • Documente no README como integrar com um proxy (conceitual).
  3. Perfil “preview”
    • Adicione web-preview com NEXT_PUBLIC_APP_NAME="Lanchonete Preview" e tag de imagem :preview.
    • Explique quando preview é útil (homologação/aprovação).
  4. Imagem “alpine” (desafio)
    • Tente portar para node:20-alpine e documente problemas (ex.: sharp) e correções.
  5. Liveness vs Readiness
    • Troque o healthcheck para checar /cardapio com retries.
    • Explique liveness (processo vivo) vs readiness (pronto para tráfego).
