Ao final deste capítulo, o(a) aluno(a) será capaz de:

3) Conteúdo teórico

3.1. Autenticação x Autorização

Em sistemas web, é comum confundir autenticação com autorização, mas elas respondem perguntas diferentes. Autenticação responde “Quem é você?” — ou seja, confirma a identidade do usuário (por login e senha, por exemplo). Já autorização responde “O que você pode fazer?” — define se aquele usuário tem permissão para acessar uma rota, executar uma ação ou visualizar um recurso. Um usuário pode estar autenticado (logado) e ainda assim não ter permissão para certas ações.

No contexto da Lanchonete, a diferença fica clara: um atendente precisa estar logado para registrar pedidos, mas não deve poder alterar categorias e produtos; já o gerente pode administrar o catálogo. Portanto, primeiro garantimos autenticação (login/registro/logout funcionando) e, depois, aplicamos autorização (regras por perfil/role). Separar esses conceitos ajuda a manter o projeto organizado e evita soluções inseguras, como “esconder o link do menu” e achar que isso protege a rota.

No Laravel, autenticação pode ser implementada rapidamente com scaffolding (Breeze), que fornece rotas, controllers e views. Para autorização, existem várias opções: middlewares, gates e policies. Como este é um capítulo didático, vamos começar com uma autorização simples baseada em uma coluna role no usuário (gerente/atendente). Mais adiante, você pode evoluir para Policies e Gates quando precisar de regras mais finas (por exemplo, “o usuário pode editar apenas itens que ele criou”).

Boas práticas ao pensar em autenticação/autorização:

  • Autenticação ≠ autorização — Login não significa permissão total.
  • Não confie no front-end — Esconder links não substitui proteção de rota.
  • Autorize no servidor — Regras devem estar em middleware/gates/policies.
Exemplo aplicado no passo a passo (Cap. 5)
Na seção 4.1 e 4.2, você instala o Breeze e passa a ter login/registro funcionando (autenticação). Na seção 4.3, você protege rotas do catálogo com middleware auth (ainda é autenticação: só entra logado). Depois, na seção 4.7 e 4.8, você usa role (gerente/atendente) para exibir menu condicional e restringir acesso às categorias (autorização).

3.2. Sessão e middlewares

HTTP é stateless: cada requisição é independente. Então, para “lembrar” que um usuário está logado entre uma página e outra, precisamos de um mecanismo de estado. Esse mecanismo, na maioria dos sistemas tradicionais, é a sessão. A sessão funciona assim: o servidor guarda dados (por exemplo, o id do usuário autenticado) e o navegador guarda apenas um identificador da sessão em um cookie. Em cada nova requisição, o navegador envia o cookie e o servidor consegue recuperar a sessão.

No Laravel, quando você faz login, o framework grava na sessão as informações necessárias para identificar o usuário. A partir daí, funções como auth()->user() passam a funcionar. Quando você faz logout, o Laravel invalida a sessão, removendo esse vínculo. Por isso, sessão é a base do “usuário continuar logado”. Em projetos com API, esse papel pode ser feito por tokens; mas no modelo web com Blade, sessão é o padrão.

Middleware é um “filtro” que roda antes (e às vezes depois) da rota. Ele pode bloquear a requisição, redirecionar, ou adicionar alguma lógica transversal (logging, limitação de requisições, etc.). O middleware auth é o mais importante aqui: ele verifica se o usuário está autenticado; se não estiver, ele redireciona para /login. Esse é o mecanismo que realmente protege a rota. Sem middleware, qualquer pessoa poderia acessar /categorias digitando a URL.

Exemplos de usos típicos de middleware no Laravel:

  • auth — Exigir login para acessar determinadas rotas.
  • guest — Exigir que o usuário NÃO esteja logado (ex.: páginas de login/registro).
  • throttle — Limitar número de requisições (útil contra abuso).
  • custom role — Bloquear acesso com base em perfil, como gerente/atendente.
Exemplo aplicado no passo a passo (Cap. 5)
Na seção 4.3, você coloca Route::resource(...) dentro de Route::middleware(["auth"])...group(...). Isso faz com que /categorias e /produtos só possam ser acessados após login. Depois, na seção 4.7, você usa @auth e auth()->user() na navbar: isso só funciona porque a sessão mantém o usuário autenticado entre as requisições.

3.3. Laravel Breeze (scaffolding)

Scaffolding é quando um framework gera “estrutura inicial” pronta para uma funcionalidade comum. No caso do Laravel Breeze, ele gera rapidamente autenticação básica: páginas de registro, login, esqueci minha senha (dependendo da opção), rotas, controllers e views. Para projetos didáticos, o Breeze economiza muito tempo, porque você não precisa implementar do zero uma parte que é comum a praticamente todo sistema.

O Breeze existe em variações (Blade, React, Vue). Nesta apostila, usamos Breeze com Blade, para manter o projeto coerente com os capítulos anteriores. Mesmo assim, o Breeze usa Vite para gerenciar assets front-end (CSS/JS). Por isso, normalmente você precisa rodar npm install e npm run dev. Em ambiente de laboratório, isso pode ser um desafio, então é importante entender que: (1) npm install baixa dependências; (2) npm run dev compila e serve assets no modo desenvolvimento; (3) npm run build gera arquivos finais para produção.

Após instalar o Breeze, novas rotas surgem (como /login, /register e /dashboard). Algumas já vêm protegidas por middleware auth. Além disso, o Breeze adiciona migrations relacionadas ao usuário e, dependendo da versão do Laravel, pode incluir alterações para sessões, jobs ou tokens. Por isso, é recomendado rodar php artisan migrate após a instalação, garantindo que o banco fique alinhado com o novo conjunto de tabelas/colunas necessárias.

Pontos de atenção ao usar Breeze:

  • Rodar migrations — Depois de instalar, execute php artisan migrate.
  • Rodar Vite — Em dev, use npm run dev para ter CSS/JS carregando corretamente.
  • Manter layout consistente — Você pode integrar links do seu navbar com as rotas do Breeze.
Exemplo aplicado no passo a passo (Cap. 5)
Na seção 4.1, você executa composer require laravel/breeze --dev e depois php artisan breeze:install blade. Em seguida, roda npm install e npm run dev para compilar os assets e php artisan migrate para atualizar o banco. Na seção 4.2, você testa /register, /login e /dashboard. Isso confirma que o scaffolding de autenticação está ativo e funcional.

3.4. Perfis (roles) e controle de acesso (visão didática)

Depois que o login funciona, surge a necessidade de controlar o que cada tipo de usuário pode acessar. Uma forma simples de começar é adicionar um campo role (perfil) na tabela users. Esse campo pode ter valores como “gerente” e “atendente”. Então, você usa esse valor para decidir: (1) quais links aparecem no menu, e (2) quais rotas realmente podem ser acessadas.

É importante destacar que “menu condicional” melhora a experiência (UX), mas não é segurança por si só. Um atendente pode digitar a URL /categorias manualmente. Por isso, o controle real deve acontecer no servidor, normalmente via middleware. Um middleware de role recebe o papel exigido (ex.: gerente) e bloqueia com 403 se o usuário não tiver permissão. Essa abordagem é didática e funciona bem para sistemas pequenos. Em sistemas maiores, você evolui para Policies/Gates, que permitem regras mais granulares.

Mesmo nesse modelo simples, boas práticas ainda valem: use valores controlados (whitelist) para roles, defina um default seguro (atendente) e evite permitir que usuários comuns alterem seu próprio role. Em um sistema real, a troca de role seria uma ação administrativa protegida. Aqui, usamos tinker para fins de aprendizado.

Regras práticas para trabalhar com roles:

  • Default seguro — Usuários novos devem ter role com menos privilégios (atendente).
  • Controle no servidor — Bloquear rota com middleware e retornar 403 se não autorizado.
  • Menu é UX — Menu condicional ajuda, mas não substitui proteção de rota.
Exemplo aplicado no passo a passo (Cap. 5)
Na seção 4.4, você cria a coluna role com default "atendente". Na seção 4.6, você promove um usuário para "gerente" usando tinker. Na seção 4.7, a navbar usa @auth e um if (auth()->user()->role === "gerente") para mostrar links de administração. Na seção 4.8, você aplica uma restrição simples para permitir acesso a /categorias somente quando role for gerente (retornando 403 caso contrário).

4) Passo a passo guiado (Projeto Lanchonete)

Meta do capítulo: instalar o Breeze, proteger rotas, criar perfis simples e exibir menu condicional.

4.1. Instalar o Laravel Breeze (Blade)

No terminal, dentro do projeto:
Shell
composer require laravel/breeze --dev
php artisan breeze:install blade

npm install
npm run dev

php artisan migrate
Observação
Se o professor preferir, pode rodar npm run build uma vez e depois apenas php artisan serve. Em ambiente de laboratório, o mais comum é usar npm run dev durante a aula.

4.2. Testar login/registro e rotas do Breeze

Suba o servidor:
Shell
php artisan serve
Acesse:
· /register para criar usuário
· /login para entrar
· /dashboard (rota protegida criada pelo Breeze)

4.3. Proteger rotas do catálogo com middleware auth

Em routes/web.php, agrupe rotas que só podem ser acessadas com login:
PHP
Route::middleware(['auth'])->group(function () {
    Route::resource('categorias', CategoriaController::class);
    // Route::resource('produtos', ProdutoController::class);
});
(Se você já tem ProdutoController, inclua também.)

4.4. Criar coluna role (perfil) na tabela users

Crie uma migration para adicionar a coluna:
Shell
php artisan make:migration add_role_to_users_table --table=users
Edite a migration gerada em database/migrations/xxxx_add_role_to_users_table.php:
PHP
public function up(): void
{
    Schema::table('users', function (Blueprint $table) {
        $table->string('role')->default('atendente')->after('email');
    });
}

public function down(): void
{
    Schema::table('users', function (Blueprint $table) {
        $table->dropColumn('role');
    });
}
Rode a migration:
Shell
php artisan migrate

4.5. Atualizar o Model User para permitir leitura/edição do role

Edite app/Models/User.php e inclua o campo no $fillable (se existir):
PHP
protected $fillable = [
    'name',
    'email',
    'password',
    'role',
];

4.6. Definir um usuário gerente (seeder rápido)

Opção simples: após registrar, use o tinker para promover o seu usuário para gerente:
Shell
php artisan tinker

>>> $u = App\Models\User::where('email','seuemail@exemplo.com')->first();
>>> $u->role = 'gerente';
>>> $u->save();
>>> exit

4.7. Menu condicional por perfil (Gerente/Atendente)

Edite sua navbar (resources/views/partials/navbar.blade.php) e mostre links de administração apenas para Gerente. Exemplo de bloco condicional:
PHP
@auth
    <li class="nav-item">
        <a class="nav-link" href="{{ route('categorias.index') }}">Categorias</a>
    </li>

    @if (auth()->user()->role === 'gerente')
        <li class="nav-item">
            <a class="nav-link" href="{{ route('produtos.index') }}">Produtos</a>
        </li>
    @endif

    <li class="nav-item">
        <a class="nav-link" href="/dashboard">Dashboard</a>
    </li>
@endauth

@guest
    <li class="nav-item"><a class="nav-link" href="/login">Entrar</a></li>
    <li class="nav-item"><a class="nav-link" href="/register">Criar conta</a></li>
@endguest

4.8. Restringir acesso a Categorias para Gerente (simples)

Para um controle didático e rápido, use um middleware inline no arquivo de rotas. No routes/web.php:
PHP
Route::middleware(['auth'])->group(function () {

    Route::get('/categorias', [CategoriaController::class, 'index'])
        ->middleware(function ($request, $next) {
            abort_unless(auth()->user()->role === 'gerente', 403);
            return $next($request);
        })
        ->name('categorias.index');

    // DICA: para simplificar, aplique a mesma ideia nas demais rotas de categorias,
    // ou crie um middleware "role" (atividade correlata).
});
Nota didática
O ideal é criar um middleware próprio (ex.: role:gerente) ou usar Policies/Gates (Cap. 14). Aqui usamos uma abordagem simples para fixar o conceito.
