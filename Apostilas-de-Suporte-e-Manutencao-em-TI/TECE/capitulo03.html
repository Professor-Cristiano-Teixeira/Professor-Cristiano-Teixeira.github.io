Capítulo 03 — Modelos de Serviço em Nuvem: IaaS, PaaS e SaaS

Carga: 4h

Projeto-base: Mini-projeto 1 — VM + bucket + segurança básica (continuação)

Stack fixa: Conta gratuita (AWS/Azure/GCP), VS Code, Terminal/PowerShell, Navegador

Resultados de aprendizagem deste capítulo:

  • Diferenciar IaaS, PaaS e SaaS com base em definições, responsabilidades e casos de uso.
  • Aplicar critérios práticos para escolher o modelo adequado a cenários de suporte de TI.
  • Avaliar implicações operacionais (custos, escala, segurança, manutenção) de cada modelo.
  • Classificar soluções reais no modelo correto e justificar tecnicamente.

Competências e Habilidades

  • Compreender modelos de serviço de nuvem e responsabilidade compartilhada.
  • Analisar requisitos de negócio para tomada de decisão técnica.
  • Comunicar justificativas técnicas de forma clara e objetiva.
  • Aderir a boas práticas de segurança e custo/benefício ao selecionar serviços.

Parte Teórica (explicação do conteúdo)

1) O que são Modelos de Serviço em Nuvem?

Modelos de serviço em nuvem definem “de quem é a responsabilidade” por cada parte da pilha tecnológica. Em linhas gerais, IaaS (Infrastructure as a Service) oferece recursos de infraestrutura (compute, rede, armazenamento) sob demanda; PaaS (Platform as a Service) entrega uma plataforma pronta para desenvolver e executar aplicações; SaaS (Software as a Service) disponibiliza o software completo, acessado via web, com gerenciamento quase total pelo provedor.

Entender essa divisão evita erros comuns, como assumir que segurança do sistema operacional é gerenciada no SaaS (em geral não é responsabilidade do cliente) ou que backups de banco de dados em PaaS são sempre automáticos (varia por serviço e configuração).

Onde vou aplicar isso: você usará essas definições para classificar 10 soluções reais e justificar escolhas na matriz de decisão.

2) IaaS — Infraestrutura como Serviço

No IaaS, você provisiona componentes básicos: máquinas virtuais, discos, redes virtuais, balanceadores. O provedor cuida do data center, hardware físico e virtualização; o cliente configura sistema operacional, patches, middleware e a aplicação. É flexível e oferece controle detalhado, porém exige mais operação e governança (atualizações, hardening, backups, monitoramento).

Casos típicos: migração “lift-and-shift” de servidores, ambientes legados que requerem SO específico, laboratórios e testes com configuração customizada.

Onde vou aplicar isso: ao analisar cenários que exigem customização de SO, você selecionará IaaS na atividade prática.

3) PaaS — Plataforma como Serviço

O PaaS abstrai o sistema operacional e parte do middleware, entregando ambientes prontos para executar código ou serviços gerenciados (por exemplo, bancos de dados, filas, functions, app services). O provedor gerencia patches do SO e parte de disponibilidade; você foca no aplicativo e nos dados. Normalmente acelera desenvolvimento e reduz a sobrecarga operacional.

Trade-offs: menos controle do SO, possíveis limites de customização e dependência de serviços específicos do fornecedor (vendor lock-in). Ainda assim, ganhos em produtividade, segurança padronizada e escalabilidade automática são relevantes.

Onde vou aplicar isso: ao escolher banco de dados gerenciado ou “app service” para hospedar uma API de tickets no passo a passo.

4) SaaS — Software como Serviço

No SaaS, o software completo é fornecido via internet. O provedor gerencia infraestrutura, plataforma e aplicação; o cliente gerencia contas, permissões, configurações de uso e dados inseridos. Exemplos: e-mail corporativo, suítes de produtividade, ferramentas ITSM, CRM, sistemas de RH.

Benefícios: implantação rápida, custos previsíveis por usuário, menor esforço de manutenção. Limitações: customização geralmente restrita, dependência total da disponibilidade do provedor e políticas de dados do fornecedor.

Onde vou aplicar isso: ao classificar ferramentas de atendimento/FAQ e justificar por que são SaaS na matriz.

5) Responsabilidade Compartilhada por Modelo

Responsabilidades variam por modelo. Em IaaS, você gerencia SO, patches e configurações de segurança. Em PaaS, você gerencia código, dados e configurações de serviço, enquanto o provedor cuida do SO. Em SaaS, você se concentra no uso correto, controle de acesso (IAM), privacidade e conformidade de dados.

  "IaaS": ["SO e patches", "Firewall no SO", "Backup do app/dados", "Monitoramento do host"],
  "PaaS": ["Config do serviço", "Código e dados", "Chaves/segredos", "Monitoramento da app"],

Onde vou aplicar isso: na justificativa técnica de cada classificação, explicando o que você gerencia em cada caso.

6) Critérios de Escolha por Contexto de Negócio

Escolher o modelo adequado envolve analisar: urgência (time-to-value), nível de customização exigido, equipe disponível para operar, requisitos de segurança/compliance, custos de curto e longo prazo, integração com sistemas existentes e risco de lock-in.

Uma matriz de decisão ajuda a ponderar critérios de forma objetiva. Atribua pesos e pontuações por cenário para comparar opções.

{
  "criterios": [
    {"nome": "Time-to-Value", "peso": 3},
    {"nome": "Customização", "peso": 2},
    {"nome": "Operação/Suporte", "peso": 3},
    {"nome": "Custo Total", "peso": 3},
    {"nome": "Compliance", "peso": 2}
  ]
}
Onde vou aplicar isso: você preencherá uma matriz com pesos e pontuações para defender sua escolha.

7) Implicações Operacionais

Cada modelo impacta a operação diária. IaaS demanda rotinas de patching, hardening, backup e monitoramento do SO. PaaS reduz essas tarefas, mas requer atenção a limites de serviço, escalonamento, chaves e logs. SaaS exige governança de acesso, DLP, configurações de privacidade, auditoria e integração via API quando necessário.

Para suporte técnico, entender esses impactos acelera triagem de incidentes, reduz tempo de recuperação e melhora a comunicação com usuários e gestores.

Onde vou aplicar isso: você descreverá implicações operacionais na justificativa de cada item classificado.

Etapa 4 — Classificar cada item

Preencha o campo “classificacao” com IaaS, PaaS ou SaaS e escreva uma justificativa técnica objetiva. Modelo de justificativa:

- O que o provedor gerencia?
- O que o cliente gerencia?
- Implicações operacionais (patches, backup, IAM, logs etc.)
- Critérios que pesaram na escolha (ex.: Time-to-Value, Custo)

Etapa 5 — Montar uma planilha de pontuação (opcional)

Se desejar comparar alternativas para um mesmo problema (ex.: hospedar uma API), crie um CSV com pesos e notas de 1 a 5.

Você pode somar manualmente ou usar um script simples:

// calc.js — soma ponderada (exemplo conceitual)
const criterios = [
  { nome: "Time-to-Value", peso: 3, IaaS: 2, PaaS: 5, SaaS: 5 },
  { nome: "Customização", peso: 2, IaaS: 5, PaaS: 3, SaaS: 1 },
  { nome: "Operação/Suporte", peso: 3, IaaS: 2, PaaS: 4, SaaS: 5 },
  { nome: "Custo Total", peso: 3, IaaS: 3, PaaS: 4, SaaS: 4 },
  { nome: "Compliance", peso: 2, IaaS: 3, PaaS: 4, SaaS: 4 },
];
const soma = (m) => criterios.reduce((acc,c) => acc + c.peso*(c[m]||0), 0);
console.log({ IaaS: soma('IaaS'), PaaS: soma('PaaS'), SaaS: soma('SaaS') });

Etapa 6 — Registrar implicações operacionais

Para cada item, adicione um parágrafo curto destacando controles e rotinas:

- IaaS: patching do SO, hardening, backups, antivirus/EDR, monitoramento de host.
- PaaS: configuração de rede/segurança do serviço, rotação de chaves/segredos, logs e métricas do serviço.
- SaaS: IAM (MFA, grupos), DLP, políticas de retenção, auditoria de atividades e integrações via API.
