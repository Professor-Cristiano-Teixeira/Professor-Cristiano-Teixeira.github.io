Capítulo 05 — Normalização (1FN, 2FN, 3FN)

Carga: Não especificada

Projeto-base: Caso de Vendas (Clientes, Pedidos e Itens)

Stack fixa: MySQL + MySQL Workbench; Python (opcional para validações)

Resultados de aprendizagem deste capítulo:

  • Identificar redundâncias e anomalias em tabelas não normalizadas.
  • Aplicar rigorosamente 1FN, 2FN e 3FN a um esquema relacional.
  • Explicar dependências funcionais e justificar decisões de normalização.
  • Equilibrar normalização e desempenho, reconhecendo trade-offs práticos.
  • Produzir um esquema normalizado pronto para implementação em DDL (Cap. 06).

Competências e Habilidades

  • Modelar dados relacionais com foco em integridade e consistência.
  • Analisar dependências funcionais e chaves primárias/estrangeiras.
  • Reestruturar tabelas para eliminar anomalias de inserção/atualização/exclusão.
  • Documentar e comunicar decisões técnicas de modelagem.

Parte Teórica (explicação do conteúdo)

Por que normalizar?

Normalização é um processo sistemático de organização de dados em um banco relacional para reduzir redundâncias e evitar anomalias de inserção, atualização e exclusão. Ao distribuir dados em tabelas relacionadas de forma coerente, o esquema fica mais consistente e simples de manter.

As anomalias surgem quando a mesma informação aparece repetidas vezes. Por exemplo, o nome de um cliente duplicado em várias linhas de pedidos. Uma atualização incorreta em uma linha e esquecida em outra pode comprometer a integridade.

Onde vou aplicar isso: durante a transição do DER (Cap. 03) para o modelo relacional (Cap. 04) e antes de implementar as tabelas no MySQL (Cap. 06). Também ao revisar modelos legados.

Dependências funcionais

Uma dependência funcional X → Y indica que um conjunto de atributos X determina unicamente os atributos Y. Ex.: CPF → NomeCliente significa que, para um CPF específico, há exatamente um NomeCliente associado.

Chaves primárias devem determinar todos os demais atributos não-chave na tabela. Dependências parciais (parte da chave determina atributos) e transitivas (um atributo não-chave determina outro não-chave) são indícios de problemas.

Onde vou aplicar isso: para verificar se a tabela atende às formas normais. Você usará essas dependências para justificar cada decomposição no passo a passo.

Primeira Forma Normal (1FN)

Regras: todos os atributos contêm valores atômicos (não multivalorados nem repetitivos) e não há grupos repetidos. Ex.: colunas Item1, Item2, Item3 violam 1FN; listas separadas por vírgula em uma única coluna também.

Estratégia: criar uma tabela de itens relacionada à entidade principal, substituindo colunas repetidas por linhas (um para muitos).

Onde vou aplicar isso: na divisão de “Pedidos” e “ItensPedido”, separando o que é do pedido (cabeçalho) do que é do item (linhas).

Segunda Forma Normal (2FN)

Válida para tabelas com chave primária composta: nenhum atributo não-chave pode depender de apenas parte da chave primária. Se a chave é (PedidoID, ProdutoID), então atributos como DataPedido devem depender do pedido inteiro, e não de apenas um dos componentes.

Estratégia: mover atributos que dependem somente de um componente da chave para outra tabela correspondente (ex.: DataPedido vai para “Pedidos”; PrecoUnitario vai para “Produtos” se for estável ou permanece no item como preço praticado no momento).

Onde vou aplicar isso: ao revisar a tabela “ItensPedido”, garantindo que cada atributo dependa de (PedidoID, ProdutoID) por completo.

Terceira Forma Normal (3FN)

Exige que não existam dependências transitivas de chave para atributo não-chave. Se Chave → A e A → B, então há dependência transitiva Chave → B; nesse caso, B deve ser movido para uma tabela onde A seja chave.

Estratégia: separar atributos que descrevem outros atributos não-chave (ex.: CEP determinando Cidade/UF deve ser normalizado removendo Cidade/UF para uma tabela de referência, se fizer sentido para o contexto).

Onde vou aplicar isso: ao identificar atributos derivados de outros (ex.: SubtotalItem = Qtd x PrecoUnitario), que devem ser calculados em consulta/relatório, não armazenados se puderem ser derivados de forma determinística.

Trade-offs entre normalização e performance

Mais normalização tende a reduzir redundância, mas pode aumentar a quantidade de junções em consultas. Em cenários de relatórios complexos, pode haver equilíbrio: manter alguns dados derivados ou desnormalizados para leitura rápida, desde que com processos de atualização confiáveis.

Decisão prática: começar em 3FN para o sistema transacional (OLTP). Desnormalizações pontuais devem ser documentadas e justificadas por métricas de desempenho.

Onde vou aplicar isso: ao preparar relatórios (Cap. 08–09) e pensar em índices. A normalização é a base, e ajustes de desempenho vêm depois, com medição.

Passo a Passo — Normalizando o caso de Vendas até 3FN

Objetivo desta etapa:

Partir de uma tabela “PedidosBruto” mal estruturada e chegar a um conjunto de tabelas normalizadas (Clientes, Produtos, Pedidos, ItensPedido) pronto para implementação em DDL no Capítulo 06.


1) Tabela inicial (não normalizada)

Considere a tabela “PedidosBruto”, típica de uma planilha:

-- Exemplo didático: não crie em produção; é um ponto de partida
-- Colunas com grupos repetidos e dados misturados
-- PK inexistente ou mal definida, anomalias prováveis
CREATE TABLE PedidosBruto (
  PedidoID        INT,
  DataPedido      DATE,
  ClienteID       INT,
  NomeCliente     VARCHAR(120),
  CPFCliente      VARCHAR(14),
  Endereco        VARCHAR(200),
  CEP             VARCHAR(9),
  Cidade          VARCHAR(80),
  UF              CHAR(2),
  Item1_ProdutoID INT,
  Item1_Nome      VARCHAR(120),
  Item1_Qtd       INT,
  Item1_Preco     DECIMAL(10,2),
  Item2_ProdutoID INT,
  Item2_Nome      VARCHAR(120),
  Item2_Qtd       INT,
  Item2_Preco     DECIMAL(10,2),
  Item3_ProdutoID INT,
  Item3_Nome      VARCHAR(120),
  Item3_Qtd       INT,
  Item3_Preco     DECIMAL(10,2)
);

Problemas: grupos repetidos (Item1/Item2/Item3), dados de cliente misturados ao pedido, risco de inconsistência (NomeCliente duplicado com grafias diferentes).

Onde aplico: Identificação de 1FN violada (grupos repetidos). Vamos corrigir no próximo passo.

2) Aplicar 1FN — valores atômicos e remoção de grupos repetidos

Quebramos “PedidosBruto” em duas estruturas: “Pedidos” (cabeçalho) e “ItensPedido” (linhas), cada item em sua própria linha.

-- Cabeçalho do pedido
CREATE TABLE Pedidos (
  PedidoID    INT PRIMARY KEY,
  DataPedido  DATE,
  ClienteID   INT
);

-- Linhas do pedido
CREATE TABLE ItensPedido (
  PedidoID     INT,
  ProdutoID    INT,
  Quantidade   INT,
  PrecoUnit    DECIMAL(10,2),
  PRIMARY KEY (PedidoID, ProdutoID)
);

Agora cada item do pedido é representado por uma linha em ItensPedido. Ainda faltam tabelas de “Clientes” e “Produtos” para separar descrições e atributos próprios.

Onde aplico: Conversão de grupos repetidos em linhas 1:N. Preparação para 2FN ao definir PK composta em ItensPedido.

3) Aplicar 2FN — eliminar dependências parciais

Na tabela “ItensPedido”, a PK é composta (PedidoID, ProdutoID). Atributos devem depender da chave inteira. “DataPedido” depende de PedidoID (cabeçalho) e não deve estar em ItensPedido. “Nome do produto” depende de ProdutoID e deve ficar em “Produtos”.

-- Tabela de clientes: dados que dependem de ClienteID
CREATE TABLE Clientes (
  ClienteID    INT PRIMARY KEY,
  NomeCliente  VARCHAR(120),
  CPFCliente   VARCHAR(14),
  Endereco     VARCHAR(200),
  CEP          VARCHAR(9),
  Cidade       VARCHAR(80),
  UF           CHAR(2)
);

-- Ajuste na tabela Pedidos para referenciar Cliente
-- (se já criada sem FK, vamos apenas documentar a intenção de chave estrangeira)
-- Em DDL final (Cap. 06) adicionaremos as FKs:
-- ALTER TABLE Pedidos ADD CONSTRAINT fk_pedidos_clientes
--   FOREIGN KEY (ClienteID) REFERENCES Clientes(ClienteID);

-- Tabela de produtos: dados que dependem de ProdutoID
CREATE TABLE Produtos (
  ProdutoID    INT PRIMARY KEY,
  NomeProduto  VARCHAR(120)
  -- Preço de catálogo pode ficar aqui se for um preço padrão,
  -- mas o preço praticado no pedido permanece em ItensPedido (histórico).
);

Agora, em ItensPedido, mantemos Quantidade e PrecoUnit como preço praticado na venda. “NomeProduto” não fica em ItensPedido; pertence a Produtos.

Onde aplico: Checagem de dependências parciais: cada atributo em ItensPedido deve depender de (PedidoID, ProdutoID) por completo.

4) Aplicar 3FN — eliminar dependências transitivas

Verifique atributos que dependem de outros atributos não-chave. Ex.: CEP → (Cidade, UF) em alguns contextos. Se a organização requer consistência forte, pode-se criar uma tabela de CEPs, mas na prática muitas bases mantêm Endereço/CEP/Cidade/UF no cadastro de Clientes.

Outro caso: SubtotalItem = Quantidade x PrecoUnit é um atributo derivado; mantenha como cálculo nas consultas para evitar inconsistência.

-- Versão final normalizada (3FN) – DDL ilustrativa sem FKs (serão adicionadas no Cap. 06)
-- Clientes(ClienteID, NomeCliente, CPFCliente, Endereco, CEP, Cidade, UF)
-- Produtos(ProdutoID, NomeProduto)
-- Pedidos(PedidoID, DataPedido, ClienteID)
-- ItensPedido(PedidoID, ProdutoID, Quantidade, PrecoUnit)

-- Exemplo de consulta calculando subtotal sem armazenar:
-- SELECT i.PedidoID, i.ProdutoID, i.Quantidade, i.PrecoUnit,
--        (i.Quantidade * i.PrecoUnit) AS Subtotal
-- FROM ItensPedido i;
Onde aplico: Remoção de atributos derivados armazenados e separação de dados que descrevem outros dados não-chave quando necessário.

5) Consolidar o modelo normalizado

Com o esquema em 3FN, podemos reforçar integridade referencial com chaves estrangeiras e preparar o DDL final (Cap. 06).

-- Esboço de chaves estrangeiras (para aplicar no Cap. 06):
-- ALTER TABLE Pedidos
--   ADD CONSTRAINT fk_pedidos_clientes
--   FOREIGN KEY (ClienteID) REFERENCES Clientes(ClienteID);

-- ALTER TABLE ItensPedido
--   ADD CONSTRAINT fk_itens_pedido
--   FOREIGN KEY (PedidoID) REFERENCES Pedidos(PedidoID),
--   ADD CONSTRAINT fk_itens_produtos
--   FOREIGN KEY (ProdutoID) REFERENCES Produtos(ProdutoID);

Valide cenários de anomalia: inserir pedido sem cliente? bloquear com FK. Duplicar nome de produto? permitido, desde que ProdutoID seja único.

Onde aplico: Preparação para implementação no MySQL Workbench e testes com DML no Cap. 07–09.

6) Verificação rápida das formas normais

  • 1FN: não há grupos repetidos; colunas atômicas; itens em tabela própria.
  • 2FN: em tabelas com PK composta, nenhum atributo não-chave depende apenas de parte da PK.
  • 3FN: não há dependência transitiva de chave para atributo não-chave; derivados são calculados.

7) Bônus (opcional) — Script de checagem simples em Python

Podemos esboçar uma verificação textual para detectar colunas repetidas (violação da 1FN) em um CSV de planilha original.

import csv
from collections import Counter

def detectar_grupos_repetidos(cabecalho):
  prefixos = [c.split('_')[0] for c in cabecalho if '_' in c]
  cont = Counter(prefixos)
  return [p for p, q in cont.items() if q >= 2]

with open('PedidosBruto.csv', newline='', encoding='utf-8') as f:
  reader = csv.reader(f)
  header = next(reader)
  repetidos = detectar_grupos_repetidos(header)
  if repetidos:
    print('Possível violação de 1FN. Grupos repetidos:', repetidos)
  else:
    print('Não foram detectados grupos repetidos no cabeçalho.')
Onde aplico: Diagnóstico inicial em dados legados antes de modelar o esquema no SGBD.
