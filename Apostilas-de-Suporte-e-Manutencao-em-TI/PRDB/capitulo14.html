Parte Teórica (explicação do conteúdo)

1) O que é ORM e por que usar

ORM (Object-Relational Mapping) é uma técnica que permite mapear classes e objetos da aplicação para tabelas e registros do banco relacional. Em vez de escrever diretamente SQL para cada operação, trabalhamos com modelos (classes) e uma camada de abstração que traduz as ações em comandos SQL.

Benefícios incluem produtividade (menos SQL repetitivo), consistência (padrões de acesso), segurança (parametrização por padrão) e manutenção (evoluir o esquema e modelos de forma centralizada). Entretanto, entender SQL continua essencial, pois o ORM gera SQL para o SGBD executar.

Onde vou aplicar isso: na reimplementação do CRUD de produtos (cap. 13) usando modelos e operações de sessão do ORM.

2) Mapeamento Objeto-Relacional (Modelos)

O mapeamento define como uma classe corresponde a uma tabela, e como seus atributos correspondem às colunas. Em SQLAlchemy, declaramos uma classe base, a tabela (__tablename__) e os tipos/constraints de cada coluna.

Chaves primárias e estrangeiras também são representadas. O ORM usa metadados para criar o SQL apropriado para o SGBD. O modelo é a “fonte de verdade” da camada de dados da aplicação.

Onde vou aplicar isso: ao criar a classe Produto e, opcionalmente, Categoria, com tipos, primary key e relacionamentos.

3) Sessões e Unidade de Trabalho

A sessão gerencia o ciclo de vida dos objetos persistidos: novos, pendentes, em memória, sujos (modificados) e removidos. O padrão “Unit of Work” agrupa operações como uma transação: ao executar commit(), o ORM sincroniza as mudanças com o banco, e rollback() desfaz alterações em caso de erro.

É boa prática criar fábricas de sessão e usar context managers para garantir fechamento e tratamento de exceções.

Onde vou aplicar isso: ao construir funções create/read/update/delete que abrem sessão, executam a operação e fazem commit() ou rollback().

4) Consultas com ORM (Filters, Order, Paginação)

ORMs oferecem APIs para consultas: filtrar (filter/where), ordenar (order_by), limitar e paginar resultados. Em SQLAlchemy, as consultas modernas usam a ORM Query ou o 2.0 style com select().

Para casos simples, o código fica mais legível. Para relatórios complexos, pode ser vantajoso escrever SQL explícito.

Onde vou aplicar isso: ao listar produtos por preço, pesquisar por nome e implementar paginação simples.

5) Relacionamentos (One-to-Many, Many-to-Many)

Relacionamentos mapeiam chaves estrangeiras e coleções de objetos associados. Com relationship() definimos a navegação entre entidades. O ORM trata carregamento lazy/eager conforme configuração, evitando consultas desnecessárias quando possível.

Onde vou aplicar isso: ao ligar Produto a Categoria (1:N), para consultar produtos por categoria.

6) Noções de Migrações (Alembic)

Migrações versionam mudanças no esquema: criar tabelas, adicionar colunas, constraints etc. O Alembic (ecossistema SQLAlchemy) gera scripts de migração e permite subir/descer versões com upgrade/downgrade.

Mesmo conhecendo DDL, migrações padronizam evolução de banco em equipe e ambientes (dev/homolog/produção).

Onde vou aplicar isso: criar o esqueleto de projeto com Alembic, gerar uma revisão inicial e compreender o fluxo.

7) Vantagens e Limites do ORM

Vantagens: rapidez no desenvolvimento, menos repetição de SQL, integração com transações, segurança por parametrização, portabilidade entre SGBDs.

Limites: curva de aprendizado, possível overhead em consultas complexas, tuning mais difícil em cenários de alta performance; em relatórios sofisticados, SQL explícito pode ser melhor.

Onde vou aplicar isso: na comparação final reescrevendo uma consulta feita em SQL no cap. 13 com o ORM e analisando diferenças.

8) Segurança, Injeção de SQL e Boas Práticas

ORMs parametrizam consultas, reduzindo riscos de SQL Injection. Ainda assim, evite concatenar strings dinâmicas em filtros e use parâmetros do ORM. Valide dados de entrada e trate exceções propagando mensagens claras sem vazar detalhes sensíveis.

Onde vou aplicar isso: ao implementar as funções do CRUD com blocos try/except, commits e rollbacks apropriados.

Passo a Passo — Reimplementando o CRUD com ORM (SQLAlchemy)

Objetivo desta etapa:

Configurar SQLAlchemy com MySQL, criar modelos, estabelecer sessão e reescrever o CRUD de produtos com transações e consultas básicas.


Preparando o ambiente

Crie/abra a pasta do projeto do CRUD (cap. 13). Instale SQLAlchemy e, se necessário, o driver do MySQL (mysqlclient ou PyMySQL). Abaixo, exemplo com PyMySQL.

# em um terminal com o venv do projeto ativado
pip install sqlalchemy pymysql
# opcional (noções de migração)
pip install alembic

Garanta que o MySQL esteja ativo e que você saiba a conexão (host, porta, usuário, senha e nome do banco).

Configurando o engine e a Base declarativa

Crie um arquivo db.py para centralizar a conexão e a base de modelos.

# db.py
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker, declarative_base

# Substitua credenciais conforme seu ambiente
USER = "root"
PASSWORD = "senha"
HOST = "localhost"
PORT = 3306
DBNAME = "vendas"

DATABASE_URL = f"mysql+pymysql://{USER}:{PASSWORD}@{HOST}:{PORT}/{DBNAME}?charset=utf8mb4"

engine = create_engine(
    DATABASE_URL,
    echo=False,           # True para ver o SQL gerado
    pool_pre_ping=True,   # ajuda a evitar conexões 'mortas'
)

SessionLocal = sessionmaker(bind=engine, autoflush=False, autocommit=False)
Base = declarative_base()

Esse módulo será importado pelos modelos e operações de CRUD.

Criando o modelo Produto e (opcional) Categoria

Crie models.py com as classes mapeadas.

# models.py
from sqlalchemy import Column, Integer, String, Numeric, ForeignKey
from sqlalchemy.orm import relationship
from db import Base

class Categoria(Base):
    __tablename__ = "categorias"
    id = Column(Integer, primary_key=True, autoincrement=True)
    nome = Column(String(100), nullable=False, unique=True)

    produtos = relationship("Produto", back_populates="categoria")

    def __repr__(self):
        return f"<Categoria id={self.id} nome={self.nome!r}>"

class Produto(Base):
    __tablename__ = "produtos"
    id = Column(Integer, primary_key=True, autoincrement=True)
    nome = Column(String(120), nullable=False)
    preco = Column(Numeric(10, 2), nullable=False)
    categoria_id = Column(Integer, ForeignKey("categorias.id"), nullable=True)

    categoria = relationship("Categoria", back_populates="produtos")

    def __repr__(self):
        return f"<Produto id={self.id} nome={self.nome!r} preco={self.preco} cat={self.categoria_id}>"

Para criar as tabelas no banco a partir dos modelos, utilize:

# create_schema.py
from db import engine, Base
import models  # importa para registrar os modelos
Base.metadata.create_all(bind=engine)
print("Esquema criado/atualizado com sucesso!")

Execute o script de criação uma única vez ou sempre que inserir novos modelos/colunas durante a fase de protótipo.

Fábrica de sessão e utilitário de contexto

Crie um helper para usar sessão com segurança e transação.

# session_utils.py
from contextlib import contextmanager
from db import SessionLocal

@contextmanager
def get_session():
    session = SessionLocal()
    try:
        yield session
        session.commit()
    except Exception:
        session.rollback()
        raise
    finally:
        session.close()

Com esse padrão, cada bloco with get_session() garante commit/rollback e fechamento.

CRUD: Create, Read, Update, Delete com ORM

Implemente operações em crud.py reaproveitando o padrão do cap. 13, agora com ORM.

# crud.py
from typing import Optional, List
from decimal import Decimal
from models import Produto, Categoria
from session_utils import get_session

def criar_categoria(nome: str) -> Categoria:
    with get_session() as s:
        cat = Categoria(nome=nome)
        s.add(cat)
        s.flush()  # popula cat.id
        return cat

def criar_produto(nome: str, preco: Decimal, categoria_id: Optional[int] = None) -> Produto:
    with get_session() as s:
        prod = Produto(nome=nome, preco=preco, categoria_id=categoria_id)
        s.add(prod)
        s.flush()
        return prod

def obter_produto_por_id(pid: int) -> Optional[Produto]:
    with get_session() as s:
        return s.get(Produto, pid)

def listar_produtos(nome_like: Optional[str] = None, limite: int = 20, offset: int = 0) -> List[Produto]:
    with get_session() as s:
        q = s.query(Produto).order_by(Produto.nome.asc())
        if nome_like:
            q = q.filter(Produto.nome.ilike(f"%{nome_like}%"))
        return q.offset(offset).limit(limite).all()

def atualizar_preco(pid: int, novo_preco: Decimal) -> bool:
    with get_session() as s:
        prod = s.get(Produto, pid)
        if not prod:
            return False
        prod.preco = novo_preco
        # commit ocorre no exit do contexto
        return True

def deletar_produto(pid: int) -> bool:
    with get_session() as s:
        prod = s.get(Produto, pid)
        if not prod:
            return False
        s.delete(prod)
        return True

Note que usamos flush() para obter o id gerado antes do commit, quando necessário.

Testando rapidamente o CRUD

Crie um script simples de teste:

# main.py
from decimal import Decimal
from crud import (criar_categoria, criar_produto,
                  obter_produto_por_id, listar_produtos,
                  atualizar_preco, deletar_produto)

def demo():
    cat = criar_categoria("Informática")
    p = criar_produto("Teclado Mecânico", Decimal("199.90"), cat.id)
    print("Criado:", p)

    achado = obter_produto_por_id(p.id)
    print("Lido:", achado)

    lista = listar_produtos(nome_like="tec")
    print("Listagem parcial:", lista)

    ok = atualizar_preco(p.id, Decimal("179.90"))
    print("Atualizado?", ok, obter_produto_por_id(p.id))

    ok2 = deletar_produto(p.id)
    print("Removido?", ok2, obter_produto_por_id(p.id))

if __name__ == "__main__":
    demo()

Execute e verifique as saídas. No Workbench, confira os registros afetados.

Consultas: filtros, ordenação e paginação (ORM 2.0 style opcional)

Exemplo usando a API select() (SQLAlchemy 2.x):

# queries.py
from sqlalchemy import select
from db import SessionLocal
from models import Produto

def listar_paginado(pagina: int = 1, tam: int = 10):
    offset = (pagina - 1) * tam
    with SessionLocal() as s:
        stmt = select(Produto).order_by(Produto.preco.desc()).offset(offset).limit(tam)
        return s.execute(stmt).scalars().all()

Use a versão de consulta que seu professor/projeto adotar (Query API ou 2.0 style), mantendo consistência.

Noções de migração com Alembic (opcional)

Fluxo básico (demonstração):

# inicializar alembic (na raiz do projeto)
alembic init migrations

# editar alembic.ini para apontar DATABASE_URL
# editar env.py para usar a Base.metadata dos seus modelos

# gerar revisão baseada nos modelos atuais
alembic revision --autogenerate -m "cria tabelas iniciais"

# aplicar migração ao banco
alembic upgrade head

As revisões guardam histórico de mudanças. Em equipe, suba os scripts no repositório.

Comparando: SQL direto vs. ORM

Consulta exemplo do cap. 13, agora via ORM. SQL direto (recordando):

SELECT id, nome, preco
FROM produtos
WHERE preco >= 100
ORDER BY preco DESC
LIMIT 5;

Equivalente com ORM (Query API):

from db import SessionLocal
from models import Produto

with SessionLocal() as s:
    q = (s.query(Produto)
           .filter(Produto.preco >= 100)
           .order_by(Produto.preco.desc())
           .limit(5))
    resultados = q.all()
    for r in resultados:
        print(r.id, r.nome, r.preco)

Ambas funcionam; o ORM favorece reutilização e segurança, e o SQL explícito pode ser preferido para relatórios complexos.
