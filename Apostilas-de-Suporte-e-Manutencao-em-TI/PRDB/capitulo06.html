Capítulo 06 — DDL: Criação de Esquemas no MySQL

Carga: 4–6 horas (teoria e prática em laboratório)

Projeto-base: Caso de Vendas (clientes, produtos, pedidos e itens)

Stack fixa: MySQL + MySQL Workbench

Resultados de aprendizagem deste capítulo:

  • Implementar um esquema relacional no MySQL usando comandos DDL (CREATE, ALTER, DROP).
  • Definir tipos de dados e constraints adequados (PRIMARY KEY, FOREIGN KEY, UNIQUE, NOT NULL, DEFAULT, CHECK).
  • Converter o modelo lógico do caso de vendas em tabelas físicas funcionais.
  • Executar alterações seguras de esquema (ALTER TABLE) e compreender impactos em dados.
  • Validar integridade referencial, opções ON DELETE/UPDATE e boas práticas de nomeação.

Competências e Habilidades

  • Aplicar linguagem SQL DDL para criação e manutenção de estruturas de dados.
  • Escolher tipos de dados e constraints coerentes com regras de negócio.
  • Garantir integridade e consistência via chaves e referências.
  • Documentar e versionar mudanças de esquema em scripts organizados.

  • Validação: testar constraints com INSERTs simples e observar erros para aprender.

Parte Teórica (explicação do conteúdo)

1) O que é DDL (Data Definition Language)

A DDL é o subconjunto da SQL responsável por definir e alterar a estrutura do banco: bancos de dados, tabelas, colunas, índices e constraints. Os principais comandos são CREATE, ALTER e DROP. Eles moldam o “esqueleto” que receberá os dados.

Ao contrário da DML (que insere/atualiza/exclui linhas), a DDL cria e modifica objetos. Por isso, exige cuidado: mudanças estruturais impactam todas as aplicações que consomem o banco.

Onde vou aplicar isso no passo a passo: você usará DDL para criar o banco do caso de vendas, suas tabelas, definir tipos e todas as chaves/constraints.

2) CREATE DATABASE e CREATE TABLE

CREATE DATABASE cria um novo banco com um nome único. Em geral, define-se o conjunto de caracteres (CHARSET) e a collation, afetando ordenação e comparações de strings.

CREATE TABLE estabelece colunas, tipos de dados e constraints. Uma boa definição inicial reduz retrabalho depois. Convém padronizar nomes em snake_case, usar singular para tabelas de entidades (ex.: cliente, produto) e plural quando fizer sentido localmente, mantendo a consistência.

Onde vou aplicar isso no passo a passo: logo no início criaremos o banco e cada tabela do caso de vendas, uma por uma, em script versionado.

3) Tipos de dados no MySQL (visão prática)

Os tipos mais comuns: INT/BIGINT para inteiros, DECIMAL(p,s) para valores monetários, VARCHAR(n) para textos curtos, TEXT para textos longos, DATE/DATETIME/TIMESTAMP para datas, BOOLEAN (TINYINT(1)) para flags lógicas.

Para dinheiro, prefira DECIMAL a FLOAT/DOUBLE, evitando imprecisões binárias. Para códigos e nomes, escolha tamanhos suficientes (ex.: VARCHAR(100) para nome). Para datas de criação/atualização, DATETIME com DEFAULT CURRENT_TIMESTAMP pode ser útil.

Onde vou aplicar isso no passo a passo: ao definir colunas de clientes, produtos, pedidos e itens, escolheremos tipos adequados ao domínio.

4) Constraints: PRIMARY KEY, FOREIGN KEY, UNIQUE, NOT NULL, DEFAULT, CHECK

PRIMARY KEY (PK) identifica cada linha de forma única. Pode ser um inteiro auto_increment ou uma chave natural (desde que estável). FOREIGN KEY (FK) garante referência válida entre tabelas (ex.: pedido → cliente).

UNIQUE impede duplicidades (ex.: e-mail do cliente). NOT NULL exige valor informado. DEFAULT define valor padrão quando nada é passado. CHECK valida uma condição (MySQL 8+ implementa CHECK, mas algumas restrições podem variar por engine).

Onde vou aplicar isso no passo a passo: definiremos PKs, FKs com ações ON DELETE/UPDATE, e constraints para garantir integridade de dados.

5) Integridade referencial e ON DELETE/ON UPDATE

Ao criar FKs, você pode escolher a ação quando o registro pai é apagado/alterado: RESTRICT/NO ACTION (impede), CASCADE (propaga a exclusão/atualização), SET NULL (define FK como NULL, se permitido) e SET DEFAULT (menos comum no MySQL).

Use CASCADE com cautela: pode remover itens em cadeia. Em muitos cenários transacionais, preferimos RESTRICT/NO ACTION para evitar perdas acidentais.

Onde vou aplicar isso no passo a passo: ao declarar FKs de itens de pedido e pedidos, escolheremos a melhor política para o caso.

6) ALTER TABLE e mudanças seguras

ALTER TABLE adiciona/renomeia/remove colunas, cria índices e adiciona/drope constraints. Em ambientes com dados, sempre avalie impactos e faça backup. Em laboratório, exercitaremos adições e alterações simples.

Estratégias seguras incluem: criar colunas novas (mantendo as antigas até migração), preencher valores, depois remover as colunas antigas; executar em transações quando possível, e testar em ambiente de homologação.

Onde vou aplicar isso no passo a passo: faremos ajustes incrementais, como adicionar índice/coluna e modificar tamanho de VARCHAR.

7) DROP e ordem de exclusão

DROP TABLE remove a tabela e seus dados; DROP DATABASE remove todo o banco. A ordem importa por causa das FKs: primeiro remova tabelas filhas, depois as pais, ou drope as FKs explicitamente.

Em produção, drop é crítico e normalmente evitado sem backup/migração. No laboratório, usaremos com consciência para refazer o esquema quando necessário.

Onde vou aplicar isso no passo a passo: você poderá recriar do zero o esquema para treinar, seguindo a ordem correta.

Passo a Passo — Implementar o esquema do Caso de Vendas no MySQL

Objetivo desta etapa:

Criar um banco de dados e todas as tabelas do caso de vendas (clientes, produtos, pedidos, itens_pedido) com tipos e constraints corretos, além de executar ajustes via ALTER TABLE e validar a integridade referencial.


1) Preparar o ambiente (MySQL Workbench)

  1. Abra o MySQL Workbench e conecte-se ao servidor local (ou do laboratório).
  2. Crie um novo script SQL: File → New Query Tab.
  3. Guarde seu arquivo como 06_ddl_caso_vendas.sql no seu projeto.

Script inicial: criar o banco

-- 1) Criar o banco de dados com charset/collation
CREATE DATABASE IF NOT EXISTS caso_vendas
  DEFAULT CHARACTER SET utf8mb4
  DEFAULT COLLATE utf8mb4_general_ci;

-- 2) Selecionar o banco
USE caso_vendas;
Dica: use um script por capítulo para versionar sua evolução. Comente bem cada bloco.

2) Tabela cliente

Clientes têm id, nome, email único, data de cadastro e status (ativo/inativo). Escolhemos tipos que refletem o domínio.

-- Tabela: cliente
DROP TABLE IF EXISTS cliente;
CREATE TABLE cliente (
  id_cliente INT AUTO_INCREMENT PRIMARY KEY,
  nome VARCHAR(100) NOT NULL,
  email VARCHAR(150) NOT NULL UNIQUE,
  data_cadastro DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  ativo BOOLEAN NOT NULL DEFAULT TRUE,
  CHECK (nome <> '')
) ENGINE=InnoDB;
Onde aplico teoria: PK (id_cliente), UNIQUE (email), NOT NULL/DEFAULT, CHECK e engine InnoDB para FKs.

3) Tabela produto

Produtos têm id, nome, preço e estoque. Para valores monetários, use DECIMAL.

-- Tabela: produto
DROP TABLE IF EXISTS produto;
CREATE TABLE produto (
  id_produto INT AUTO_INCREMENT PRIMARY KEY,
  nome VARCHAR(120) NOT NULL,
  preco DECIMAL(10,2) NOT NULL CHECK (preco >= 0),
  estoque INT NOT NULL DEFAULT 0 CHECK (estoque >= 0),
  ativo BOOLEAN NOT NULL DEFAULT TRUE
) ENGINE=InnoDB;
Onde aplico teoria: tipos adequados (VARCHAR, DECIMAL, INT) e validações com CHECK.

4) Tabela pedido (FK para cliente)

Pedidos pertencem a um cliente. Decida a política de exclusão: aqui usamos RESTRICT para evitar perda acidental de histórico.

-- Tabela: pedido
DROP TABLE IF EXISTS pedido;
CREATE TABLE pedido (
  id_pedido INT AUTO_INCREMENT PRIMARY KEY,
  id_cliente INT NOT NULL,
  data_pedido DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  status VARCHAR(20) NOT NULL DEFAULT 'ABERTO',
  observacoes TEXT NULL,
  CONSTRAINT fk_pedido_cliente
    FOREIGN KEY (id_cliente) REFERENCES cliente(id_cliente)
    ON DELETE RESTRICT
    ON UPDATE CASCADE
) ENGINE=InnoDB;
Onde aplico teoria: FK com ON DELETE/UPDATE. Use CASCADE em UPDATE (id raramente muda) e RESTRICT na exclusão.

5) Tabela item_pedido (tabela de relacionamento N:M resolvida)

Itens ligam pedido a produto. A PK pode ser composta (id_pedido, id_produto) para impedir duplicidade do mesmo produto no mesmo pedido.

-- Tabela: item_pedido
DROP TABLE IF EXISTS item_pedido;
CREATE TABLE item_pedido (
  id_pedido INT NOT NULL,
  id_produto INT NOT NULL,
  quantidade INT NOT NULL CHECK (quantidade > 0),
  preco_unitario DECIMAL(10,2) NOT NULL CHECK (preco_unitario >= 0),
  PRIMARY KEY (id_pedido, id_produto),
  CONSTRAINT fk_item_pedido_pedido
    FOREIGN KEY (id_pedido) REFERENCES pedido(id_pedido)
    ON DELETE RESTRICT
    ON UPDATE CASCADE,
  CONSTRAINT fk_item_pedido_produto
    FOREIGN KEY (id_produto) REFERENCES produto(id_produto)
    ON DELETE RESTRICT
    ON UPDATE CASCADE
) ENGINE=InnoDB;
Onde aplico teoria: PK composta, múltiplas FKs e CHECKs garantindo quantidades/preços.

6) Executar e validar o esquema

  1. Selecione todo o script e execute (raio/“Execute the selected portion”).
  2. No Schema Navigator, atualize e confirme as tabelas criadas.
  3. Teste a integridade com inserts mínimos (ex.: inserir cliente, depois pedido e itens).

Testes rápidos

USE caso_vendas;

INSERT INTO cliente (nome, email) VALUES ('Ana Silva', 'ana@exemplo.com');

-- Tente criar pedido para cliente inexistente (deve falhar)
INSERT INTO pedido (id_cliente) VALUES (999);

-- Crie pedido correto
INSERT INTO pedido (id_cliente) VALUES (1);

-- Tente item com produto inexistente (deve falhar)
INSERT INTO item_pedido (id_pedido, id_produto, quantidade, preco_unitario)
VALUES (1, 999, 2, 10.00);

-- Crie um produto e o item
INSERT INTO produto (nome, preco, estoque) VALUES ('Caneta Azul', 2.50, 100);
INSERT INTO item_pedido (id_pedido, id_produto, quantidade, preco_unitario)
VALUES (1, 1, 2, 2.50);
Onde aplico teoria: validação prática das FKs (erros esperados quando referências não existem).

7) ALTER TABLE: ajustes comuns

Agora faremos alterações incrementais com ALTER TABLE, simulando evolução do esquema.

USE caso_vendas;

-- 7.1) Adicionar índice em produto.nome para buscas rápidas
ALTER TABLE produto
  ADD INDEX idx_produto_nome (nome);

-- 7.2) Aumentar tamanho do email do cliente
ALTER TABLE cliente
  MODIFY COLUMN email VARCHAR(200) NOT NULL;

-- 7.3) Adicionar coluna 'desconto' no item_pedido com padrão 0
ALTER TABLE item_pedido
  ADD COLUMN desconto DECIMAL(10,2) NOT NULL DEFAULT 0 CHECK (desconto >= 0);

-- 7.4) Criar constraint de domínio de status do pedido via CHECK (MySQL 8+)
ALTER TABLE pedido
  ADD CONSTRAINT chk_pedido_status
  CHECK (status IN ('ABERTO','PAGO','CANCELADO'));
Onde aplico teoria: ALTER TABLE para evoluir o esquema, índices, mudança de tipos e regras de domínio.

8) DROP (opcional, somente para treino)

Se quiser recriar tudo do zero, siga a ordem correta: primeiro tabelas filhas, depois pais.

-- CUIDADO: isso removerá dados!
DROP TABLE IF EXISTS item_pedido;
DROP TABLE IF EXISTS pedido;
DROP TABLE IF EXISTS produto;
DROP TABLE IF EXISTS cliente;

-- Remover o banco todo (opcional)
-- DROP DATABASE IF EXISTS caso_vendas;
Onde aplico teoria: ordem de DROP por causa de FKs. Use somente para treinos controlados.

Critérios de avaliação

  • Aderência às regras de negócio propostas e justificativa das decisões (ex.: políticas ON DELETE).
  • Uso adequado de ALTER TABLE e índices, com breve explicação do impacto.
