Projeto-base: Comparação prática: CSV vs. Tabela Relacional

Stack fixa: Python, MySQL, MySQL Workbench, MongoDB, MongoDB Compass, Thonny IDE

  • Diferenciar modelos conceitual e lógico de dados e sua finalidade.

Parte Teórica (explicação do conteúdo)

1) Por que usar um SGBD? Vantagens em relação a arquivos

Um Sistema Gerenciador de Banco de Dados (SGBD) é um software especializado para armazenar, organizar e recuperar dados de forma eficiente e segura. Diferente de arquivos planos (como CSV), um SGBD oferece controle de concorrência, integridade, consultas declarativas (SQL), segurança por usuários/perfis e mecanismos de backup e recuperação.

As principais vantagens incluem: redução de redundância, consistência dos dados, independência entre dados e aplicações, escalabilidade e suporte a transações. Isso torna processos como relatórios, auditoria e integração entre sistemas mais robustos.

Onde vou aplicar isso no passo a passo: você observará, na prática, como o SGBD garante tipos, chaves e consultas complexas em comparação ao CSV, registrando evidências no seu relatório.

2) Componentes essenciais de um SGBD

Catálogo (metadados): descreve a estrutura do banco (tabelas, colunas, tipos, índices, chaves). Permite que o SGBD e os usuários entendam o “formato” dos dados sem depender do código da aplicação.

Linguagens: DDL (definição do esquema), DML (manipulação de dados), DCL (controle de acesso) e TCL (controle de transações). Em SGBDs relacionais, essas linguagens se expressam via SQL.

Transações: conjunto de operações atômicas com propriedades ACID (Atomicidade, Consistência, Isolamento, Durabilidade). Garantem que erros não deixem o banco em estados inválidos.

Segurança: autenticação, autorização (permissões), políticas de acesso e auditoria. Garante que apenas usuários/automações autorizados vejam e modifiquem dados sensíveis.

Onde vou aplicar isso no passo a passo: você criará uma tabela (DDL), fará inserções e consultas (DML) e notará como tipos e chaves (catálogo) e as regras de integridade suportam a qualidade dos dados.

3) Modelos de dados: conceitual e lógico

O modelo conceitual (ex.: Diagrama Entidade-Relacionamento) captura a visão de negócio: entidades, atributos e relacionamentos. É agnóstico de tecnologia, focado em representar regras e significados dos dados.

O modelo lógico traduz o conceitual para estruturas específicas do SGBD (ex.: tabelas, colunas, tipos, chaves). É nele que se define como entidades viram tabelas, relacionamentos viram chaves estrangeiras e tipos de dados são escolhidos.

Separar conceitual e lógico favorece entendimento com usuários e boa implementação técnica, evitando problemas futuros de integridade e desempenho.

Onde vou aplicar isso no passo a passo: ao pensar a tabela relacional a partir do CSV, você identificará atributos e chaves (visão lógica) que derivam naturalmente de um esboço conceitual do domínio.

Passo a Passo — CSV vs. Tabela Relacional (MySQL)

Objetivo desta etapa:

Executar um experimento simples comparando armazenamento em arquivo CSV com uma tabela relacional no MySQL, observando integridade, consultas e facilidades do SGBD.


Passo 0 — Preparar o conjunto de dados (CSV)

Crie um arquivo chamado clientes.csv com alguns registros fictícios. Utilize um editor de texto ou planilha. Garanta que haja casos com dados faltantes e duplicados para observação.

id,nome,email,cidade,uf
1,Ana Souza,ana.souza@example.com,São Paulo,SP
2,Caio Lima,caio.lima@example.com,Rio de Janeiro,RJ
3,Patrícia Melo,patricia.melo@example.com,Belo Horizonte,MG
3,Patrícia Melo,patricia.melo@example.com,Belo Horizonte,MG
4,,marcos.silva@example.com,Curitiba,PR
5,Marina Dias,marina.dias@example.com,São Paulo,SP
Observação: Note a linha duplicada (id=3) e um nome ausente (linha do id=4). Esses casos ajudarão a comparar integridade entre CSV e SGBD.

Passo 1 — Criar um banco e uma tabela no MySQL (DDL)

Abra o MySQL Workbench. Conecte-se ao servidor local. Crie um banco de testes e uma tabela com restrições mínimas: chave primária, NOT NULL e UNIQUE para email.

-- Criar banco de dados de teste
CREATE DATABASE IF NOT EXISTS prdb_cap02
  DEFAULT CHARACTER SET utf8mb4
  DEFAULT COLLATE utf8mb4_general_ci;

USE prdb_cap02;

-- Criar tabela clientes
DROP TABLE IF EXISTS clientes;
CREATE TABLE clientes (
  id INT PRIMARY KEY,
  nome VARCHAR(100) NOT NULL,
  email VARCHAR(120) NOT NULL UNIQUE,
  cidade VARCHAR(80),
  uf CHAR(2)
);
Relacionando com a teoria: aqui você está usando DDL e registrando metadados no catálogo: tipos, chaves e constraints passam a ser conhecidos pelo SGBD.

Passo 2 — Inserir dados e observar integridade (DML)

Tente inserir dados equivalentes aos do CSV. Observe como a tabela reage a duplicidades de chave primária e email, e a valores nulos em campos NOT NULL.

USE prdb_cap02;

-- Registros válidos
INSERT INTO clientes (id, nome, email, cidade, uf) VALUES
(1, 'Ana Souza', 'ana.souza@example.com', 'São Paulo', 'SP'),
(2, 'Caio Lima', 'caio.lima@example.com', 'Rio de Janeiro', 'RJ');

-- Tentativa de duplicidade de PK (id=3 inserido duas vezes)
INSERT INTO clientes (id, nome, email, cidade, uf) VALUES
(3, 'Patrícia Melo', 'patricia.melo@example.com', 'Belo Horizonte', 'MG');

-- TENTE repetir o id=3 para observar o erro
-- INSERT INTO clientes (id, nome, email, cidade, uf) VALUES
-- (3, 'Patrícia Melo', 'patricia.melo@example.com', 'Belo Horizonte', 'MG');

-- Tentativa de nome NULL (violação do NOT NULL)
-- INSERT INTO clientes (id, nome, email, cidade, uf) VALUES
-- (4, NULL, 'marcos.silva@example.com', 'Curitiba', 'PR');
Efeito prático: o SGBD rejeita automaticamente registros que violem chaves e regras. Em um CSV, seria preciso criar scripts de validação por conta própria.

Passo 3 — Consultar e filtrar dados (SELECT)

Realize consultas típicas e compare com a dificuldade de fazer o mesmo em CSV sem ferramentas adicionais.

-- Listar todos
SELECT * FROM clientes;

-- Filtrar por UF
SELECT id, nome, cidade, uf
FROM clientes
WHERE uf = 'SP'
ORDER BY nome;

-- Buscar por domínio de e-mail
SELECT id, nome, email
FROM clientes
WHERE email LIKE '%@example.com';
Comparação: enquanto em CSV você dependeria de planilhas ou scripts, no SGBD a linguagem SQL oferece consultas declarativas eficientes e reprodutíveis.

Passo 4 — Importar CSV rapidamente (opcional)

Use o Workbench (Table Data Import Wizard) para importar clientes.csv. Mapeie as colunas e observe os erros gerados por duplicidades ou nulos, reforçando a integridade do SGBD.

Caso prefira script, um caminho é carregar o CSV no Python e inserir via SQL parametrizado.

# Exemplo ilustrativo de leitura de CSV em Python
import csv

with open('clientes.csv', newline='', encoding='utf-8') as f:
    reader = csv.DictReader(f)
    for row in reader:
        print(row['id'], row['nome'], row['email'])
Lição: importar dados para o SGBD centraliza regras de qualidade (constraints) e facilita auditoria e evolução do esquema.
