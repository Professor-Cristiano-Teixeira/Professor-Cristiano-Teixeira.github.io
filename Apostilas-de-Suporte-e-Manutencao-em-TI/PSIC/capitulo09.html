Capítulo 09 — HTTP e WebSocket para IoT: REST, códigos de status, timeouts e tempo real

Carga: 6h (2 encontros)

Projeto-base: Dispositivo IoT enviando telemetria via HTTP POST e recebendo configuração via HTTP GET, com prova de conceito de WebSocket eco

Stack fixa: ESP32 + MicroPython (ou Arduino C++), servidor local em Python (Flask) + WebSocket (websocket/ws), JSON, cURL/Postman

Resultados de aprendizagem deste capítulo:

  • Explicar diferenças entre HTTP (REST) e WebSocket e quando usar cada um na IoT.
  • Construir requisições GET/POST/PUT com JSON e interpretar códigos de status HTTP.
  • Implementar timeouts, retries e idempotência básica em clientes IoT.
  • Consumir uma API local para enviar telemetria e obter configurações do dispositivo.
  • Implementar um canal WebSocket de eco para mensagens em tempo real.
  • Registrar e analisar respostas e erros (logs) para troubleshooting.

Competências e Habilidades

  • Interpretar protocolos de aplicação (HTTP/WS) em cenários de IoT.
  • Serializar e validar dados em JSON.
  • Aplicar boas práticas de cliente HTTP: timeout, retry, backoff e verificação de status.
  • Operar ferramentas de teste (cURL/Postman) para inspecionar requisições/respostas.
  • Documentar endpoints, payloads e fluxos.
  • Configurar servidor local simples (Flask) e WS de teste para integração.

Plano de Aula (Capítulo 09)

  6. Laboratório 3 (30 min): Prova de conceito de WebSocket eco (cliente web e/ou script Python).
  7. Fechamento (10 min): Checklist, entregáveis e orientações para atividades individuais.

Parte Teórica (explicação do conteúdo)

1) HTTP para IoT: métodos e recursos

HTTP é um protocolo de aplicação cliente-servidor amplamente utilizado. Em IoT, é comum criar uma API REST para que o dispositivo envie telemetria (POST) e busque configurações (GET). Recursos são identificados por URLs (ex.: /telemetria, /config/dispositivo123) e representações transitam em formatos como JSON.

Onde vou aplicar: Você criará um endpoint /telemetria para receber POST JSON do dispositivo e um /config para o dispositivo fazer GET de parâmetros.

2) Métodos GET, POST, PUT e idempotência

GET recupera dados sem alterar estado do servidor; deve ser idempotente e seguro. POST cria/enfileira ações ou envia dados; não é idempotente por padrão. PUT substitui/atualiza um recurso e é idempotente (repetir o mesmo PUT não muda o resultado final). Em IoT, usar PUT para atualizar uma configuração específica é útil, enquanto POST é adequado para telemetria histórica.

Onde vou aplicar: Usaremos POST para telemetria e GET para buscar configurações. Você também verá um exemplo de PUT para alterar um limite de temperatura.

3) Códigos de status e tratamento de erros

Respostas HTTP possuem códigos de status: 2xx (sucesso), 4xx (erro do cliente), 5xx (erro do servidor). Exemplos: 200 OK, 201 Created, 400 Bad Request (JSON inválido), 401 Unauthorized (sem credencial), 404 Not Found (recurso inexistente), 500 Internal Server Error. O cliente deve registrar o código e agir: reprocessar, corrigir payload, aguardar e tentar novamente, etc.

Onde vou aplicar: No firmware, você fará logs do status e mensagens de erro; no servidor Flask, retornará códigos adequados.

4) Timeouts, retries e backoff

Dispositivos IoT estão sujeitos a variações de rede. Sempre configure timeout para as requisições. Em caso de falha transitória (ex.: 5xx ou timeout), aplique retry com backoff exponencial e limite de tentativas para evitar tempestades de tráfego e gasto excessivo de energia.

Onde vou aplicar: O cliente MicroPython implementará timeout e tentativas com backoff simples.

5) WebSocket: comunicação bidirecional

WebSocket mantém uma conexão persistente e full‑duplex entre cliente e servidor, útil para atualizações em tempo real (ex.: comandos imediatos, dashboards reativos). Diferente de HTTP, não requer nova conexão a cada mensagem. Em IoT, é comum no backend/dashboard; no dispositivo, o suporte depende da memória e bibliotecas disponíveis.

Onde vou aplicar: Você executará uma prova de conceito com um servidor de eco WebSocket e um cliente (navegador ou script) para entender o fluxo.

6) HTTP vs. MQTT vs. WebSocket: quando usar

HTTP é ótimo para integrações com serviços web e endpoints REST, coleta eventual e webhooks. MQTT é excelente para telemetria leve e pub/sub com tópicos e QoS. WebSocket serve para streams em tempo real e dashboards. A escolha depende de latência, overhead, confiabilidade, consumo de energia e arquitetura do sistema.

Onde vou aplicar: Você comparará latência percebida e esforço de implementação entre POST periódico e WebSocket de eco.

Passo a Passo — Enviando telemetria via HTTP e configurando WebSocket de eco

Objetivo desta etapa:

Construir um fluxo completo: subir uma API local (Flask), testar com cURL/Postman, programar o ESP32 (MicroPython) para enviar POST JSON e realizar GET de configurações com timeout e retries; por fim, rodar um servidor de eco WebSocket e interagir com um cliente.


1) Preparar o ambiente no PC (servidor HTTP com Flask)

Instale Python 3.10+ e crie um ambiente virtual. Em seguida, instale Flask.

# Windows (PowerShell) / Linux / macOS

# Ativar:

Crie o arquivo servidor.py com dois endpoints: POST /telemetria e GET /config.

from flask import Flask, request, jsonify

app = Flask(__name__)

CONFIG_ATUAL = {
    "deviceId": "esp32-01",
    "intervalo_s": 10,
    "limite_temp": 28.5
}

@app.route("/telemetria", methods=["POST"])
def telemetria():
    try:
        data = request.get_json(force=True, silent=False)
        # Validação simples
        if not data or "deviceId" not in data or "temperatura" not in data:
            return jsonify({"erro": "payload inválido"}), 400
        # Simule persistência/log
        print("[TELEMETRIA]", data)
        return jsonify({"status": "ok", "received": data}), 201
    except Exception as e:
        print("Erro:", e)
        return jsonify({"erro": "falha no servidor"}), 500

@app.route("/config", methods=["GET"])
def config():
    device_id = request.args.get("deviceId", "")
    # Poderia personalizar por device_id; aqui retorna config padrão
    return jsonify(CONFIG_ATUAL), 200

@app.route("/config/limite", methods=["PUT"])
def atualizar_limite():
    body = request.get_json(force=True, silent=False) or {}
    novo = body.get("limite_temp")
    if isinstance(novo, (int, float)):
        CONFIG_ATUAL["limite_temp"] = float(novo)
        return jsonify({"status": "atualizado", "limite_temp": CONFIG_ATUAL["limite_temp"]}), 200
    return jsonify({"erro": "limite_temp ausente ou inválido"}), 400

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)

Execute o servidor:

python servidor.py
# Acesse http://localhost:5000/config no navegador

2) Cliente no dispositivo (ESP32 + MicroPython)

Carregue MicroPython no ESP32 e conecte-se ao Wi‑Fi. Em seguida, crie o arquivo main.py com timeout e retry simples.

# main.py (MicroPython no ESP32)
import time, json
import network
import urequests as requests

WIFI_SSID = "SEU_SSID"
WIFI_PSK  = "SUA_SENHA"
API_BASE  = "http://SEU_PC:5000"  # ex: http://192.168.0.10:5000
DEVICE_ID = "esp32-01"

def wifi_connect():
    sta = network.WLAN(network.STA_IF)
    sta.active(True)
    if not sta.isconnected():
        sta.connect(WIFI_SSID, WIFI_PSK)
        t0 = time.ticks_ms()
        while not sta.isconnected() and time.ticks_diff(time.ticks_ms(), t0) < 15000:
            time.sleep_ms(300)
    print("Wi-Fi:", "OK" if sta.isconnected() else "FALHA", sta.ifconfig())
    return sta.isconnected()

def http_get(url, timeout=5):
    try:
        resp = requests.get(url, timeout=timeout)
        code = resp.status_code
        text = resp.text
        resp.close()
        return code, text
    except Exception as e:
        return None, str(e)

def http_post(url, payload, timeout=5):
    try:
        headers = {"Content-Type":"application/json"}
        resp = requests.post(url, data=json.dumps(payload), headers=headers, timeout=timeout)
        code = resp.status_code
        text = resp.text
        resp.close()
        return code, text
    except Exception as e:
        return None, str(e)

def backoff_sleep(attempt):
    # backoff exponencial com limite
    wait = min(2 ** attempt, 30)
    print("Retry em", wait, "s")
    time.sleep(wait)

def loop_main():
    if not wifi_connect():
        return
    tentativa = 0
    while True:
        # 1) Obter config
        code, text = http_get(API_BASE + "/config?deviceId=" + DEVICE_ID, timeout=5)
        if code == 200:
            cfg = json.loads(text)
            intervalo = int(cfg.get("intervalo_s", 10))
            limite = float(cfg.get("limite_temp", 30))
            print("Config:", cfg)
            tentativa = 0  # zera backoff após sucesso
        else:
            print("GET falhou:", code, text)
            tentativa += 1
            backoff_sleep(tentativa)
            continue

        # 2) Medir sensor (simulado)
        temperatura = 26.5
        umidade = 55.0
        payload = {"deviceId": DEVICE_ID, "temperatura": temperatura, "umidade": umidade}
        code, text = http_post(API_BASE + "/telemetria", payload, timeout=5)
        if code in (200, 201):
            print("POST ok:", code, text)
            tentativa = 0
        else:
            print("POST falhou:", code, text)
            tentativa += 1
            backoff_sleep(tentativa)
            continue

        # 3) Espera pelo próximo ciclo
        time.sleep(intervalo)

loop_main()

Substitua SEU_PC pelo IP do computador que executa o Flask. Verifique o console serial do ESP32 para logs de status e respostas.

3) Prova de conceito WebSocket (eco)

Instale a biblioteca websockets no PC e rode um servidor de eco simples.

pip install websockets
# ws_eco.py
import asyncio, websockets

async def echo(websocket):
    async for msg in websocket:
        print("Recebido:", msg)
        await websocket.send("eco: " + msg)

async def main():
    async with websockets.serve(echo, "0.0.0.0", 8765):
        print("WS eco em ws://localhost:8765")
        await asyncio.Future()  # roda para sempre

if __name__ == "__main__":
    asyncio.run(main())

Cliente rápido via navegador (abra um arquivo .html local e teste):

Atividades Práticas para o(a) aluno(a) (desenvolver por conta própria)

Objetivo: Consolidar o uso de HTTP/REST e WebSocket em cenários reais de IoT, reforçando boas práticas de cliente, servidor e depuração.

  1. Extensão do cliente: Inclua cabeçalho Authorization: Bearer <token> no POST/GET do ESP32 e valide o token no Flask (retorne 401 se ausente/errado).
  2. Endpoint de comandos: Crie um endpoint /comandos (GET) que retorne uma lista JSON de ações (ex.: buzzer=on/off). Faça o dispositivo buscar e imprimir no console.
  3. Mini-dashboard: Crie uma página HTML que faça fetch periódico em /ultimas (novo endpoint) e liste as últimas 5 telemetrias. Opcional: use WebSocket para atualizar em tempo real.

Critérios de Avaliação (rubrica resumida)

  • Funcionamento: requisições corretas, respostas adequadas, tratamento de erros.
  • Código: legibilidade, modularização mínima, comentários e logs claros.
  • Rede e protocolo: uso de status HTTP apropriados e timeouts/retries.
  • Segurança básica: token simples ou separação de credenciais do código.
  • Documentação: README curto com endpoints, exemplos de cURL e instruções de execução.

Pesquisas complementares (sugestões)

  • Comparação de overhead e latência: HTTP/REST vs. MQTT em redes instáveis.
  • Boas práticas de desenho de APIs REST para dispositivos restritos (paginação, compactação, cache).
  • WebSocket seguro (wss://) e implicações de firewall/NAT em ambientes industriais.
  • Estratégias de idempotência no cliente e no servidor (chaves de deduplicação).
