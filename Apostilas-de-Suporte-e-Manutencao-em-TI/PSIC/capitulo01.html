Capítulo 01 — Introdução à IoT: conceitos, arquitetura e cenários

Carga: 4 a 6 horas

Projeto-base: Mapeamento de um caso de uso local (monitoramento de sala) com fluxo ponta‑a‑ponta

Stack fixa: ESP8266/ESP32, MQTT (HiveMQ público), HTTP/REST, JSON, MySQL/MongoDB (local ou simulado)

Resultados de aprendizagem deste capítulo:

  • Definir o que é Internet das Coisas e identificar seus principais componentes (dispositivo, gateway, nuvem/serviços).
  • Explicar fluxos de dados típicos: sensor → protocolo (MQTT/HTTP) → serviço → banco de dados → dashboard.
  • Reconhecer desafios de escala, energia, conectividade e segurança em cenários reais.
  • Mapear um caso de uso local em um diagrama de blocos com entradas, saídas, protocolo e armazenamento.

Competências e Habilidades

  • Comunicar e documentar arquiteturas de sistemas IoT.
  • Relacionar componentes físicos e de software no fluxo de dados.
  • Analisar requisitos de conectividade e segurança básicos.
  • Planejar protótipos com foco em testes e mensuração.

Plano de Aula (Capítulo 01)

  • Parte 1 (30–40 min): Conceitos fundamentais de IoT, exemplos reais, componentes e desafios.
  • Parte 2 (40–50 min): Arquitetura de referência: dispositivo, gateway, rede, serviços em nuvem e banco de dados.
  • Parte 3 (30–40 min): Protocolos e fluxos de dados (MQTT, HTTP/REST), JSON e tópicos.
  • Laboratório guiado (60–80 min): Mapeamento de um caso de uso local (monitoramento de sala) em diagrama de blocos, definição de métricas, tópicos MQTT/rotas HTTP e esquema de dados.
  • Encerramento (10–15 min): Recapitulação, checklist e atividades práticas sugeridas.

Parte Teórica (explicação do conteúdo)

1) O que é IoT e onde vemos no dia a dia

Internet das Coisas (IoT) é o ecossistema de dispositivos físicos conectados à internet (ou redes locais), capazes de coletar, processar e trocar dados. Esses dispositivos incluem sensores (temperatura, umidade, movimento), atuadores (relés, motores), microcontroladores (ESP8266/ESP32) e serviços (brokers, APIs, bancos de dados) que transformam dados em ação e insights.

Aplicações comuns vão de automação residencial (climatização, iluminação) a cidades inteligentes (estacionamento, iluminação pública), indústria (monitoramento preditivo), agro (umidade do solo) e saúde (wearables). Em todos, há coleta de dados, transmissão e análise para tomada de decisão.

Onde vou aplicar isso no passo a passo: você mapeará um cenário local (monitoramento de sala) e identificará os elementos IoT nele.

2) Componentes de uma solução IoT

Uma solução típica possui: (a) dispositivo com sensores/atuadores; (b) conectividade (Wi‑Fi, celular, LoRa); (c) gateway/serviço (broker MQTT, API HTTP); (d) armazenamento (MySQL/MongoDB); (e) aplicação (dashboard e alertas). Opcionalmente há edge computing para pré-processamento.

O dispositivo lê sensores e envia telemetria; o serviço recebe, valida e persiste; a aplicação exibe gráficos e gera alertas; os atuadores podem ser acionados por comandos do serviço para fechar o loop.

Onde vou aplicar isso no passo a passo: você criará um diagrama de blocos contendo todos esses componentes e ligações.

3) Arquitetura e topologias de comunicação

No MQTT, dispositivos publicam/assinam tópicos em um broker. É leve e ideal para eventos frequentes. No HTTP/REST, dispositivos realizam requisições GET/POST/PUT a um servidor. É simples de integrar com serviços web. Em ambos, o payload costuma ser JSON.

Topologias: dispositivos → broker/API → BD → dashboard ou dispositivos → gateway local → nuvem. A escolha depende de energia, rede e requisitos de latência/confiabilidade.

Onde vou aplicar isso no passo a passo: você definirá qual protocolo usar no seu cenário e desenhará o fluxo de dados completo.

4) Desafios: escala, energia e segurança

Escala: com muitos dispositivos, há pressão sobre rede, processamento e armazenamento. Energia: dispositivos a bateria exigem duty cycle, modos de sono e otimização de payload.

Segurança: proteger credenciais, usar TLS/HTTPS quando possível, validar dados, aplicar princípio do menor privilégio. Embutir segurança desde o início reduz riscos.

Onde vou aplicar isso no passo a passo: você listará riscos e estratégias simples (ex.: separar credenciais, limitar tópicos) no seu diagrama e documentação.

5) Fluxo de dados ponta‑a‑ponta (E2E)

Um fluxo E2E descreve cada etapa por onde o dado passa: sensor mede → firmware cria JSON → envia por MQTT/HTTP → serviço valida e armazena → dashboard consulta e exibe → opcionalmente gera alerta → comando retorna ao dispositivo (atuador).

Documentar o fluxo ajuda no diagnóstico e na medição de desempenho (latência, perda, disponibilidade).

Onde vou aplicar isso no passo a passo: você escreverá um “contrato de dados” (JSON), definirá tópicos/URLs e o esquema do banco.

Passo a Passo — Mapeando um caso de uso IoT (monitoramento de sala)

Objetivo desta etapa:

Produzir um diagrama de blocos e um plano mínimo E2E para um cenário local, incluindo contratos de dados JSON, tópicos MQTT/rotas HTTP e esquema simples de armazenamento.


Etapa 1 — Definir o problema e as métricas

Contexto sugerido: uma sala de aula. O objetivo é monitorar temperatura e umidade, além de ocupação simples (porta aberta/fechada).

  1. Variáveis medidas: temperatura (°C), umidade (%), estado_porta (0/1).
  2. Periodicidade: a cada 10 s.
  3. Alertas: temperatura acima de 28 °C ou umidade abaixo de 30%.

Etapa 2 — Escolher protocolo e fluxo

Escolha um protocolo para telemetria inicial:

  • MQTT: leve, pub/sub, ideal para telemetria e comandos.
  • HTTP/REST: simples para integrar com serviços web e bancos via API.

Para este capítulo, defina o fluxo padrão: dispositivo → MQTT (broker público de testes, ex.: HiveMQ) → serviço consumidor → BD → dashboard.

Exemplo de tópico MQTT:

psic/salaA/telemetria
psic/salaA/alertas
psic/salaA/cmd

Etapa 3 — Contrato de dados (payload JSON)

Defina um “contrato” claro para as mensagens JSON. Inclua timestamp, deviceId e os campos de interesse. Isso facilita armazenamento e validação.

{
  "deviceId": "ESP32-SalaA-01",
  "ts": "2025-01-01T12:00:00Z",
  "sensores": {
    "temperatura": 26.8,
    "umidade": 45.2,
    "estado_porta": 1
  },
  "meta": {
    "fw": "v1.0.0",
    "rssi": -58
  }
}
Dica: padronize o timezone (UTC) no timestamp e documente versões de firmware para rastreabilidade.

Etapa 4 — Esquema de armazenamento

Escolha um banco para telemetria simples. No SQL (MySQL), crie uma tabela com colunas básicas; no NoSQL (MongoDB), uma coleção de documentos.

SQL (MySQL) — tabela telemetria:

CREATE TABLE telemetria (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  device_id VARCHAR(64) NOT NULL,
  ts TIMESTAMP NOT NULL,
  temperatura DECIMAL(5,2),
  umidade DECIMAL(5,2),
  estado_porta TINYINT,
  rssi INT,
  fw VARCHAR(16)
);

NoSQL (MongoDB) — documento de exemplo:

{
  "deviceId": "ESP32-SalaA-01",
  "ts": {"$date": "2025-01-01T12:00:00Z"},
  "temperatura": 26.8,
  "umidade": 45.2,
  "estado_porta": 1,
  "rssi": -58,
  "fw": "v1.0.0"
}

Etapa 5 — Definir endpoints alternativos HTTP (opcional)

Mesmo usando MQTT, descreva rotas HTTP para futura integração.

POST /api/telemetria
GET  /api/config?deviceId=ESP32-SalaA-01
GET  /api/telemetria?deviceId=ESP32-SalaA-01&limit=100

Exemplo de POST JSON (mesmo contrato da Etapa 3):

{
  "deviceId": "ESP32-SalaA-01",
  "ts": "2025-01-01T12:00:00Z",
  "sensores": {"temperatura": 26.8, "umidade": 45.2, "estado_porta": 1},
  "meta": {"fw": "v1.0.0", "rssi": -58}
}

Etapa 6 — Esboçar o diagrama de blocos

Desenhe os blocos e setas: Dispositivo (ESP8266/ESP32) → Wi‑Fi → Broker MQTT (HiveMQ) → Serviço (consumidor) → Banco (MySQL/MongoDB) → Dashboard. Inclua também o caminho de comando (dashboard → serviço → tópico cmd → dispositivo).

Se estiver sem ferramenta de diagrama, descreva textualmente:

[ESP32 sensores] --Wi‑Fi--> [Broker MQTT] --sub/parse--> [Serviço] --persist--> [BD]
                                                   \--pub alertas--> [Dashboard]
[Dashboard comando] --API--> [Serviço] --pub cmd--> [ESP32 atuador]

Etapa 7 — Boas práticas iniciais

  • Use nomes de tópicos consistentes e minúsculos.
  • Separe credenciais do código (arquivo .env, config.local).
  • Valide JSON recebido antes de persistir.
  • Planeje reconexão de rede e filas locais em caso de falha.

Exemplo de arquivo de configuração (pseudo .env/.json):

{
  "mqtt": {
    "broker": "broker.hivemq.com",
    "port": 1883,
    "topic_pub": "psic/salaA/telemetria",
    "topic_cmd": "psic/salaA/cmd"
  },
  "http": {"baseUrl": "http://localhost:3000/api"},
  "device": {"id": "ESP32-SalaA-01", "pub_interval_ms": 10000}
}

Etapa 8 — Simular dados e validar contrato

Antes do hardware, publique mensagens de teste usando um cliente MQTT (MQTTX/MQTT Explorer/Studio) ou um script.

Publicando com MQTTX (exemplo textual):

Broker: broker.hivemq.com (porta 1883)
Tópico: psic/salaA/telemetria
Payload: { "deviceId":"ESP32-SalaA-01", "ts":"2025-01-01T12:00:00Z",
           "sensores":{"temperatura":27.5,"umidade":44.1,"estado_porta":0},
           "meta":{"fw":"v1.0.0","rssi":-60} }

Script simples (Node/CLI hipotético com curl para HTTP):

# Exemplo HTTP de teste (se tiver um endpoint local)
curl -X POST http://localhost:3000/api/telemetria \
  -H "Content-Type: application/json" \
  -d '{"deviceId":"ESP32-SalaA-01","ts":"2025-01-01T12:00:00Z",
       "sensores":{"temperatura":27.5,"umidade":44.1,"estado_porta":0},
       "meta":{"fw":"v1.0.0","rssi":-60}}'

Atividades Práticas para o(a) aluno(a) (desenvolver por conta própria)

Objetivo: Consolidar a compreensão de arquitetura IoT ao elaborar diagramas, contratos de dados e planos mínimos de integração.

  1. Mapeie um segundo ambiente (biblioteca, laboratório ou corredor) e produza um diagrama de blocos com pelo menos 2 sensores e 1 atuador. Inclua os tópicos MQTT e um endpoint HTTP alternativo.
  2. Projete um contrato JSON para um alerta de conforto térmico, incluindo campos para limiar, histerese e “fonte do alerta” (dispositivo/servidor).
  3. Modele a tabela/coleção para armazenar alertas e consultas mais comuns (últimas 24h por deviceId).

Critérios de avaliação (formativa)

  • Clareza do diagrama e coerência do fluxo E2E.
  • Contrato de dados JSON consistente e validável.
  • Definição correta de tópicos/endpoints e esquema de dados.
  • Considerações básicas de segurança e confiabilidade.
  • Organização do material entregue (nomes de arquivos, versão, datas).

Pesquisas complementares (sugestões)

  • Quando usar MQTT vs. HTTP em IoT? Comparar latência, overhead e confiabilidade.
  • Boas práticas de modelagem de dados de séries temporais (SQL vs. NoSQL).
  • Exemplos de incidentes reais em IoT causados por configurações inseguras.
  • Impacto do ciclo de trabalho e modos de sono no consumo do ESP32/ESP8266.

Entregáveis ao final do Capítulo 01
