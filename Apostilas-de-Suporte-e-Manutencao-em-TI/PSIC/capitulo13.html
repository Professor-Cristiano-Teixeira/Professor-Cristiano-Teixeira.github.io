Capítulo 13 — Versionamento, documentação e padronização

Carga: 4–6 horas (estimado)

Projeto-base: Repositório IoT padrão com README completo, diagramas e templates

Stack fixa: Git/GitHub, Markdown, diagrams.net, ESP8266/ESP32 (exemplos), Git CLI

Resultados de aprendizagem deste capítulo:

  • Configurar um repositório Git com branches, convenções de commits e tags/releases.
  • Produzir README técnico claro com diagrama de blocos, pinagem e Guia de Build/Flash/Teste.
  • Manter uma lista de materiais (BOM) e padrões de código consistentes.
  • Criar templates de issues e PRs para padronizar suporte e colaboração.
  • Aplicar versionamento semântico e gerar release de artefatos do projeto.

Competências e Habilidades

  • Organização de repositórios e documentação técnica.
  • Uso prático de Git (branches, merge, tags).
  • Comunicação técnica por meio de Markdown e diagramas.
  • Padronização de código e rastreabilidade de mudanças.
  • Preparação de materiais para manutenção e suporte.

Plano de Aula (Capítulo 13)

  1. Contexto e importância (15 min): problemas comuns sem versionamento e documentação; impacto em suporte/manutenção.
  2. Revisão rápida de Git (20 min): clone, branch, commit, merge, tag. Convenções e boas práticas.
  3. Documentação essencial (30 min): estrutura de README, diagrama de blocos, pinagem e BOM. Demonstração no diagrams.net.
  4. Padrões de código e templates (25 min): convenções, template de issues/PRs e CHANGELOG semântico.
  5. Laboratório guiado (60–90 min): montar repositório padrão, criar branches, escrever README e gerar uma release v0.1.0.
  6. Encerramento (10 min): checklist, critérios de qualidade e entregáveis do capítulo.

Parte Teórica (explicação do conteúdo)

1) Por que versionamento em IoT?

Projetos IoT combinam hardware, firmware, rede e serviços. Sem versionamento, torna-se difícil rastrear alterações, reproduzir builds e comparar comportamentos entre versões. Git oferece histórico, ramificações para experimentos e marcações de versões estáveis.

Com tags e releases, é possível relacionar binários/firmware a um estado do código-fonte, facilitar rollback e auditoria. Em equipes, branches organizam fluxos de trabalho sem interromper a versão principal.

Onde vou aplicar: no passo a passo, você criará um repositório com branches, fará commits padronizados, abrirá PRs e publicará uma release marcada com tag.

2) Fluxo de branches e convenções de commit

Fluxos comuns: main (produção), develop (integração), feature/..., fix/..., hotfix/... Escolha um fluxo simples e sustentável para a turma. Commits devem ser frequentes, com mensagens claras e no imperativo (ex.: “Adiciona leitura do DHT22”).

Commits semânticos ajudam: tipo (feat, fix, docs, chore, refactor), escopo opcional e descrição curta. Ex.: “feat(sensor): publica telemetria em QoS 1”.

Onde vou aplicar: você criará branches feature/ e praticará mensagens de commit semânticas no laboratório.

3) Versionamento semântico (SemVer)

SemVer usa MAJOR.MINOR.PATCH (ex.: 1.2.3). Incrementos: MAJOR para mudanças incompatíveis, MINOR para novas funcionalidades compatíveis e PATCH para correções. Em IoT, SemVer facilita compatibilidade entre firmware, API e dashboard.

Aplicar tags como v0.1.0 e gerar notas de release cria marcos claros para testes e suporte.

Onde vou aplicar: você criará uma tag v0.1.0 e publicará uma release com notas.

4) README técnico e diagrama de blocos

O README é a porta de entrada do repositório: descreve objetivo, arquitetura (diagrama), instruções de build/flash/teste, pinagem, variáveis de ambiente/segredos e como contribuir.

Diagrama de blocos mostra relação entre sensor/atuador, MCU, rede, broker/HTTP e banco/dash. Use nomenclatura coerente com os componentes reais.

Onde vou aplicar: você usará um template de README e desenhará um diagrama no diagrams.net, adicionando uma imagem ao repositório.

5) Pinagem e BOM (Bill of Materials)

A pinagem documenta ligações entre pinos do MCU e periféricos (GPIO, alimentação, pull-up etc.). A BOM lista os itens do projeto (código, quantidade, especificação, observações), permitindo reposição e reprodução do protótipo.

Onde vou aplicar: você criará uma tabela de pinagem e um arquivo BOM.md com a lista de materiais.

6) Padrões de código e templates de issues/PR

Definir convenções de código (nomes de funções, formatação, comentários) reduz erros e acelera revisão. Templates de issues e PRs garantem que bugs e mudanças venham com contexto, passos de reprodução e evidências.

Onde vou aplicar: você criará .github/ISSUE_TEMPLATE e PULL_REQUEST_TEMPLATE, além de um CONTRIBUTING.md simples.

7) CHANGELOG e rastreabilidade

Um CHANGELOG resume mudanças por versão. Manter esse arquivo ajuda quem dá suporte a entender o que mudou e quando. Vincule issues/PRs e tags.

Onde vou aplicar: você iniciará um CHANGELOG.md e o atualizará ao publicar a release.

Passo a Passo — Repositório padrão com Git, README, diagramas e release

Objetivo desta etapa:

Estruturar um repositório IoT padronizado com branches, commits semânticos, README completo com diagrama, pinagem e BOM; configurar templates de issues/PR e publicar uma release v0.1.0.


1) Criar o repositório e a estrutura básica

Crie uma pasta do projeto, inicialize Git e adicione arquivos essenciais. A estrutura mínima inclui README.md, LICENSE, .gitignore, src/, docs/ e .github/.

# 1. Criar pasta e iniciar Git
mkdir iot-monitor && cd iot-monitor
git init

# 2. Configuração de usuário (se necessário)
git config user.name "Seu Nome"
git config user.email "seu.email@example.com"

# 3. Estrutura inicial
mkdir -p src docs .github/ISSUE_TEMPLATE
touch README.md LICENSE .gitignore CHANGELOG.md
echo "# Compilar/flash scripts, firmware etc." > src/README.md

# 4. .gitignore básico (ESP/Arduino + IDEs)
cat > .gitignore << 'EOF'
# IDE/OS
.DS_Store
.vscode/
.idea/
*.log

# Arduino/PlatformIO
.build/
.pio/
*.elf
*.bin
*.hex

# Segredos locais
.env
secrets.json
EOF

# 5. Primeiro commit
git add .
git commit -m "chore: estrutura inicial do repositório"
Onde vou aplicar: esses arquivos serão usados em todos os próximos passos para documentação, padronização e releases.

2) Definir branches e convenções de commit

Crie um fluxo simples com main e develop. Use branches feature/ para novas funcionalidades e fix/ para correções. Adote mensagens semânticas.

# Criar branch develop e protegê-la no remoto depois
git branch -M main
git checkout -b develop

# Exemplo de branch de feature
git checkout -b feature/readme-template

# Exemplo de commit semântico
git add README.md
git commit -m "docs: adiciona template inicial de README"
Exemplos de mensagens:
- feat(sensor): adiciona leitura do DHT22
- fix(wifi): corrige reconexão com backoff exponencial
- docs: inclui diagrama de blocos e pinagem
- refactor(net): separa módulo de rede do loop principal
- chore(ci): ajusta workflow de build
Onde vou aplicar: você praticará criando branches feature/ e abrindo PR para a branch develop.

3) Montar README técnico completo

Use o template abaixo e adapte para seu projeto. Inclua objetivos, arquitetura, diagrama, pinagem, BOM, build/flash/teste e variáveis de ambiente.

# {{NOME_DO_PROJETO}}
Monitoramento ambiental IoT com ESP8266/ESP32, telemetria MQTT/HTTP e dashboard.

## Sumário
- Visão geral
- Arquitetura e diagrama
- Pinagem
- Lista de materiais (BOM)
- Configuração (segredos/variáveis)
- Build, Flash e Teste
- Convenções (código, commits, branches)
- Suporte e Contribuição
- Licença

## Visão geral
Descreva objetivo, sensores, atuadores e protocolos utilizados.

## Arquitetura e diagrama
![Diagrama](docs/diagrama.png)
Fluxo: Sensor → MCU (Wi‑Fi) → Broker MQTT/HTTP → Banco → Dashboard/Alertas.

## Pinagem
| Componente | Pino MCU | Observação        |
|-----------:|:--------:|-------------------|
| DHT22      | D4/GPIO2 | Pull-up interno   |
| LED        | D2/GPIO4 | Ativo em nível BAIXO |

## Lista de materiais (BOM)
| Código | Item                 | Qtde | Observações          |
|------:|----------------------|:----:|----------------------|
| 001   | ESP8266 NodeMCU      | 1    | MicroUSB             |
| 002   | Sensor DHT22         | 1    | 3.3V                 |
| 003   | Resistor 330Ω        | 1    | LED                  |

## Configuração
Crie um arquivo `.env` (não commitar):
```
WIFI_SSID=<ssid>
WIFI_PASS=<senha>
BROKER_URL=tcp://broker.hivemq.com:1883
```

## Build, Flash e Teste
1. Compilar no Arduino IDE/PlatformIO.
2. Fazer flash via USB.
3. Abrir Serial Monitor (115200) e validar logs.

## Convenções
Commits semânticos (feat, fix, docs, chore, refactor), branches main/develop/feature.

## Suporte e Contribuição
Abra issues com logs, passos para reproduzir e contexto do hardware.

## Licença
CC0 1.0 / MIT (escolha uma).
Onde vou aplicar: você preencherá o README com os dados reais do seu protótipo e adicionará a imagem do diagrama em docs/.

4) Criar diagrama de blocos e adicionar ao repositório

Abra o diagrams.net (draw.io), crie um diagrama com sensores, MCU, Wi‑Fi, broker/HTTP, BD e dashboard, exporte para PNG e salve em docs/diagrama.png.

# Exemplo: adicionando o diagrama
git checkout -b feature/diagrama
# (adicione docs/diagrama.png)
git add docs/diagrama.png README.md
git commit -m "docs: adiciona diagrama de blocos ao README"
git push -u origin feature/diagrama
Onde vou aplicar: o diagrama facilita entendimento e troubleshooting nos próximos capítulos.

5) Pinagem e BOM detalhadas

Crie arquivos dedicados para pinagem e materiais. Ex.: docs/pinagem.md e BOM.md. Mantenha consistência com o circuito e o código.

docs/pinagem.md
# Pinagem
- DHT22: VCC (3.3V), GND, DATA → D4 (GPIO2)
- LED: Anodo → 3.3V via resistor 330Ω, Catodo → D2 (GPIO4)

BOM.md
# Lista de Materiais (BOM)
- ESP8266 NodeMCU (x1)
- DHT22 (x1)
- Protoboard (x1)
- Resistores: 330Ω (x1), 10kΩ (x1, se necessário pull-up)
- Jumpers diversos
Onde vou aplicar: documentação de hardware será usada para montar, revisar e manter o protótipo.

7) CHANGELOG e versionamento semântico

Inicie o CHANGELOG e crie uma tag de versão. Publique uma release no remoto (GitHub/GitLab) com notas.

CHANGELOG.md
# Changelog
Todas as mudanças notáveis neste projeto serão documentadas aqui.

## [v0.1.0] - 2026-05-01
### Adicionado
- Estrutura inicial do repositório
- README com diagrama, pinagem e BOM
- Templates de issues e PR
# Marcar versão e criar tag
git checkout main
git merge --no-ff develop -m "merge: release v0.1.0"
git tag -a v0.1.0 -m "Primeira release: docs + estrutura"
git push origin main --tags
Onde vou aplicar: a release v0.1.0 será a base para os próximos incrementos e suporte.

8) Exemplo de diretório src/ com convenções

Organize o firmware em camadas: hardware (drivers), lógica (negócio) e rede. Use nomes claros e comentários objetivos.

src/
├─ hardware/
│  ├─ dht_sensor.h
│  └─ dht_sensor.cpp
├─ net/
│  ├─ wifi.h
│  └─ wifi.cpp
├─ app/
│  └─ app.cpp
└─ main.ino
// src/net/wifi.h
#pragma once
#include <Arduino.h>
bool wifi_connect(const char* ssid, const char* pass, uint8_t retries = 5);
bool wifi_is_connected();

// src/net/wifi.cpp
#include "wifi.h"
#include <ESP8266WiFi.h>
bool wifi_connect(const char* ssid, const char* pass, uint8_t retries){
  WiFi.mode(WIFI_STA);
  WiFi.begin(ssid, pass);
  while(retries-- > 0 && WiFi.status() != WL_CONNECTED){
    delay(1000);
    Serial.print(".");
  }
  Serial.println();
  return WiFi.status() == WL_CONNECTED;
}
Onde vou aplicar: padronização de nomes e camadas melhora manutenção e revisão por pares.

Atividades Práticas para o(a) aluno(a) (desenvolver por conta própria)

Objetivo: Consolidar versionamento, documentação e padronização em um repositório IoT replicável.

  1. Crie um repositório do seu projeto IoT com a estrutura proposta e publique no GitHub/GitLab.
  2. Preencha README com diagrama, pinagem, BOM e guia de build/flash/teste. Adicione docs/diagrama.png.
  3. Implemente templates de issue/PR e abra 1 issue fictícia de bug com logs. Abra 1 PR contra develop.
  4. Marque a versão v0.1.0, gere CHANGELOG e publique a release com notas sucintas.

Critérios de avaliação (qualitativos)

  • Organização do repositório e clareza do README (completo e testável).
  • Consistência das convenções (commits, branches, padrões de código).
  • Diagramas e documentação de hardware (pinagem e BOM) coerentes.
  • Uso correto de tags/releases e CHANGELOG com SemVer.

Pesquisas complementares (sugestões)

  • Convention Commits e SemVer: como padronizar mensagens e versões.
  • Boas práticas de README em projetos IoT (exemplos no GitHub).
  • diagrams.net: dicas para diagramas limpos e legíveis.
  • Modelos de ISSUE/PR no GitHub e automações simples (Actions).

Entregáveis ao final do Capítulo 13

  • Repositório público/privado contendo README completo, docs/diagrama.png, BOM.md e docs/pinagem.md.
  • Templates de issues e PRs, CONTRIBUTING.md, LICENSE e CHANGELOG.md.
  • Histórico de commits semânticos em branches feature/ e merge na develop/main.
  • Release publicada v0.1.0 com notas de versão e tag correspondente.
