Capítulo 11 — Visualização e dashboards em tempo real

Carga: 4h (estimada)

Projeto-base: Dashboard web local que exibe telemetria em tempo real e dispara alertas por limiar

Stack fixa: HTML/CSS/JS + Chart.js + MQTT sobre WebSocket (HiveMQ público) e/ou REST/WebSocket local

Resultados de aprendizagem deste capítulo:

  • Planejar e montar um dashboard simples para dados IoT em tempo real.
  • Plotar séries temporais com atualização contínua e janelas de tempo.
  • Implementar alertas por limiar com histerese para reduzir falso positivo.
  • Consumir dados via MQTT (WebSocket) e/ou API REST/WS local.
  • Aplicar princípios básicos de UX para operação e leitura rápida.

Competências e Habilidades

  • Configurar e consumir fontes de dados em tempo real.
  • Construir gráficos de linha e cartões de KPI com JavaScript.
  • Aplicar agregações simples (média, min, max) por janela.
  • Projetar alertas com histerese e mensagens operacionais claras.
  • Documentar decisões de UX e testar com dados simulados e reais.

Plano de Aula (Capítulo 11)

1) Abertura (10 min) — Relembrar fluxo IoT ponta a ponta (dispositivo → broker/API → BD → dashboard). Apresentar objetivos: exibir séries temporais, KPIs e alertas em tempo real.

2) Teoria guiada (30–40 min) — Dashboards e princípios de UX; atualização em tempo real; séries temporais; janelas e agregações; alertas com histerese; quando usar MQTT x HTTP x WebSocket.

3) Laboratório (60–80 min) — Montar dashboard HTML/JS com Chart.js, assinar tópico MQTT via WebSocket ou consumir API/WS local, plotar dados e implementar alertas.

4) Testes e validação (20–30 min) — Simular diferentes taxas, latência e perda; inspecionar console; ajustar janela e limites.

5) Encerramento (10 min) — Revisar lições; propor atividades derivadas e checklist de entregáveis.

Parte Teórica (explicação do conteúdo)

1) O que é um dashboard em IoT e quando usar

Um dashboard é uma interface visual que reúne dados-chave para operação e decisão. Em IoT, ele mostra leituras de sensores, estado de atuadores e eventos. Bons dashboards priorizam clareza, confiabilidade e baixa latência para que operadores identifiquem rapidamente desvios ou alarmes.

Você pode ter dashboards locais (rodando no notebook/lab) ou web hospedados. Para prototipagem e aulas, uma página HTML com JavaScript e uma biblioteca de gráficos (ex.: Chart.js) é suficiente.

Onde vou aplicar isso? No passo a passo, você criará um dashboard HTML/JS que assina dados em tempo real e exibe cartões de KPI e um gráfico de linha.

2) Dados em tempo real: MQTT, HTTP e WebSocket

MQTT é leve e orientado a publicação/assinatura. Com suporte a WebSocket, o navegador consegue se conectar a um broker e receber mensagens instantaneamente. HTTP/REST é útil para consultas e histórico, mas não é ideal para push contínuo. WebSocket cria um canal bidirecional persistente entre cliente e servidor para eventos em tempo real.

Escolha MQTT quando tiver um broker disponível e tópicos bem definidos; use WebSocket quando você controla um servidor que emite eventos; mantenha HTTP para endpoints de histórico ou agregações.

Onde vou aplicar isso? No passo a passo, daremos duas opções: consumir MQTT via WebSocket (HiveMQ público) ou usar fetch/REST (simulador local) como fallback.

3) Séries temporais e janelas de visualização

Séries temporais são pontos no tempo (timestamp, valor). Em visualização, é prático manter uma janela deslizante (ex.: últimos 5 minutos ou últimos 100 pontos) para que o gráfico permaneça legível. Limitar a quantidade evita consumo excessivo de memória e melhora desempenho.

Também é comum aplicar agregações simples na janela (média, mínimo, máximo) e exibir como KPIs ou linhas auxiliares.

Onde vou aplicar isso? No script do dashboard, você manterá um buffer com tamanho máximo e atualizará KPIs de média/min/máx em cada novo ponto.

4) Alertas por limiar com histerese

Alerta por limiar dispara quando o valor ultrapassa um limite. Contudo, ruído pode causar “pisca” constante. Histerese define dois limiares: um para entrar em alerta (ex.: 30.0) e outro, menor, para sair (ex.: 29.0). Assim, o alerta só desarma quando o valor fica suficientemente abaixo do limite de entrada.

Boas práticas incluem debounce temporal (manter condição por X segundos antes de disparar) e mensagens objetivas para operação.

Onde vou aplicar isso? No passo a passo, você implementará um estado de alerta com limiar de entrada e saída e um badge visual.

5) UX mínima para operação

UX em dashboards deve facilitar leitura rápida: cores consistentes, unidades sempre visíveis, escala do gráfico adequada e cartões de KPI com rótulos claros. Disponibilize botões essenciais (pausar, limpar dados, alterar janela) e seções identificadas (Conexão, Métricas, Alertas).

Onde vou aplicar isso? Você criará cartões de KPI, um indicador de status de conexão e botões para controlar a janela/limites.

6) Dados de exemplo e saneamento

Ao consumir dados externos, valide o formato esperado (ex.: JSON com campos deviceId, ts, value). Descarte leituras absurdas (outliers), converta unidades se necessário e trate exceções para que o dashboard não trave por um pacote inválido.

Onde vou aplicar isso? No código, você validará campos obrigatórios e ignorará mensagens incompletas, logando avisos no console.

Exemplo de payload de telemetria (JSON)

{
  "deviceId": "esp32-lab-01",
  "ts": 1713985200000,
  "sensor": "tempC",
  "value": 28.6
}

Passo a Passo — Dashboard web em tempo real (MQTT/WebSocket ou REST)

Objetivo desta etapa:

Construir uma página HTML local que: (1) mostre KPIs (média, min, max), (2) plote gráfico de linha em tempo real, (3) dispare alerta com histerese, consumindo dados de um tópico MQTT via WebSocket ou de uma API REST de teste.


Preparar o ambiente e arquivos

Setup

Crie uma pasta de trabalho e um arquivo index.html. Usaremos CDNs para Chart.js e MQTT sobre WebSocket. Alternativamente, adicionaremos um modo “simulado/REST”.

<script>
// ===== Config MQTT (HiveMQ público) =====
const MQTT_URL = "wss://broker.hivemq.com:8884/mqtt"; // público, sem TLS mútua
let client = null;

// ===== Estado do dashboard =====
let buffer = []; // {x: Date, y: Number}
let alerts = 0;
let inAlarm = false;

const els = {
  dot: document.getElementById('statusDot'),
  txt: document.getElementById('statusText'),
  kAvg: document.getElementById('kpiAvg'),
  kMin: document.getElementById('kpiMin'),
  kMax: document.getElementById('kpiMax'),
  kAlr: document.getElementById('kpiAlerts'),
  alertBox: document.getElementById('alertBox'),
  win: document.getElementById('inpWindow'),
  thOn: document.getElementById('inpThOn'),
  thOff: document.getElementById('inpThOff'),
  topic: document.getElementById('inpTopic'),
};

// ===== Chart.js =====
const ctx = document.getElementById('chart');
const chart = new Chart(ctx, {
  type: 'line',
  data: {
    datasets: [{
      label: 'Temperatura (°C)',
      data: buffer,
      borderColor: '#dc3545',
      backgroundColor: 'rgba(220,53,69,.1)',
      tension: .2,
      pointRadius: 0
    }]
  },
  options: {
    responsive: true,
    animation: false,
    parsing: false,
    scales: {
      x: { type: 'time', time: { unit: 'second', tooltipFormat: 'HH:mm:ss' } },
      y: { title: { display: true, text: '°C' } }
    },
    plugins: {
      legend: { display: true }
    }
  }
});

// ===== Funções utilitárias =====
function setStatus(ok, text) {
  els.dot.style.background = ok ? '#198754' : '#6c757d';
  els.txt.textContent = text || (ok ? 'Conectado' : 'Desconectado');
}
function updateKpis() {
  const vals = buffer.map(p => p.y);
  if(vals.length === 0){
    els.kAvg.textContent = '--';
    els.kMin.textContent = '--';
    els.kMax.textContent = '--';
    return;
  }
  const sum = vals.reduce((a,b)=>a+b,0);
  const avg = sum/vals.length;
  const min = Math.min(...vals);
  const max = Math.max(...vals);
  els.kAvg.textContent = avg.toFixed(2);
  els.kMin.textContent = min.toFixed(2);
  els.kMax.textContent = max.toFixed(2);
}
function trimWindow() {
  const maxPoints = parseInt(els.win.value || '100', 10);
  if(buffer.length > maxPoints){
    buffer.splice(0, buffer.length - maxPoints);
  }
}
function handleAlarm(value){
  const thOn = parseFloat(els.thOn.value);
  const thOff = parseFloat(els.thOff.value);
  if(!Number.isFinite(thOn) || !Number.isFinite(thOff)) return;

  // entra em alarme
  if(!inAlarm && value >= thOn){
    inAlarm = true;
    alerts += 1;
    els.kAlr.textContent = alerts;
    els.alertBox.className = 'alert alert-danger mt-3';
    els.alertBox.textContent = `ALERTA: valor ${value.toFixed(2)}°C ≥ limiar ${thOn.toFixed(2)}°C`;
    els.alertBox.classList.remove('d-none');
  }
  // sai do alarme (histerese)
  if(inAlarm && value <= thOff){
    inAlarm = false;
    els.alertBox.className = 'alert alert-warning mt-3';
    els.alertBox.textContent = `RECUPERAÇÃO: valor ${value.toFixed(2)}°C ≤ limiar de saída ${thOff.toFixed(2)}°C`;
    els.alertBox.classList.remove('d-none');
    // opcional: esconder após 3s
    setTimeout(() => els.alertBox.classList.add('d-none'), 3000);
  }
}
function addPoint(ts, value){
  // validação básica
  if(!Number.isFinite(value) || !Number.isFinite(ts)) return;
  const time = new Date(ts);
  if(isNaN(time.getTime())) return;

  buffer.push({ x: time, y: value });
  trimWindow();
  chart.update();
  updateKpis();
  handleAlarm(value);
}

// ===== Conexão MQTT =====
function connectMqtt(){
  const topic = els.topic.value.trim();
  if(!topic){ alert('Informe um tópico'); return; }

  if(client){ try{ client.end(true); }catch(e){} client = null; }

  client = mqtt.connect(MQTT_URL);
  client.on('connect', () => {
    setStatus(true, 'Conectado (MQTT WS)');
    client.subscribe(topic, (err) => {
      if(err){ console.warn('Erro ao assinar:', err); }
    });
  });
  client.on('message', (topic, payload) => {
    try{
      const msg = JSON.parse(payload.toString());
      // esperado: { deviceId, ts, sensor, value }
      if(typeof msg.value !== 'number') return;
      const ts = msg.ts || Date.now();
      addPoint(ts, msg.value);
    }catch(e){
      console.warn('JSON inválido:', e);
    }
  });
  client.on('error', (err) => {
    console.error('MQTT erro:', err);
    setStatus(false, 'Erro MQTT');
  });
  client.on('close', () => setStatus(false, 'Desconectado'));
}

function disconnectMqtt(){
  if(client){
    try{ client.end(true); }catch(e){}
    client = null;
  }
  setStatus(false, 'Desconectado');
}

document.getElementById('btnConnect').addEventListener('click', connectMqtt);
document.getElementById('btnDisconnect').addEventListener('click', disconnectMqtt);
document.getElementById('btnClear').addEventListener('click', () => {
  buffer.length = 0;
  chart.update();
  updateKpis();
  inAlarm = false;
  els.alertBox.classList.add('d-none');
});

Publicar telemetria de teste via cliente MQTT

Teste com MQTT

Use um cliente MQTT (MQTTX/Explorer/Studio) e publique em lab/telemetria/temp um JSON no formato abaixo a cada 1s. Verifique o gráfico atualizar.

{
  "deviceId": "esp32-lab-01",
  "ts":  {{Date.now}},
  "sensor": "tempC",
  "value": 29.2
}

Substitua ts por um timestamp em milissegundos (ou omita para o dashboard usar Date.now()).

Alternativa: consumir dados via REST (pull)

HTTP/JSON

Se você implementou um endpoint local no Cap. 10 (ex.: http://localhost:3000/telemetria/ultimos), pode fazer polling simples:

// Exemplo de polling REST (adicione abaixo do script principal)
async function fetchUltimos(){
  try{
    const r = await fetch('http://localhost:3000/telemetria/ultimos?limit=1', { cache:'no-store' });
    if(!r.ok) return;
    const dados = await r.json(); // esperado: lista de { ts, value }
    dados.forEach(p => addPoint(p.ts || Date.now(), Number(p.value)));
  }catch(e){ /* silencioso no dashboard */ }
}
setInterval(fetchUltimos, 1000);
Observação: Polling tem mais latência e overhead que MQTT/WS. Útil para histórico e provas de conceito.

Critérios de avaliação (rubrica resumida)

  • Funcionalidade: dados em tempo real exibidos corretamente; KPIs atualizados.
  • Qualidade do código: clareza, comentários essenciais e tratamento de erros.
  • UX: legibilidade, cores consistentes, unidades, responsividade básica.
  • Alertas: histerese implementada e comportamento estável sob ruído.
  • Teste e evidências: prints, vídeos curtos ou logs que comprovem funcionamento.

Pesquisas complementares (sugestões)

  • Comparação de bibliotecas de gráficos para web (Chart.js, ECharts, Plotly): prós, contras e desempenho.
  • MQTT over WebSocket: como funciona no navegador, limitações e segurança.
  • Padrões de cores e acessibilidade em dashboards (WCAG): contraste e daltonismo.
  • Estratégias de agregação e downsampling para séries temporais volumosas.
  • Boas práticas de mensagens operacionais: como escrever alertas claros e acionáveis.
