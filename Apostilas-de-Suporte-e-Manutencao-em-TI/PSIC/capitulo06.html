Capítulo 06 — Estruturas de controle, modularização e bibliotecas

Carga: 4h (2h teoria + 2h prática)

Projeto-base: Refatoração do projeto do Cap. 05 (termômetro com LED/buzzer) em módulos com arquivo de configuração e logs

Stack fixa: ESP8266/ESP32 com MicroPython (Thonny) ou Arduino C++ (IDE Arduino), simulação opcional no Wokwi

Resultados de aprendizagem deste capítulo:

  • Organizar o firmware em camadas: hardware (drivers), lógica de negócio e rede.
  • Implementar e consumir funções utilitárias e bibliotecas de terceiros com responsabilidade.
  • Carregar configurações externas via JSON e aplicar validações básicas.
  • Adicionar logs com níveis (INFO/WARN/ERROR) e implementar watchdog simples.
  • Refatorar o projeto do Cap. 05 mantendo funcionalidade e melhorando manutenção.

Competências e Habilidades

  • Modularização e reutilização de código.
  • Leitura e integração de bibliotecas externas.
  • Documentação mínima de módulos e interfaces.
  • Depuração orientada a logs.
  • Boas práticas de configuração e tratamento de erros.

Parte Teórica (explicação do conteúdo)

Arquitetura do firmware em camadas

Separar o firmware em camadas torna o código mais legível, testável e fácil de manter. Uma divisão prática inclui: camada de hardware (drivers de GPIO/sensores/atuadores), camada de lógica (regras do negócio, como limites e histerese) e camada de rede (comunicação, que será expandida nos próximos capítulos).

Com essa separação, mudanças no sensor (hardware) não quebram a lógica e vice‑versa. Além disso, testes podem simular o hardware para validar a lógica sem o dispositivo físico.

Onde vou aplicar isso: na criação de módulos hw.py (hardware), logic.py (regras) e, futuramente, net.py (rede), além de um main.py que orquestra as camadas.

Funções utilitárias e drivers de sensores

Funções utilitárias concentram tarefas recorrentes, como conversões, formatações de timestamp e cálculo de médias. Drivers encapsulam o acesso ao hardware (ler ADC, acionar PWM, ler DHT/DS18B20), expondo uma API simples e estável para a lógica de negócios.

O uso de drivers evita duplicação e reduz erros de integração. Ao trocar o sensor, somente o driver muda, mantendo a interface para o restante do sistema.

Onde vou aplicar isso: criaremos um módulo sensors.py com uma classe/funcões para leitura de temperatura e um módulo actuators.py (ou dentro de hw.py) para LED/buzzer.

Configuração externa via JSON

Armazenar parâmetros em um arquivo JSON (ex.: limites de temperatura, pinos, níveis de log) permite ajustar o comportamento do firmware sem recompilar. Isso aumenta a reprodutibilidade e facilita o suporte.

É essencial validar o conteúdo lido: tipos corretos, faixas aceitáveis e valores padrão caso falte algo. Nunca assuma que o config está sempre perfeito.

Onde vou aplicar isso: criaremos config.json e um config.py que carrega e valida as chaves, fornecendo valores default seguros.

Tratamento de erros e logs

Logs com níveis (DEBUG/INFO/WARN/ERROR) aceleram o diagnóstico. Em dispositivos embarcados, direcionamos logs à Serial e, opcionalmente, gravamos em arquivo quando houver sistema de arquivos suficiente.

O tratamento de exceções (try/except) deve ser usado para isolar pontos sensíveis: leitura de sensores, acesso a arquivos e inicialização de periféricos. Nunca silencie erros sem registrar algo nos logs.

Onde vou aplicar isso: implementaremos um logger simples (logger.py) e envolveremos leituras sensíveis com try/except, registrando mensagens úteis.

Watchdog básico

O watchdog monitora o loop principal e reinicia o dispositivo se algo travar. Em MicroPython/ESP32 existe hardware/software watchdog; quando indisponível, um watchdog “lógico” (timer que verifica batimentos/heartbeats) já ajuda a detectar travamentos.

Defina intervalos realistas e “alimente” o watchdog em cada ciclo saudável. Evite operações bloqueantes ou sem timeouts.

Onde vou aplicar isso: criaremos watchdog.py com um temporizador simples e pulsos (feed) no final de cada iteração do loop.

2) Criar config.json e validador

Crie o arquivo de configuração com parâmetros ajustáveis:

{
  "pins": { "led": 2, "buzzer": 15, "sensor_adc": 34 },
  "limits": { "min_c": 15.0, "max_c": 28.0, "hysteresis": 0.8 },
  "loop": { "period_ms": 1000 },
  "log": { "level": "INFO" }
}

Implementação do loader/validador:

# config.py
import ujson as json

DEFAULTS = {
    "pins": {"led": 2, "buzzer": 15, "sensor_adc": 34},
    "limits": {"min_c": 15.0, "max_c": 28.0, "hysteresis": 1.0},
    "loop": {"period_ms": 1000},
    "log": {"level": "INFO"}
}

def _deep_merge(base, override):
    for k, v in override.items():
        if isinstance(v, dict) and isinstance(base.get(k), dict):
            _deep_merge(base[k], v)
        else:
            base[k] = v
    return base

def load_config(path="config.json"):
    cfg = DEFAULTS.copy()
    try:
        with open(path, "r") as f:
            data = json.loads(f.read())
        cfg = _deep_merge(cfg, data)
    except Exception as e:
        print("[WARN] config: usando DEFAULTS (erro ao ler:", e, ")")
    # validações mínimas
    limits = cfg["limits"]
    if limits["min_c"] >= limits["max_c"]:
        print("[WARN] config: min_c >= max_c, ajustando para defaults")
        cfg["limits"] = DEFAULTS["limits"].copy()
    if cfg["loop"]["period_ms"] < 200:
        print("[WARN] config: period_ms muito baixo, ajustando para 200")
        cfg["loop"]["period_ms"] = 200
    return cfg
Onde vou aplicar isso: o main.py chamará load_config() e passará os parâmetros para drivers e regras.

3) Logger simples com níveis

# logger.py
import time

LEVELS = {"DEBUG":10, "INFO":20, "WARN":30, "ERROR":40}
_current_level = LEVELS["INFO"]

def set_level(name:str):
    global _current_level
    _current_level = LEVELS.get(name.upper(), 20)

def _ts():
    try:
        return "{:.3f}".format(time.ticks_ms()/1000)
    except:
        return "0.000"

def log(level, msg):
    if LEVELS[level] >= _current_level:
        print("[{} {}] {}".format(_ts(), level, msg))

def debug(m): log("DEBUG", m)
def info(m):  log("INFO", m)
def warn(m):  log("WARN", m)
def error(m): log("ERROR", m)
Onde vou aplicar isso: em todos os pontos críticos (leitura de sensor, acionamento, exceções) para facilitar troubleshooting.

4) Drivers: sensores e atuadores (camada de hardware)

# hw/sensors.py
try:
    import machine
except:
    machine = None

class TempSensorADC:
    def __init__(self, pin):
        if machine is None:
            raise RuntimeError("Sem machine (simulação não configurada)")
        self.adc = machine.ADC(machine.Pin(pin))
        try:
            self.adc.atten(machine.ADC.ATTN_11DB)  # ESP32
        except:
            pass

    def read_celsius(self):
        raw = self.adc.read()
        # Exemplo: mapeamento fictício 0..4095 -> 0..50 °C
        temp_c = (raw/4095.0)*50.0
        return round(temp_c, 2)

# hw/actuators.py
try:
    import machine
except:
    machine = None

class Led:
    def __init__(self, pin, active_high=True):
        if machine is None:
            raise RuntimeError("Sem machine")
        self.pin = machine.Pin(pin, machine.Pin.OUT)
        self.active_high = active_high
        self.off()

    def on(self):
        self.pin.value(1 if self.active_high else 0)

    def off(self):
        self.pin.value(0 if self.active_high else 1)

class Buzzer:
    def __init__(self, pin):
        if machine is None:
            raise RuntimeError("Sem machine")
        self.pin = machine.Pin(pin, machine.Pin.OUT)
        self.off()

    def beep(self, ms=150):
        self.pin.value(1)
        try:
            import time
            time.sleep_ms(ms)
        finally:
            self.pin.value(0)

    def off(self):
        self.pin.value(0)
Onde vou aplicar isso: main.py criará instâncias desses drivers e a lógica decidirá quando ligá‑los.

5) Regras de negócio com histerese (camada de lógica)

# logic/rules.py
class HysteresisController:
    def __init__(self, min_c, max_c, h):
        self.min_c = min_c
        self.max_c = max_c
        self.h = h
        self._state = "OK"  # OK | LOW | HIGH

    def evaluate(self, temp_c: float):
        prev = self._state
        if self._state == "OK":
            if temp_c < self.min_c:
                self._state = "LOW"
            elif temp_c > self.max_c:
                self._state = "HIGH"
        elif self._state == "LOW":
            if temp_c >= self.min_c + self.h:
                self._state = "OK"
        elif self._state == "HIGH":
            if temp_c <= self.max_c - self.h:
                self._state = "OK"
        return prev, self._state
Onde vou aplicar isso: o main.py chamará evaluate(temp) e decidirá LED/buzzer conforme o estado.

6) Watchdog simples

# watchdog.py
import time

class SoftWatchdog:
    def __init__(self, timeout_ms=5000):
        self.timeout_ms = timeout_ms
        self.last_feed = time.ticks_ms()

    def feed(self):
        self.last_feed = time.ticks_ms()

    def check(self):
        if time.ticks_diff(time.ticks_ms(), self.last_feed) > self.timeout_ms:
            raise RuntimeError("Watchdog timeout")
Onde vou aplicar isso: no loop principal, após cada ciclo bem‑sucedido, chamar feed(); no início de cada ciclo, chamar check().

7) Orquestração no main.py

# main.py
import time
from config import load_config
import logger
from watchdog import SoftWatchdog
from hw.sensors import TempSensorADC
from hw.actuators import Led, Buzzer
from logic.rules import HysteresisController

def setup():
    cfg = load_config()
    logger.set_level(cfg["log"]["level"])
    logger.info("Iniciando sistema...")
    pins = cfg["pins"]
    led = Led(pins["led"])
    buz = Buzzer(pins["buzzer"])
    sensor = TempSensorADC(pins["sensor_adc"])
    ctrl = HysteresisController(
        cfg["limits"]["min_c"],
        cfg["limits"]["max_c"],
        cfg["limits"]["hysteresis"]
    )
    wd = SoftWatchdog(timeout_ms = max(3000, cfg["loop"]["period_ms"] * 3))
    period = cfg["loop"]["period_ms"]
    return cfg, sensor, led, buz, ctrl, wd, period

def loop(sensor, led, buz, ctrl, wd, period_ms):
    while True:
        try:
            wd.check()
            temp = sensor.read_celsius()
            prev, state = ctrl.evaluate(temp)
            logger.info("Temp={:.2f}°C estado={} (prev={})".format(temp, state, prev))
            if state == "HIGH":
                led.on(); buz.beep(100)
            elif state == "LOW":
                led.on(); buz.off()
            else:
                led.off(); buz.off()
            wd.feed()
            time.sleep_ms(period_ms)
        except Exception as e:
            logger.error("Falha no loop: {}".format(e))
            # backoff básico
            try: time.sleep_ms(500)
            except: pass

if __name__ == "__main__":
    cfg, sensor, led, buz, ctrl, wd, period = setup()
    loop(sensor, led, buz, ctrl, wd, period)
Onde vou aplicar isso: este é o ponto de entrada do firmware; a partir daqui você poderá integrar Wi‑Fi e MQTT nos próximos capítulos.

// logic/Rules.h
#pragma once
class HysteresisController {
  public:
    HysteresisController(float minC, float maxC, float h)
      : minC(minC), maxC(maxC), h(h), state(0) {} // 0 OK, -1 LOW, +1 HIGH
    int evaluate(float t){
      int prev = state;
      if(state == 0){
        if(t < minC) state = -1;
        else if(t > maxC) state = +1;
      } else if(state == -1){
        if(t >= minC + h) state = 0;
      } else if(state == +1){
        if(t <= maxC - h) state = 0;
      }
      return state;
    }
  private:
    float minC, maxC, h;
    int state;
};

Atividades Práticas para o(a) aluno(a) (desenvolver por conta própria)

Objetivo: Consolidar modularização, configuração via JSON e uso de logs/erros no firmware.

Atividade 1 — Níveis de log e métricas

Adicione um parâmetro log.level em config.json para alternar entre DEBUG e INFO. No nível DEBUG, registre também o valor bruto do ADC e o tempo de ciclo (ms). Gere um trecho de log e anexe ao README.

Atividade 2 — Fail‑safe de configuração

Simule um config.json inválido (por exemplo, min_c maior que max_c) e comente como o sistema reagiu. Proponha defaults seguros e registre no README.

Atividade 3 — Simulação de travamento

Introduza propositalmente um delay muito alto (p. ex., 10s) e verifique se o watchdog detecta e trata a condição. Ajuste timeouts conforme necessário e registre o comportamento nos logs.
