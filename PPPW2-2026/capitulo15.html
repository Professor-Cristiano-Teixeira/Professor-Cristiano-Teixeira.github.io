Capítulo 15 — Segurança Web na Prática: XSS, SQLi, CSRF, Sessões e Headers

Neste capítulo você vai blindar a lanchonete contra problemas comuns: SQL Injection, XSS, CSRF, além de fortalecer sessões/cookies e aplicar headers de segurança. Você também vai revisar o que já fez (CRUDs, Admin, API e Fetch) sob a ótica de segurança.

  • Prevenir XSS com escape de saída e validação.

Conceitos fundamentais

1) SQL Injection (SQLi)

Acontece quando você concatena entrada do usuário no SQL. A mitigação principal é usar prepared statements e validar tipos (int, float, etc.). 

// RUIM (vulnerável)
$sql = "SELECT * FROM item WHERE nome LIKE '%".$q."%'";

// BOM (prepared)
$st = $pdo->prepare("SELECT * FROM item WHERE nome LIKE :q");
$st->execute([':q'=>'%'.$q.'%']);

2) Cross-Site Scripting (XSS)

Acontece quando dados não confiáveis são exibidos no HTML sem escape. A mitigação é escape de saída (ex.: htmlspecialchars) e evitar inserir HTML vindo do usuário. 

// BOM: sanitização/escape ao imprimir
function esc($v){ return htmlspecialchars((string)$v, ENT_QUOTES, 'UTF-8'); }
echo esc($nome);

3) Cross-Site Request Forgery (CSRF)

Um atacante tenta induzir o usuário logado a enviar uma requisição. Mitigue usando tokens CSRF em ações sensíveis (POST/PUT/DELETE) e conferindo no servidor.

4) Sessões e cookies seguros

  • Regenerar ID no login: session_regenerate_id(true).
  • Cookie de sessão com HttpOnly e SameSite.
  • Em HTTPS: Secure=true.

5) Headers de segurança

Alguns headers ajudam a reduzir vetores comuns:

  • X-Content-Type-Options: nosniff
  • X-Frame-Options: DENY (ou CSP frame-ancestors)
  • Referrer-Policy: strict-origin-when-cross-origin
  • Content-Security-Policy (CSP) — avançado

Pesquisas complementares sugeridas

  • Diferença entre validação, sanitização e escape.
  • O que é CSP e como ela reduz XSS.
  • Como configurar headers no Apache (XAMPP) via .htaccess.

Passo a passo — Aplicando segurança no projeto

1) Centralize escape e validação

Crie utilitários em src/App/Util.php para reduzir repetição:

<?php
// src/App/Util.php
class Util {
  public static function esc($v): string {
    return htmlspecialchars((string)$v, ENT_QUOTES, 'UTF-8');
  }
  public static function int($v, int $default=0): int {
    $n = filter_var($v, FILTER_VALIDATE_INT);
    return $n === false ? $default : (int)$n;
  }
  public static function floatBR($v, float $default=0): float {
    $s = str_replace(',', '.', (string)$v);
    return is_numeric($s) ? (float)$s : $default;
  }
}

2) Garanta prepared statements em todo DAO

Audite todos os DAOs e substitua concatenação por parâmetros.

// Exemplo de busca segura
$q = trim((string)($_GET['q'] ?? ''));
$st = $pdo->prepare("SELECT id,nome,preco FROM item WHERE nome LIKE :q");
$st->execute([':q'=>'%'.$q.'%']);

3) Escape de saída em views

Toda vez que imprimir dado não confiável, use esc():

<h3><?= Util::esc($item['nome']) ?></h3>

4) CSRF em formulários sensíveis

Reutilize o Csrf do Cap. 06/07 e aplique em:

  • Salvar/Excluir no Admin
  • Logout
  • Endpoints POST/PUT/DELETE que dependem da sessão (opcional, mas recomendado)
// No form
<input type="hidden" name="csrf" value="<?= Util::esc(Csrf::token()) ?>" />

// No servidor
if(!Csrf::check((string)($_POST['csrf'] ?? ''))){
  http_response_code(403);
  exit('CSRF inválido');
}

5) Sessão segura (cookie params + regeneração)

No início do app (bootstrap), configure cookies de sessão (em DEV, Secure pode ser false):

<?php
// bootstrap_session.php
session_set_cookie_params([
  'lifetime' => 0,
  'path' => '/lanchonete',
  'secure' => false,   // true em HTTPS
  'httponly' => true,
  'samesite' => 'Lax'
]);
session_start();

6) Headers de segurança no PHP

<?php
header('X-Content-Type-Options: nosniff');
header('X-Frame-Options: DENY');
header('Referrer-Policy: strict-origin-when-cross-origin');
// CSP (exemplo mínimo, ajuste conforme necessário):
// header("Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';");

7) API REST (Cap. 14): autenticação e controle de acesso

Se sua API for usada apenas internamente (Admin logado), exija sessão/role no início do controlador. Ex.: exigir admin para POST/PUT/DELETE. 

<?php
require_once __DIR__.'/../../src/App/Auth.php';
Auth::requireLogin();
if(($_SERVER['REQUEST_METHOD'] ?? 'GET') !== 'GET'){
  Auth::requireRole('admin');
}

8) Erros e logs

Não exiba stack trace em produção. Em DEV ok; em PROD, registre log e retorne mensagem genérica.

<?php
try {
  // ...
} catch(Throwable $e){
  // error_log($e); // em produção
  http_response_code(500);
  echo json_encode(['ok'=>false,'error'=>'Erro no servidor']);
}
Resumo: Você reforçou o projeto com prepared statements, escape, CSRF, sessão/cookies seguros e headers — cobrindo os principais riscos.

Atividades práticas (para concluir na aula seguinte)

  1. Checklist de segurança: faça uma lista (arquivo README) com evidências: onde aplicou prepared, esc, CSRF e headers.
  2. Proteção API: bloqueie POST/PUT/DELETE na API para usuários não-admin.
  3. CSP (opcional): aplique uma CSP mínima e ajuste para não quebrar seus scripts.

Dica: “escape na saída” é obrigatório mesmo quando você valida entrada.
