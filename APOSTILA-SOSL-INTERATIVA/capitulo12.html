Capítulo 12 — Configurações, Processos e Rede (diagnóstico e administração)

Este capítulo fecha o 3º bimestre. Você vai aprender como um técnico diagnostica problemas de forma profissional: (1) configs (arquivos em /etc), (2) processos (o que está rodando e consumindo recursos) e (3) rede (IP, rota, DNS, portas). Ao final, você fará a Entrega 3 do Projeto Integrador com um relatório completo.

/etc (configs) nano / tee / diff systemctl ps / top / htop kill / pkill journalctl ip / ss ping / traceroute DNS (dig/nslookup) nmcli (Mint) Entrega 3

Objetivos de aprendizagem

  • Reconhecer configurações essenciais em /etc e aplicar mudanças seguras (backup + evidência).
  • Entender o que é um processo, como listar, monitorar e finalizar (ps/top/kill).
  • Relacionar serviços do systemd com processos e logs (systemctl + journalctl).
  • Diagnosticar rede: IP, rota, DNS e portas (ip/ss/ping/traceroute/dig).
  • Produzir um relatório de diagnóstico “ticket-ready” com comandos e evidências.
  • Entregar a Entrega 3 consolidando Caps 09–12 (CLI, arquivos, usuários, configs, processos e rede).

Pré-requisitos

  • Cap. 09 e 10: CLI e utilitários de texto (grep/tee).
  • Cap. 11: usuários/permissões e uso consciente de sudo.
  • Cap. 07: systemd e journalctl (conceitos básicos de logs).
Segurança: nunca edite configs sem backup. Evite mexer em rede do host. No laboratório, seguimos alterações pequenas e reversíveis.

1) Teoria: como um técnico pensa (configs + processos + rede)

1.1 Configuração é “fonte da verdade” (e muda comportamento)

Em Linux, muita configuração é feita por arquivos de texto em /etc. Quando um serviço “não funciona”, a causa frequentemente está em: configuração errada, arquivo inexistente, permissão ou dependência.

Alterar config é uma mudança controlada: você faz backup, aplica alteração mínima e registra evidência.

Onde vou aplicar isso? No passo a passo você vai fazer backup e comparar arquivos com diff.

1.2 Processo vs serviço: o que está rodando agora

Processo é um programa em execução (tem PID). Serviço é uma unit do systemd que controla processos (iniciar/parar/reiniciar) e registra logs.

Onde vou aplicar isso? Você vai cruzar systemctl status com ps e depois conferir logs no journalctl.

1.3 Diagnóstico de rede: camadas (IP → rota → DNS → portas)

Em suporte, “sem internet” pode significar várias coisas. A forma profissional é testar em camadas: IP (tenho endereço?) → rota (tenho caminho?) → DNS (resolvo nomes?) → portas (serviço responde?).

Onde vou aplicar isso? No passo a passo você vai usar ip, ip route, ping, resolvectl/dig e ss.

1.4 Logs são evidência, não “ruído”

Logs contam a história do que aconteceu. Para suporte, eles são evidência para justificar uma ação. Você já viu o journal no Cap. 07; aqui você usa logs para fechar diagnóstico.

Onde vou aplicar isso? Você vai incluir no relatório as últimas linhas relevantes do journal.

2) Configurações: arquivos essenciais e boas práticas

2.1 Arquivos essenciais em /etc (foco de suporte)

ArquivoPara que serveQuando olhar
/etc/os-releaseIdentifica distribuição/versãoInventário e compatibilidade
/etc/hostsResolução local de nomesProblemas pontuais de DNS/nome
/etc/hostnameNome da máquinaInventário e rede
/etc/resolv.confDNS (em algumas distros é gerenciado)Falha de resolução de nomes
/etc/fstabMontagens de discoErro de boot/montagem (cuidado)

2.2 Regra de mudança segura (padrão profissional)

  1. Identificar arquivo/serviço impactado.
  2. Backup: copiar o arquivo antes (.bak).
  3. Alteração mínima: uma mudança por vez.
  4. Validar: reiniciar serviço/testar.
  5. Registrar evidência: comandos e resultados (antes/depois).
Cuidado: em ambientes reais, mudanças exigem aprovação. Aqui é laboratório, mas o hábito é o mesmo.

2.3 Ferramentas úteis para configs

# editar (use com cautela)
sudo nano /etc/hosts

# salvar saída em arquivo e ver ao mesmo tempo
comando | tee -a relatorio.txt

# comparar arquivos (antes/depois)
diff -u arquivo.bak arquivo

3) Processos: listar, monitorar e finalizar com responsabilidade

3.1 ps: fotografia dos processos

# processos do usuário
ps -u $USER

# visão completa (muito usado)
ps aux | head

# procurar um processo
ps aux | grep -i firefox

3.2 top/htop: monitoramento ao vivo

top
# sair: q

# htop (se instalado)
htop
Onde vou aplicar isso? Quando “está lento”, você verifica CPU/RAM e quem está consumindo.

3.3 Finalizar processos: sinais e cuidado

kill envia sinais. O mais comum é TERM (15) — pedir para encerrar — e, em último caso, KILL (9) — força. 

# pedir para encerrar (preferível)
kill -15 PID

# forçar (último recurso)
kill -9 PID

# por nome (cuidado)
pkill -f nome_do_processo
Boa prática: sempre identifique o processo certo antes. Em suporte, finalizar errado pode derrubar serviços.

3.4 systemd + logs: status e histórico

# status de um serviço
systemctl status NetworkManager --no-pager

# logs do serviço
journalctl -u NetworkManager -b --no-pager | tail -n 40

4) Rede: IP, rota, DNS e portas (sequência de diagnóstico)

4.1 IP e interfaces

# resumo de interfaces e IP
ip -br a

# detalhes
ip a

4.2 Rotas

ip route

Sem rota padrão (default), a máquina pode não alcançar internet.

4.3 Teste de conectividade (camadas)

# ping no gateway (substitua pelo IP do seu gateway)
# ping -c 3 192.168.0.1

# ping em IP público (testa saída sem depender de DNS)
ping -c 3 8.8.8.8

# ping por nome (testa DNS)
ping -c 3 google.com

4.4 DNS (resolução de nomes)

# em sistemas com systemd-resolved
resolvectl status 2>/dev/null || true

# alternativas (podem não existir)
nslookup google.com 2>/dev/null || true
dig google.com +short 2>/dev/null || true
Se nslookup/dig não existir: é comum instalar dnsutils. Isso é opcional e deve ser registrado.

4.5 Portas e conexões (ss)

# sockets escutando (TCP/UDP)
ss -tulpen | head

# conexões TCP
ss -tan | head

4.6 Rede no desktop Mint (nmcli)

# status do NetworkManager
nmcli general status 2>/dev/null || true

# dispositivos
nmcli device status 2>/dev/null || true

5) Passo a passo (prático): relatório completo de diagnóstico

Objetivo: gerar um relatório único para anexar a um ticket: configs + processos + rede + logs.

Resultado final: arquivo ~/SOSL/cap12/diagnostico-cap12.txt com seções e evidências.
1 Preparar pasta e arquivo do relatórioSetup
mkdir -p ~/SOSL/cap12
R=~/SOSL/cap12/diagnostico-cap12.txt
: > "$R"
2 Cabeçalho do relatórioRegistro
{
  echo "DIAGNÓSTICO — CAP. 12";
  echo "Data: $(date)";
  echo "Usuário: $(whoami)";
  echo "Host: $(hostname)";
  echo "----------------------------------------";
} | tee -a "$R"
3 Configs essenciais (somente leitura)Configs
echo "\n[CONFIGS — /etc]" | tee -a "$R"

# Identificação do sistema
cat /etc/os-release | tee -a "$R"

# Hostname e hosts
echo "\n-- /etc/hostname" | tee -a "$R"
cat /etc/hostname | tee -a "$R"

echo "\n-- /etc/hosts" | tee -a "$R"
cat /etc/hosts | tee -a "$R"

Aqui você treina “config como evidência”: copiar o estado atual para o relatório.

4 Processos e recursosProcessos
echo "\n[PROCESSOS / RECURSOS]" | tee -a "$R"

# uptime/carga
uptime | tee -a "$R"

# memória
free -h | tee -a "$R"

# top 10 processos por CPU
ps aux --sort=-%cpu | head -n 11 | tee -a "$R"

# top 10 processos por memória
ps aux --sort=-%mem | head -n 11 | tee -a "$R"
Onde vou aplicar isso? Quando o usuário diz “está lento”, você entrega evidência de carga e top consumidores.
5 Serviços e logs (systemd + journal)Serviços
echo "\n[SERVIÇOS / FALHAS]" | tee -a "$R"

systemctl --failed | tee -a "$R"

echo "\n[LOGS — WARN/ERR (boot atual)]" | tee -a "$R"
journalctl -b -p warning..err --no-pager | tail -n 60 | tee -a "$R"

Se não houver falhas, ótimo — o relatório registra essa evidência.

6 Rede: IP, rota, DNS e portasRede
echo "\n[REDE — IP / ROTAS]" | tee -a "$R"
ip -br a | tee -a "$R"
ip route | tee -a "$R"

echo "\n[REDE — PING]" | tee -a "$R"
# ping em IP (sem DNS)
ping -c 2 8.8.8.8 | tee -a "$R" || true
# ping por nome (DNS)
ping -c 2 google.com | tee -a "$R" || true

echo "\n[REDE — DNS]" | tee -a "$R"
resolvectl status 2>/dev/null | tee -a "$R" || true
nslookup google.com 2>/dev/null | tee -a "$R" || true
dig google.com +short 2>/dev/null | tee -a "$R" || true

echo "\n[REDE — PORTAS (ss)]" | tee -a "$R"
ss -tulpen 2>/dev/null | head -n 30 | tee -a "$R" || true
Leitura rápida: ping IP funciona mas ping nome falha → suspeita de DNS. Se ip route não tem default → suspeita de rota/gateway.
7 (Opcional) Instalar ferramentas úteis e registrarOpcional

Se alguns comandos não existirem, você pode instalar ferramentas. Registre a mudança (Cap. 06).

# ferramentas comuns
sudo apt update
sudo apt install -y htop traceroute dnsutils

# testar
htop --version
traceroute -m 5 8.8.8.8 | head
nslookup google.com | head
Ambiente real: instalar pacotes exige autorização. Aqui é laboratório.
8 Revisar e anexar como evidênciaFinal
less "$R"

du -h "$R"
Parabéns: você criou um relatório completo com abordagem profissional (camadas + evidências).

6) Atividades práticas sugeridas (2–3)

  • Atividade 1 — Caso “DNS quebrado” (simulado): descreva, em 8–10 linhas, como você provaria que o problema é DNS usando a sequência IP → DNS.
  • Atividade 2 — Processo suspeito: escolha um processo com alto uso (ou simule abrindo várias abas) e registre: PID, %CPU, %MEM e ação tomada (apenas observação ou encerramento controlado em app de usuário).
  • Atividade 3 — Evidência de config: faça backup do /etc/hosts (sem mudar) e mostre no relatório a diferença (diff deve ser vazio).

Pesquisas complementares (2–5)

  • Diferença entre processo e thread (visão básica).
  • O que é gateway padrão e por que sem ele não há internet.
  • Como o DNS funciona (cliente → resolvedor → autoritativo) em termos simples.
  • Qual a diferença entre ss e netstat (e por que ss é mais moderno).
  • Boas práticas ao editar arquivos em /etc (backup, validação, reversão).

7) Projeto Integrador — Entrega 3 (Bimestre 3)

Entrega 3: “Relatório de Diagnóstico e Administração (B3)” — consolida Caps 09–12: CLI (ajuda e inventário), manipulação de arquivos/texto, usuários/permissões e diagnóstico de configs/processos/rede. Seu objetivo é entregar um documento que qualquer técnico de suporte entregaria em um chamado.

O que entregar

  • Relatório principal (Markdown/PDF) com: diagnóstico + evidências.
  • Evidências: trechos/prints de terminal (comandos executados e resultados).
  • Seção rede: IP, rota, ping IP e ping nome + conclusão (DNS/rota ok?).
  • Seção processos: top 5 CPU e top 5 MEM + análise simples.
  • Seção permissões: uma pasta compartilhada por grupo (do Cap. 11) e evidência do setgid.
  • Seção configs: backup de um arquivo (ex.: hosts) + evidência de diff/validação.

Critérios (rubrica rápida)

  • Método: diagnóstico em camadas (IP→rota→DNS→portas) com conclusão.
  • Clareza: linguagem técnica simples e objetiva.
  • Evidência: comandos e outputs sustentando afirmações.
  • Segurança: mudanças controladas (backup/registro), nada perigoso.
