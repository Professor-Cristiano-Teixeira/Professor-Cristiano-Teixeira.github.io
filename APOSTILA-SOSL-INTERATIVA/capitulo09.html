Capítulo 09 — CLI (1): Documentação/Ajuda e Informações do Sistema

Bem-vindo ao 3º bimestre (Administração via Linha de Comando). Neste capítulo você vai dominar dois blocos essenciais: (A) como encontrar ajuda rapidamente (man/info/--help/apropos) e (B) como coletar informações do sistema para diagnóstico e inventário. A meta é você virar um técnico que resolve problemas com evidências, não por tentativa e erro.

man / info --help apropos / whatis uname / os-release hostnamectl uptime lsblk / df free journalctl (consulta rápida)

Objetivos de aprendizagem

  • Entender o papel do terminal, shell e do prompt (o que você está vendo e por quê).
  • Usar documentação local: man, info, --help, apropos, whatis.
  • Interpretar saída de comandos e reconhecer padrões de erro (permissão, arquivo inexistente, comando não encontrado).
  • Coletar inventário do sistema (SO, kernel, CPU, RAM, disco, usuários logados, uptime).
  • Gerar um relatório técnico em arquivo (prática guiada), pronto para ser anexado a um ticket de suporte.

Pré-requisitos

  • VM Linux Mint funcionando (Cap. 04).
  • Noções de FHS e onde ficam logs/configs (Cap. 08).
  • Conforto básico com abrir o Terminal (Cap. 05/06).
Segurança: neste capítulo você vai consultar e coletar informações. Evite comandos destrutivos. Se você não entende um comando, consulte man antes de executar.
Como estudar sozinho (método): (1) Leia a teoria por blocos • (2) Faça o passo a passo e gere seu relatório • (3) Responda o quiz • (4) Complete o checklist.

1) Fundamentos da CLI (caprichado, mas direto)

1.1 Terminal, shell e prompt: o que você realmente está usando

O Terminal é o aplicativo (janela) onde você digita. O Shell é o interpretador (por exemplo, bash) que lê seu texto, executa programas e mostra a saída. O prompt é o “convite” do shell (algo como aluno@sosl-vm:~$) que indica que ele está pronto.

Ler o prompt é uma habilidade de suporte: ele costuma mostrar o usuário, a máquina e a pasta atual. Isso evita erros como executar comandos no lugar errado ou como usuário errado.

Onde vou aplicar isso? No passo a passo você vai confirmar a pasta atual e criar arquivos sem se perder.

1.2 Comando, opção e argumento (e como ler um exemplo)

Um comando pode ter opções (flags) e argumentos (alvos). Exemplo: ls -lah /etc. Aqui, ls é o comando, -lah são opções e /etc é o argumento (a pasta alvo). Aprender a ler isso é aprender a reproduzir instruções de suporte.

Onde vou aplicar isso? Ao usar journalctl -b e df -h você vai reconhecer o padrão: comando + opções.

1.3 Saída, erro e código de retorno (exit status)

Programas escrevem saída normal (stdout) e erros (stderr). Além disso, cada comando retorna um código de saída: 0 normalmente significa sucesso; valores diferentes de 0 indicam erro. Isso é a base de scripts (Cap. 13), mas já ajuda no suporte. 

# Ver o código de saída do último comando
echo $?

Você usará isso no passo a passo ao testar comandos e entender quando algo falhou.

1.4 Autocompletar, histórico e produtividade (o que poupa tempo)

  • Tab: completa nomes de comandos/arquivos e reduz erros de digitação.
  • Setas ↑/↓: navega pelo histórico de comandos.
  • Ctrl+R: busca no histórico (digite parte do comando).
  • Ctrl+C: interrompe um comando travado.
  • Ctrl+L: limpa a tela (equivalente a clear).
Onde vou aplicar isso? Em inventários longos, você vai repetir padrões. O histórico economiza muito tempo.

1.5 Segurança básica: sudo, root e por que você não deve “virar root” sem necessidade

Em Linux, a conta root tem controle total. O sudo permite executar um comando com privilégios elevados. Em suporte, a regra é: use sudo apenas quando necessário e prefira comandos de consulta sem sudo. Isso reduz risco de apagar/alterar algo por engano.

Onde vou aplicar isso? No passo a passo, apenas alguns comandos (como du em /) podem precisar de sudo. Todo o restante é diagnóstico, com baixo risco.

2) Documentação e ajuda: aprender a se virar sem professor

2.1 man: manual local (o “manual do técnico”)

O comando man abre o manual de um comando. Ele funciona mesmo sem internet e costuma ser a fonte mais confiável. O segredo é saber navegar dentro do man:

  • q sai do manual
  • / busca dentro do texto (digite a palavra e Enter)
  • n vai para a próxima ocorrência
  • g vai para o começo, G para o fim
man ls
man journalctl
man systemctl
Onde vou aplicar isso? Quando um comando tiver muitas opções, você vai usar / dentro do man para achar “EXAMPLES”, “OPTIONS”.

2.2 --help: ajuda rápida (boa para lembrar opções comuns)

A maioria dos comandos suporta --help. Ele mostra um resumo rápido. É excelente quando você já sabe o básico e quer só lembrar uma opção. 

ls --help | head
journalctl --help | head

2.3 info: documentação em formato “navegável”

Alguns projetos (principalmente GNU) mantêm documentação em info. É mais detalhada e organizada por tópicos. Nem todo comando tem info, mas quando tem, costuma ser excelente. 

info coreutils 'ls invocation'
info bash

Se “info coreutils” não funcionar, teste apenas info ls ou info bash.

2.4 apropos e whatis: achar comandos quando você não sabe o nome

Uma situação típica de suporte: “preciso de um comando para ver uso de disco, mas não lembro o nome”. apropos pesquisa no índice de manpages por palavra-chave. whatis mostra descrição curta de um comando. 

# Procurar manpages relacionadas à palavra "disk"
apropos disk | head -n 15

# Descobrir o que um comando faz (descrição curta)
whatis df
whatis uname
Se apropos não retornar nada: o banco de dados de manpages pode não estar atualizado. Em algumas distros, roda-se sudo mandb (opcional) para atualizar.

2.5 Padrão de leitura profissional de manpages

Para ser autônomo, leia sempre nesta ordem: NAME (o que é) → SYNOPSIS (forma de uso) → DESCRIPTION (entenda o objetivo) → OPTIONS (as mais usadas) → EXAMPLES.

Onde vou aplicar isso? No passo a passo, você vai consultar man hostnamectl e man lsblk para entender opções.

3) Informações do sistema: inventário e diagnóstico (o que um técnico coleta)

3.1 Identidade do sistema: distribuição, versão e kernel

Em suporte, a primeira pergunta é “qual sistema e qual versão?”. Isso muda tudo: pacotes, comandos, caminhos, compatibilidade. Você pode obter isso de várias formas (algumas mais universais): 

# Versão do kernel e arquitetura
uname -a
uname -r
uname -m

# Informações da distribuição (mais universal)
cat /etc/os-release

# Em algumas distros (se existir)
lsb_release -a 2>/dev/null || true
Onde vou aplicar isso? No relatório de inventário (passo a passo) você vai registrar os principais campos do /etc/os-release.

3.2 Nome da máquina e contexto (hostname)

O nome da máquina (hostname) aparece em logs, rede e identificação de inventário. Em um laboratório com várias VMs, padronizar o hostname ajuda muito. 

hostname
hostnamectl
Alterar hostname é possível, mas aqui vamos apenas consultar. Mudanças serão tratadas em capítulos de configuração.

3.3 Tempo ligado e carga do sistema (uptime/load)

“Máquina está lenta” pode estar ligado a alta carga (load) ou falta de recursos. uptime dá tempo ligado e carga. top/htop (Cap. 12) detalha processos. 

uptime

3.4 Usuários e sessões (quem está logado?)

Em suporte interno, você precisa saber quem está logado e por onde (local/tty). Isso ajuda em auditoria básica e diagnóstico. 

who
whoami
id
w

3.5 CPU, memória e armazenamento (o trio do desempenho)

Para inventário e diagnóstico, você precisa de evidências do hardware/recursos. Em VM, isso também valida se você configurou corretamente. 

# CPU
lscpu | head -n 25

# Memória
free -h

# Discos e partições (muito útil)
lsblk

# Espaço em disco por filesystem
df -h
Onde vou aplicar isso? No passo a passo você vai coletar essas saídas e montar um relatório padronizado.

3.6 Logs rápidos: o que aconteceu “agora há pouco”

Mesmo antes de capítulos avançados, você já pode coletar logs de erros recentes: 

# Últimos erros/avisos do boot atual
journalctl -b -p warning..err --no-pager | tail -n 40

Isso é excelente para anexar em ticket quando algo falha “sem motivo”.

4) Passo a passo (prático): gerar um relatório de inventário do sistema

Objetivo: você produzir um arquivo de inventário em SOSL/cap09, com evidências copiáveis para suporte.

Resultado esperado: um arquivo inventario-cap09.txt (ou .md) com seções: SO, kernel, hostname, uptime, usuários, CPU, RAM, discos e erros recentes.
1 Preparar pastas e arquivo de relatórioSetup
# Criar pasta do capítulo
mkdir -p ~/SOSL/cap09

# Criar arquivo (vazio) do relatório
: > ~/SOSL/cap09/inventario-cap09.txt

O operador : > arquivo cria/zera o arquivo de forma segura (sem editar ainda).

2 Dica de registro: usar tee para gravar e mostrarRegistro

Você pode copiar/colar saídas manualmente, mas uma forma profissional é usar tee para gravar no arquivo. Vamos usar tee -a (append) para adicionar ao final do relatório. 

# Definir variável com caminho do relatório (facilita)
R=~/SOSL/cap09/inventario-cap09.txt

# Escrever um cabeçalho
{
  echo "INVENTÁRIO — CAP. 09 (CLI I)";
  echo "Data: $(date)";
  echo "Usuario: $(whoami)";
  echo "----------------------------------------";
} | tee -a "$R"

Se você não conhece variáveis ainda, apenas copie exatamente. Você vai aprofundar scripts no Cap. 13.

3 SO, kernel e hostnameIdentidade
echo "\n[SO / DISTRIBUIÇÃO]" | tee -a "$R"
cat /etc/os-release | tee -a "$R"

echo "\n[KERNEL]" | tee -a "$R"
uname -a | tee -a "$R"

echo "\n[HOSTNAME]" | tee -a "$R"
hostnamectl | tee -a "$R"
Onde vou aplicar isso? Em qualquer ticket: “Mint versão X, kernel Y” é o primeiro dado que um analista pede.
4 Uptime, usuários logados e contextoSessões
echo "\n[UPTIME / CARGA]" | tee -a "$R"
uptime | tee -a "$R"

echo "\n[USUÁRIOS / SESSÕES]" | tee -a "$R"
who | tee -a "$R"
id | tee -a "$R"

Se a máquina está lenta, uptime e carga (load) ajudam a formar hipóteses.

5 CPU, memória e discosRecursos
echo "\n[CPU]" | tee -a "$R"
lscpu | head -n 25 | tee -a "$R"

echo "\n[MEMÓRIA]" | tee -a "$R"
free -h | tee -a "$R"

echo "\n[DISCOS / PARTIÇÕES]" | tee -a "$R"
lsblk | tee -a "$R"

echo "\n[ESPAÇO EM DISCO]" | tee -a "$R"
df -h | tee -a "$R"
Boa prática: em suporte, sempre registre “antes e depois” se você fizer mudanças (ex.: instalar pacotes, limpar disco).
6 Erros recentes (journal) — evidência rápidaLogs
echo "\n[ERROS/AVISOS RECENTES — BOOT ATUAL]" | tee -a "$R"
journalctl -b -p warning..err --no-pager | tail -n 40 | tee -a "$R"
Atenção: se aparecerem dados sensíveis, não compartilhe publicamente. Em sala, entregue apenas ao professor.
7 Revisar o relatório e salvar evidênciaFinal
# Visualizar no terminal
less "$R"

# Mostrar tamanho do arquivo
du -h "$R"

# (Opcional) copiar o arquivo para a pasta compartilhada do host
# cp "$R" /media/sf_SOSL/ 2>/dev/null || true

Se /media/sf_SOSL não existir, você não configurou pasta compartilhada — isso é opcional.

Parabéns: você acabou de produzir um inventário profissional, com evidências. Esse padrão será reutilizado em tickets e entregas futuras.
