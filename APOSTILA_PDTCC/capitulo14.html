Capítulo 14 — UML (Classes) + Modelo de Dados (MER/DER) — Revisão e Padrão de Entrega

Carga: 100 min (1 aula semanal)

Projeto-base: TCC em formato de Artigo Científico + Sistema Computacional (com anexos)

Ferramentas: draw.io (diagrams.net) / StarUML • Banco (MySQL/PostgreSQL/SQLite) • SQL • Repositório (Git)

Resultados de aprendizagem deste capítulo:

  • Revisar diagrama de classes (UML) e produzir um modelo de classes do domínio coerente com UCs e requisitos.
  • Revisar MER/DER e transformar o modelo conceitual em esquema relacional (tabelas, chaves e relacionamentos).
  • Definir dicionário de dados e regras de integridade (PK/FK, UNIQUE, CHECK) para reduzir bugs.
  • Conectar tudo com rastreabilidade: UC → classes → tabelas → operações CRUD → testes/evidências.

Competências e habilidades

  • Modelar classes com atributos, responsabilidades, relacionamentos e multiplicidades corretamente.
  • Aplicar herança, associação, composição e agregação com sentido (sem “enfeite”).
  • Projetar esquema relacional consistente (normalização básica e integridade) adequado ao escopo do TCC.
  • Gerar artefatos de entrega: diagramas (PDF/PNG), DDL SQL, dicionário de dados e evidências no repositório.

Plano de Aula (Capítulo 14)

Aula (100 min) — Organização

  • 10 min — Retomada do Cap. 13: UCs (diagrama + especificações) e testes derivados.
  • 25 min — Revisão UML Classes: o que é esperado (classes do domínio, atributos, relações e multiplicidades).
  • 25 min — Revisão MER/DER: entidades, relacionamentos, cardinalidades e chaves.
  • 20 min — Mapeamento para tabelas: PK/FK, N:N, normalização básica, integridade e constraints.
  • 15 min — Entregáveis: diagrama de classes + DER + dicionário de dados + DDL no repositório.
  • 5 min — Fechamento: checklist + rastreabilidade UC → classes → tabelas.

Agenda do capítulo (o que fazer)

  1. Selecionar 6–12 classes centrais do domínio (não do framework) e desenhar o diagrama com relações.
  2. Construir/atualizar MER/DER (entidades e relacionamentos) coerente com o domínio e UCs.
  3. Mapear para esquema relacional e criar DDL SQL (CREATE TABLE) com PK/FK/UNIQUE/CHECK.
  4. Criar dicionário de dados (tabela, campo, tipo, regra, exemplo).
  5. Atualizar rastreabilidade: UC → classes/tabelas → endpoints/telas → testes → evidências.
Observação: A banca espera coerência: o UC que você mostrou precisa existir nas classes e nas tabelas. Diagramas gigantes e “genéricos” (com classes de framework) normalmente perdem ponto.

Parte Teórica (explicação do conteúdo)

1) Diagrama de Classes: o que é (e o que a banca espera)

O Diagrama de Classes (UML) representa a estrutura estática do sistema: classes, atributos, métodos (quando necessário) e relacionamentos. Para o TCC técnico, a banca espera principalmente um modelo do domínio — ou seja, classes que representam o mundo do problema (Aviso, Usuário, Turma, Agendamento, Item, etc.).

O erro clássico é colocar classes de framework (Controller, Repository, Activity, Page) e esquecer as classes do domínio. A banca quer ver: (1) classes centrais do problema, (2) relações corretas (1:1, 1:N, N:N), (3) multiplicidades e (4) coerência com requisitos e casos de uso (Cap. 13).

Regra prática: se a classe não aparece em nenhum UC/requisito e não guarda informação do domínio, ela provavelmente não precisa estar no diagrama de classes do TCC.

2) Classe, atributo e responsabilidade: modelando com propósito

Uma classe agrupa dados (atributos) e comportamento (métodos) relacionados. Em TCC, você pode focar em atributos e relacionamentos; métodos podem aparecer apenas quando ajudarem a explicar regras (ex.: calcularPrazo(), validarPermissao()).

Boas práticas para atributos: nome claro, tipo (String, DateTime, int), e sem duplicar informação. Ex.: não guarde “idade” se você tem “dataNascimento” (idade muda). Guarde o que é estável e derivável.

Dica: escreva uma frase por classe: “A classe X representa ____ e serve para ____”. Se você não consegue, a classe está mal definida.

3) Relacionamentos e multiplicidade (onde os alunos mais erram)

Relacionamentos indicam como classes se conectam. No TCC, o essencial é acertar associação e multiplicidades (1, 0..1, 0..*, 1..*). Multiplicidade descreve quantidade: “Uma Turma tem muitos Alunos (1..*)” e “Um Aluno pertence a uma Turma (1)”.

Diferenças importantes:

  • Associação: relação geral (Aluno — Turma).
  • Agregação (losango vazio): parte–todo fraca (Turma agrega Alunos), usada pouco; se não souber, use associação.
  • Composição (losango cheio): parte–todo forte (Aviso compõe Anexo). Se o “todo” é deletado, as partes perdem sentido.
  • Herança: especialização (Usuário → Aluno/Professor) quando compartilham atributos e regras.
Regra de banca: use composição só quando for realmente dependente. Caso contrário, use associação simples para evitar erros conceituais.

4) Do UC para classes: como garantir coerência (rastreabilidade)

Um caminho prático é: pegue 3 UCs principais (Cap. 13) e liste substantivos e dados manipulados. Substantivos viram candidatos a classes: “aviso”, “turma”, “usuário”, “confirmação”, “notificação”. Depois, pergunte: “quais atributos são necessários para cumprir o UC?”

Exemplo: UC “Cadastrar aviso” exige atributos como título, descrição, data, prioridade e autor. Isso aponta para classe Aviso e relação com Usuário/Professor. UC “Confirmar leitura” aponta para uma classe de associação (LeituraConfirmada) ou uma tabela de relacionamento entre Usuário e Aviso com timestamp.

Resultado: cada UC principal deve tocar pelo menos 1 classe e 1 tabela. Se não tocar, falta modelagem.

5) MER/DER: revisão rápida (conceitual → lógico)

O MER (Modelo Entidade-Relacionamento) representa entidades e relacionamentos no nível conceitual. O DER (Diagrama ER) representa isso visualmente. No técnico, o essencial é: identificar entidades (tabelas), atributos (campos) e cardinalidades (1:1, 1:N, N:N).

Erros comuns: (1) criar entidade para tudo (inclusive valores simples), (2) esquecer tabela associativa em N:N, (3) não definir chaves, (4) misturar dados derivados e redundantes. Use o glossário para padronizar nomes e significado (Cap. 09).

Regra: sempre marque PK e defina como FK aparece nos relacionamentos (e o que acontece no delete/update).

6) Mapeamento para tabelas: PK, FK e N:N (tabela associativa)

Quando você sai do DER e vai para o banco relacional, as regras são simples:

  • 1:N: a FK fica no lado N. Ex.: Turma(1) — Aluno(N) → aluno.turma_id.
  • 1:1: FK em um lado com UNIQUE (ou juntar em uma tabela, dependendo do caso).
  • N:N: vira tabela associativa. Ex.: Usuario(N) — Aviso(N) para “confirmação de leitura” → tabela leitura (usuario_id, aviso_id, data_hora).

A banca gosta quando vocês incluem integridade (constraints): NOT NULL, UNIQUE, CHECK, e FKs com regras (ON DELETE/UPDATE) coerentes. Isso reduz bugs e mostra maturidade técnica.

Dica: para TCC, é melhor um esquema simples e correto do que um enorme e inconsistente.

7) Normalização básica (o suficiente para o Técnico)

Você não precisa escrever um tratado de normalização, mas precisa evitar erros óbvios. Três regras simples ajudam:

  1. 1FN: cada campo guarda um valor atômico (não guarde lista em uma coluna).
  2. 2FN: em tabela com chave composta, atributos dependem da chave toda (em N:N, cuidado).
  3. 3FN: evite dependências transitivas (não repita dados que pertencem a outra entidade).

Ex.: não repita “nomeTurma” dentro de Aviso se existe Turma. Use turma_id e faça JOIN. Isso facilita manutenção.

8) Dicionário de Dados: o artefato que salva o projeto

Dicionário de dados é uma tabela que documenta cada campo do banco: nome, tipo, tamanho, regra, exemplo e observação. É muito útil para: (a) dividir trabalho (frontend/backend/BD), (b) padronizar validação, (c) evitar mudanças aleatórias de tipo e nome, e (d) facilitar escrita do artigo/anexos.

No TCC, o dicionário é simples: Tabela | Campo | Tipo | Obrigatório | Regra | Exemplo.

Boa prática: o dicionário deve usar a mesma terminologia do glossário. Se o termo mudou, atualize ambos.

9) O que entregar no Cap. 14 (padrão de banca)

  • Diagrama de classes (PDF/PNG) com 6–12 classes do domínio e multiplicidades.
  • DER/MER (PDF/PNG) com PK/FK e cardinalidades.
  • DDL SQL (arquivo .sql) com CREATE TABLE e constraints.
  • Dicionário de dados (planilha ou seção /docs).
  • Rastreabilidade: UC → classes/tabelas → endpoints/telas → testes.
Importante: versionar tudo no repositório em /docs (diagramas) e /db (SQL). Evidência = commit + export em PDF.

Glossário rápido

  • Classe: estrutura do domínio com atributos e responsabilidades.
  • Multiplicidade: quantidade (1, 0..1, 0..*, 1..*).
  • PK/FK: chave primária / chave estrangeira.
  • Tabela associativa: resolve N:N no relacional.
  • DDL: comandos SQL de definição (CREATE/ALTER).
  • Dicionário de dados: documentação dos campos e regras.

Passo a passo — Diagrama de Classes + DER + Dicionário + DDL (SQL)

Objetivo desta etapa:

Construir o modelo de classes e dados do projeto e gerar os arquivos de entrega versionados no repositório.

Passo a passo (sem programação) — do domínio ao banco

  1. Escolha 3 UCs principais (Cap. 13) e liste substantivos e dados manipulados.
  2. Crie classes do domínio (6–12): nome + 4–8 atributos essenciais.
  3. Desenhe relacionamentos e multiplicidades (1, 0..*, etc.).
  4. Monte DER/MER com entidades correspondentes e cardinalidades.
  5. Mapeie para tabelas:
    • 1:N → FK no lado N
    • N:N → tabela associativa
    • 1:1 → FK + UNIQUE (quando fizer sentido)
  6. Escreva DDL com PK/FK/UNIQUE/CHECK e tipos adequados.
  7. Crie dicionário de dados (planilha) e adicione regras/ exemplos.
  8. Versione: /docs/UML (PDF), /db/schema.sql, /docs/dicionario_dados.xlsx.

Exemplo de DDL (SQL) — simplificado

-- schema.sql (exemplo)
CREATE TABLE turma (
  id INTEGER PRIMARY KEY,
  nome VARCHAR(60) NOT NULL UNIQUE
);

CREATE TABLE usuario (
  id INTEGER PRIMARY KEY,
  turma_id INTEGER NOT NULL,
  nome VARCHAR(80) NOT NULL,
  email VARCHAR(120) NOT NULL UNIQUE,
  senha_hash VARCHAR(255) NOT NULL,
  FOREIGN KEY (turma_id) REFERENCES turma(id)
);

CREATE TABLE aviso (
  id INTEGER PRIMARY KEY,
  autor_id INTEGER NOT NULL,
  titulo VARCHAR(100) NOT NULL,
  descricao TEXT NOT NULL,
  data_publicacao DATETIME NOT NULL,
  prioridade INTEGER NOT NULL CHECK (prioridade IN (1,2,3)),
  FOREIGN KEY (autor_id) REFERENCES usuario(id)
);

CREATE TABLE leitura (
  usuario_id INTEGER NOT NULL,
  aviso_id INTEGER NOT NULL,
  data_hora DATETIME NOT NULL,
  PRIMARY KEY (usuario_id, aviso_id),
  FOREIGN KEY (usuario_id) REFERENCES usuario(id),
  FOREIGN KEY (aviso_id) REFERENCES aviso(id)
);
Dica: Use os exemplos como referência e adapte ao seu domínio (não copie sem ajustar ao seu problema).

Atividades Práticas para o(a) aluno(a)

  • Evitar classes de framework; focar no domínio.

Atividade B — MER/DER + DDL

  • Gerar schema.sql com constraints (NOT NULL, UNIQUE, CHECK).

Atividade C — Dicionário + Rastreabilidade

  • Criar dicionário de dados (tabela/campo/tipo/regra/exemplo).
  • Ligar UC → classes/tabelas → operações CRUD.
  • Registrar evidências no repositório (commits + PDFs).

Critérios de avaliação (rubrica rápida)

  • UML: classes do domínio, relações e multiplicidades corretas e legíveis.
  • Dados: DER coerente, PK/FK definidos e N:N resolvido com tabela associativa.
  • Integridade: uso adequado de constraints e tipos (reduzindo inconsistências).
  • Dicionário: campos documentados com regras e exemplos.
  • Coerência: ligação com UCs/requisitos e rastreabilidade atualizada.

Pesquisas complementares (sugestões)
